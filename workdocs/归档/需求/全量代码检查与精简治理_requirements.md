## 2. 用户故事

1. 作为项目负责人，我希望有一套“全量体检 + 分波次收敛 + 强门禁”的治理机制，避免每次迭代都继续变胖。
2. 作为后端维护者，我希望编排、路由、兜底策略在正确层级收敛，减少跨层重复逻辑。
3. 作为前端维护者，我希望将超大组件拆成可复用模块，降低联调和回归成本。
4. 作为评审与运维人员，我希望 PR 能自动识别“无退场说明的扩张改动”，并在 CI 阶段阻断。

## 3. 目标、范围与边界

### 3.1 目标

1. 完成全仓热点审计并按 P0/P1/P2 输出治理台账。
2. 以“行为等价”为前提完成关键热点减法重构。
3. 建立覆盖 `feature/refactor` 的 change-balance 强门禁。
4. 建立兜底/兼容逻辑登记与退役闭环，防止新债务持续累积。

### 3.2 范围（本期）

1. 后端：`app/**/*.py` 的编排/路由/服务层热点收敛。
2. 前端：`web/src/**/*.{ts,tsx}` 的大组件拆分与重复适配收敛。
3. 流程治理：规则、PR 模板、CI 门禁、审计脚本。
4. 文档治理：`requirements + implementation_plan + SUMMARY` 索引同步。

### 3.3 边界（本期不做）

1. 不新增业务功能和产品交互需求。
2. 不更换数据库、消息总线或前后端框架。
3. 不做全仓格式化或纯风格清理式改动。

## 4. 方案对比与选型

| 方案 | 优点 | 缺点 | 成本 | 推荐度 |
|---|---|---|---|---|
| A. 只做报告，不改流程门禁 | 快速交付，风险低 | 治理不可持续，后续仍会反弹 | 低 | ⭐⭐⭐ |
| B. 体检 + 轻门禁 | 成本适中，短期见效 | 对高复杂度热点收敛不足 | 中 | ⭐⭐⭐⭐ |
| C. 体检 + 强门禁 + 分波次重构 | 同时解决历史债务和未来反弹，形成闭环 | 对组织执行纪律要求高 | 高 | ⭐⭐⭐⭐⭐ |

结论：采用方案 C。

## 5. 验收标准

### 5.1 功能性（Happy Path）

1. 输出可追溯的热点台账，覆盖后端/前端/流程治理三类问题。
2. W1/W2/W3 波次均有明确任务、验证命令、回滚点。
3. PR 模板新增“退场清单/豁免理由/截止日期”字段并在 CI 受检。
4. 新增 `change-balance` 门禁后，`feature/refactor` PR 可自动检查预算与减法说明。

### 5.2 异常与边界

1. 若重构导致关键链路失败，必须在同波次内回滚并阻断下游波次。
2. 若临时豁免门禁，必须绑定技术债卡与截止日期，禁止无限期豁免。
3. 若证据不完整（测试未跑、日志缺失），不得标记完成。

### 5.3 性能与稳定性

1. 关键链路性能不低于当前基线（P95 波动控制在可接受范围内）。
2. 重构后核心回归链路（chat/data/todo/admin）通过率 100%。
3. CI 门禁新增后，不显著增加流水线不可接受时延。

## 6. 非功能需求

### 6.1 可维护性

1. 超长函数/组件需拆分为职责清晰的模块边界。
2. 兜底逻辑必须集中管理并可追溯，避免策略散落。

### 6.2 可观测性

1. 对“fallback 触发、豁免门禁、回滚执行”有结构化记录。
2. 每个 feature_id 具备验证命令与证据入口。

### 6.3 一致性与安全

1. PR 与任务映射一一对应，禁止无归属改动。
2. 规则升级不得破坏现有安全校验链路。

## 8. 风险与约束

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 波次并发过高导致回归面失控 | 发布质量下降 | 严格按 W1->W2->W3 分段放行 |
| 历史兜底分支删减过快 | 功能回退 | 每个分支绑定回滚点与灰度开关 |
| 门禁策略过严阻断正常开发 | 研发效率短期下降 | 引入可追溯豁免机制并按周复盘阈值 |
| 规则落地但执行不一致 | 治理名存实亡 | 通过 PR 模板 + CI + docs_guard 三重约束 |

## 9. 需求结论

本期需求采用“方案 C：全量体检 + 强门禁 + 分波次重构”，以行为等价为硬约束推进系统性减法治理，先解决高风险热点，再固化长期反弹防线。
