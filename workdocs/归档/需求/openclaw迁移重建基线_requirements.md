## 2. 目标与非目标

### 2.1 目标

1. 形成以 `P1~P6` 为执行主线、以 `Batch` 为治理视图的统一迁移基线。
2. 在不丢失归一化细节的前提下，输出可直接进入 `/jjk-vkplan` 的可执行需求边界。
3. 固化单活串行执行约束（自动执行场景）。
4. 保留 OpenClaw 对标机制（协议、工具治理、记忆、队列与子任务、门禁证据）并适配 FastAPI 现有架构。

### 2.2 非目标

1. 本阶段不直接改代码，不直接改数据库 schema。
2. 不在本阶段引入新的主文档类别。
3. 不将 `Batch` 看板直接替代 `Wave` 执行顺序。

## 3. 角色与用户故事

### 3.1 角色

1. 平台研发（后端/AI 工作流）
2. 迁移总控（计划编排与门禁）
3. 测试与验收（API/SSE/回滚/证据）
4. 自动执行代理（串行执行卡片）

### 3.2 用户故事

1. 作为迁移总控，我需要唯一状态入口和统一编号，避免“文档多头回填”。
2. 作为后端研发，我需要每个 feature 有明确代码锚点、契约字段和回滚锚点，避免实现漂移。
3. 作为测试同学，我需要每波次可执行验收命令与 DoD，避免口头“完成”。
4. 作为自动执行代理，我需要串行依赖链和硬门禁，防止并行误推进。

## 4. 功能需求（FR）

### FR-00 前置门禁（C00）

1. 在进入 `C01/P1-01` 前必须完成 `C00`（四风险修订 + 取消接口口径统一 + 证据回填）。
2. 未通过 `C00` 时，不允许推进实现卡。

### FR-01 运行时可取消（P1）

1. 支持 run 级取消控制（含状态模型、控制服务、API 入口）。
2. 取消后中断 token 回灌和队列残留，SSE 输出 `stopped` 信号。
3. 具备重启恢复与 orphan 清理策略。

### FR-02 工具治理一期（P2）

1. 从 workflow 硬编码切换到 `Registry/Policy/Broker` 治理路径。
2. 支持 allowlist/sandbox/审批与证据门禁策略分层。

### FR-03 Skill 多用户版本治理（P3）

1. Skill 定义、版本、用户绑定解耦。
2. 用户级覆盖生效且可回滚，不污染其他用户。

### FR-04 记忆检索增强（P4）

1. 从单一偏好注入升级为 recall + flush 的可追溯闭环。
2. 强制 user_id 隔离，支持降级路径。

### FR-05 稳态增强（P5）

1. 增强恢复、隔离、观测与降级，保障异常不阻断主对话。
2. 插件化能力后置接线，不阻塞 P1~P4 主线。

### FR-06 全链路收口（P6）

1. 完成 docs/code/test 三线收口与回滚演练。
2. Gate 与证据链满足“可审计、可复盘、可追溯”。

---

## 5. 非功能需求（NFR）

1. **可追溯性**：每个 feature 必须关联证据入口，能够反查来源原子。
2. **一致性**：执行状态唯一入口固定为 `迁移执行波次_implementation_plan.md` 的 Gate 看板与卡记录区。
3. **兼容性**：SSE 新事件与既有事件兼容演进，不破坏当前消费方。
4. **可回滚性**：每个波次必须有开关/降级/撤回路径。
5. **可维护性**：编号稳定（卡号/特性号稳定），禁止同义重命名。

## 6. 依赖关系与执行顺序

### 6.1 卡片依赖

1. `C00 -> C01`
2. `C01 -> C02 -> C03 -> C04`
3. `C05` 依赖 `C02` 与 `C04`
4. `C06` 依赖 `C01~C05`

### 6.2 波次依赖

1. `P1` 为高优先前置能力（运行时可取消）。
2. `P2/P3/P4` 在 `P1` 后按依赖推进。
3. `P5` 在主能力稳定后推进稳态增强。
4. `P6` 作为收口与发布前演练阶段。

---

## 7. 验收标准（DoD）

1. 每个特性有：机制、代码锚点、关键契约字段、验收命令、回滚锚点、证据入口。
2. 计划文档末尾必须提供 `planning_contract`，并声明 `execution_mode: serial`。
3. hydrate 覆盖率必须输出且可机读（含冲突裁决与 unmapped 明细）。
4. 若存在 unmapped 细节，计划状态必须 `BLOCKED` 且停止进入 `/jjk-vkplan`。
