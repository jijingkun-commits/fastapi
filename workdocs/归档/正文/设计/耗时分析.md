# AI 回答响应时间深度分析报告（v2）

> 分析日期：2026-03-04  
> 分析范围：FastAPI + LangGraph 多智能体系统（代码现状 + 运行日志）  
> 目标：基于可复核证据重排瓶颈优先级，并给出可落地、可回滚的优化路径

---

## 1. 执行结论（先说结论）

- 旧版文档中的绝对时延数字（`9.6s / 13.6s / 23.8s`）**不能作为当前基线**，因为现有日志缺失端到端真实耗时字段，且部分“延迟”字段来自请求入参而非系统测量。
- 当前最有把握的瓶颈不是“token 裁剪”，而是：
  1. **Skills 检索固定成本高且命中率低**（每轮触发、绝大多数未命中）；
  2. **Data/Vanna 热路径重复创建 engine**（连接创建开销）；
  3. **Document Memory 召回同步阻塞**；
  4. **多跳 LLM 路由带来累积时延**（supervisor + expert）。
- 优化顺序必须先做可观测闭环，再做重构；否则会出现“看起来优化了，实际上不可证伪”的情况。

## 3. 已证实事实（含统计快照）

### 3.1 Skills 检索命中率偏低（已证实）

基于 `logs/assistant.log` 统计：

| 指标 | 数值 | 说明 |
|---|---:|---|
| `selected_count=0` | 32/35（91.43%） | 大多数请求执行了检索但未注入技能 |
| `selected_count=1` | 3/35（8.57%） | 命中率低 |

结论：当前“每轮检索”策略带来稳定固定成本，但收益覆盖不足。

代码证据：
- 预处理阶段每轮触发 `search_skills_debug`：`app/ai/workflow/multi_agent_graph.py:4278`
- 检索内部会生成 embedding：`app/services/skill_service.py:2095`

### 3.2 Token 裁剪并未发生（已证实）

基于 `Context Budget` 日志统计（37 条）：

| 指标 | 数值 |
|---|---:|
| 总样本数 | 37 |
| `prepared_tokens != pruned_tokens` | 0 |
| 裁剪命中率 | 0.00% |
| `prepared_tokens` 平均值 | 1615.1 |
| `prepared_tokens` 最小/最大 | 40 / 4758 |
| 预算 `budget` | 68000 |

结论：在当前样本窗口里，上下文远未逼近预算；“token 裁剪重复计算”有优化价值，但**不是当前首瓶颈**。

代码证据：
- 预算与裁剪计算：`app/ai/workflow/multi_agent_graph.py:3249`
- 预算日志输出：`app/ai/workflow/multi_agent_graph.py:3720`

### 3.3 路由结构以 Supervisor 为主（已证实）

`Context Budget` 节点分布（37 条）：

| 节点 | 次数 | 占比 |
|---|---:|---:|
| `supervisor` | 26 | 70.27% |
| `todo_expert` | 9 | 24.32% |
| `data_expert` | 2 | 5.41% |

结论：supervisor 是所有路径必经点；expert 路径是增量时延来源。

### 3.4 高频路径重复创建 engine（已证实）

代码中仍存在热路径内 `create_engine(...)`：

- `app/ai/semantic/vanna_client.py:106`
- `app/ai/semantic/vanna_client.py:208`
- `app/ai/semantic/vanna_client.py:315`
- `app/ai/semantic/vanna_client.py:367`

结论：连接创建行为可能放大请求尾延迟与波动，优先级高于“盲目扩容连接池”。

### 3.5 Document Memory 召回为同步阻塞（已证实）

证据：
- `chat_service` 中通过同步 `get_db_context()` + `recall_document_memory(...)` 执行：`app/services/chat_service.py:742`

结论：该阶段无法与后续准备链路并行，属于确定性的串行耗时。

- 旧版将护栏标注为“LLM 调用”，与现状不符。
- 当前护栏实现为正则匹配与脱敏逻辑，不触发模型调用：
  - `app/ai/guardrails.py:56`

- 旧版“共享连接池”描述不准确。
- checkpointer 使用独立 `AsyncConnectionPool`：
  - `app/db/postgres_checkpoint.py:52`

### 4.3 纠偏项三：`data_db` 独立 engine 已存在

- 旧版把“新增 data_db 独立连接池”作为优化项不成立。
- 当前已存在 `analytics_engine`：
  - `app/db/session.py:36`

### 4.4 纠偏项四：用法证据需与当前实现一致

- 旧版举例 `supervisor_llm.ainvoke`，当前主链已是 `agent.astream`：
  - `app/ai/workflow/multi_agent_graph.py:3698`

## 5. 当前瓶颈优先级（v2）

### P0（立即）— 先补“可证明”

1. **可观测缺口（最高优先）**  
   - 现状：无统一 `ttft_ms / ttlb_ms / node_duration_ms`。  
   - 风险：任何“优化百分比”无法严格验收。  
   - 目标：先把可观测闭环补齐。

2. **Skills 检索固定成本高 + 命中率低**  
   - 现状：91.43% 未命中仍走完整检索。  
   - 目标：减少无效检索成本（短路 + 缓存）。

3. **Data/Vanna 热路径连接创建开销**  
   - 现状：多处 `create_engine(...)`。  
   - 目标：统一复用 `engine / analytics_engine`。

### P1（两周内）— 串行链路瘦身

4. **Document Memory 同步阻塞**  
   - 目标：召回结果缓存 + 异步化（或并行前置）。

5. **多跳路由累积时延**  
   - 目标：先按场景分层看 1 跳 / 2 跳，再决定是否引入轻量意图前判。

### P2（后续）— 结构优化

6. **Token 计数缓存与上下文治理**  
   - 当前是“优化项”，不是“先手项”；待 P0/P1 完成后再推进。

## 6. 实施路线图（可执行版）

### 6.1 第一阶段（Week 1）：补指标 + 快速减负

#### 任务

1. 增加 run 级指标（必须）
   - `ttft_ms`（首 token 延迟）
   - `ttlb_ms`（完整输出延迟）
   - `node_duration_ms`（preprocess/supervisor/expert/postprocess）
   - `route_path`（supervisor_only / supervisor_todo / supervisor_data）
2. Skills 检索先做两件事
   - 查询哈希缓存（`user_id + normalized_query + top_k + threshold + scope`）
   - 低价值请求短路（明确非技能场景跳过向量检索）
3. 不改语义前提下消除热路径 `create_engine(...)`
   - 改为复用现有全局 engine。

#### 验收

- 指标覆盖率 ≥ 95%（完成请求中可产出 run 级指标）
- 无效技能检索率（未命中仍检索）较当前下降 ≥ 50%
- 不引入功能回归（回答语义与路由正确率不下降）

### 6.2 第二阶段（Week 2-3）：阻塞链路并行化

#### 任务

1. Document Memory 召回缓存（TTL）
2. 召回链路异步化（或请求前置并行）
3. Skills 检索与护栏并行执行（仅在无依赖时）

#### 验收

- `preprocess` 阶段 P90 时延下降 ≥ 25%
- 命中缓存请求的预处理时延明显低于未命中组

### 6.3 第三阶段（Week 4+）：路由与模型层优化

#### 任务

1. 按路径分层优化（1 跳 vs 2 跳）
2. 评估轻量意图前判是否值得引入
3. 再决定 token 增量缓存与预算收敛策略

#### 验收

- `supervisor_only` 与 `supervisor+expert` 两类路径均达到目标阈值
- 质量指标（错误率、用户负反馈）不劣化

## 7. 回滚与治理约束

- 所有优化必须支持一键回退（关闭开关或触发降级策略）。
- 新增开关默认开启（`true`），回退路径统一“关闭开关或降级策略”。
- 若出现以下任一情况，立即回滚：
  - 错误率上升 > 10%
  - 用户负反馈上升 > 5%
  - P99 时延恶化 > 20%

---

## 8. 监控面板建议（最小集）

1. 端到端：`ttft_ms`、`ttlb_ms`（P50/P90/P99）
2. 路由：1 跳/2 跳占比与时延分层
3. 检索：skills/document recall 命中率与时延
4. 连接：连接池活跃连接、等待队列长度
5. 质量：错误率、拒答率、回退触发率

## 9. 解决方案（可直接执行）

### 9.1 方案 A：补齐 run 级时延埋点（先做）

#### 改造目标

- 让每次请求都可得到 `ttft_ms / ttlb_ms / route_path / node_duration_ms`，形成可验收基线。

#### 改造位置

- `app/services/chat_service.py`
- `app/ai/workflow/multi_agent_graph.py`

#### 实施步骤

1. 在 `sse_stream` 会话开始时记录 `request_start_ts`（`time.perf_counter()`）。
2. 在首次发出 `token` 事件时计算并记录 `ttft_ms`（只记录一次）。
3. 在 `done` 事件前计算 `ttlb_ms`。
4. 在 `multi_agent_graph` 节点包装层记录各节点耗时（preprocess/supervisor/todo_expert/data_expert/postprocess）。
5. 统一输出结构化日志（JSON），字段至少包含：
   - `run_id`
   - `thread_id`
   - `user_id`
   - `route_path`
   - `ttft_ms`
   - `ttlb_ms`
   - `node_duration_ms_map`

#### 验收标准

- 完成请求中指标覆盖率 ≥ 95%。
- 统计可分层到 `supervisor_only / supervisor_todo / supervisor_data`。

#### 回滚方式

- 关闭埋点开关：`observability.latency_probe_enabled=false`（默认 `true`）。

---

### 9.2 方案 B：Skills 检索降本（短路 + 缓存）

#### 改造目标

- 在不改变功能语义的前提下，减少“未命中但完整检索”的固定成本。

#### 改造位置

- `app/ai/workflow/multi_agent_graph.py`
- `app/services/skill_service.py`

#### 实施步骤

1. 增加检索短路策略（配置驱动，不写死业务分支）：
   - 通过配置判断是否跳过检索，如超短输入、纯噪声输入、明显非技能场景。
   - 配置项示例：`skill.short_circuit_enabled=true`、`skill.retrieval_min_query_len=6`。
2. 增加查询级缓存（TTL）：
   - key：`user_id + normalized_query + top_k + threshold + scope + retrieval_mode`。
   - value：`search_skills_debug` 结果（候选、命中、context_preview）。
3. 缓存命中时直接复用结果，避免重复 embedding + 向量检索。
4. 日志补充 `cache_hit` 字段，便于算命中率。

#### 验收标准

- `selected_count=0` 且执行完整检索的占比下降 ≥ 50%。
- `preprocess` 阶段 P90 下降 ≥ 20%（在同路径样本下）。

#### 回滚方式

- `skill.short_circuit_enabled=false`
- `skill.retrieval_cache_enabled=false`

---

### 9.3 方案 C：移除热路径 `create_engine(...)`

#### 改造目标

- 消除请求内重复创建引擎导致的连接开销与时延抖动。

#### 改造位置

- `app/ai/semantic/vanna_client.py`
- `app/ai/workflow/data_graph.py`
- 复用 `app/db/session.py` 中现有 `engine / analytics_engine`

#### 实施步骤

1. 将 `vanna_client.py` 中每次调用时的 `create_engine(self.metadata_db_url)` 改为复用模块级 engine。
2. 将 `data_graph.py` 中 `_search_metrics_exact_name / _search_metrics_by_vector / _search_training_sql` 的 `create_engine(DATABASE_URL)` 改为复用 `engine`。
3. 对分析库查询保持复用 `analytics_engine`（已存在，不再重复创建）。
4. 保持 SQL 与事务语义不变，仅替换连接来源。

#### 验收标准

- 代码中热路径不再出现新的 `create_engine(...)`。
- 同等压测下，数据路径 P95 波动收敛（抖动下降）。

#### 回滚方式

- 回退至改造前连接实现（单点可逆）。

---

### 9.4 方案 D：Document Memory 非阻塞化（缓存优先）

#### 改造目标

- 降低 `recall_document_memory` 对主链路的串行阻塞影响。

#### 改造位置

- `app/services/chat_service.py`
- `app/services/document_memory_service.py`

#### 实施步骤

1. 先做召回结果缓存（TTL）：
   - key：`user_id + normalized_query + max_results + weights + min_score`。
2. 缓存命中直接注入记忆上下文，跳过同步召回。
3. 缓存未命中时维持当前同步逻辑（先稳态），并记录 `recall_duration_ms`。
4. 第二阶段再做异步改造（独立线程执行并在函数内部自建 DB context，避免会话线程安全问题）。

#### 验收标准

- 召回命中请求的 `preprocess` 时延显著低于未命中组。
- 记忆召回失败率不升高。

#### 回滚方式

- `memory.document.recall_cache_enabled=false` 即可退回现状。

---

### 9.5 方案 E：路由跳数治理（最后做）

#### 改造目标

- 控制 `supervisor + expert` 多跳路径比例，降低累积 LLM 时延。

#### 改造位置

- `app/ai/workflow/multi_agent_graph.py`

#### 实施步骤

1. 先基于新埋点按 `route_path` 分层建基线（必须先有数据）。
2. 引入轻量前判仅用于高置信场景，低置信仍回到 supervisor（策略配置化）。
3. 前判命中时直达 expert，未命中维持现有路径。

#### 验收标准

- 高置信直达路径的正确率不低于现网 supervisor 路由。
- 对应路径 P90 时延下降且质量指标无回退。

#### 回滚方式

- `routing.fastpath_enabled=false`。
