# 存量项目屎山治理 Checklist（详细版）

- 文档版本：v1.0
- 创建日期：2026-03-03
- 适用仓库：`/Users/jijingkun/bojxAI/fastapi`
- 目标：识别并系统化简化存量代码，降低复杂度、重复逻辑与维护成本
- 使用说明：按阶段逐项勾选；未达成项不得进入下一阶段

---

## 0. 启动前对齐（必须完成）

- [ ] 明确本轮治理范围（后端/前端/全链路）。
- [ ] 明确不在本轮处理的范围（防止范围蔓延）。
- [ ] 确认“临时补丁禁止”原则（不允许硬编码分支掩盖根因）。
- [ ] 明确验收目标（复杂度下降、重复代码减少、回归无退化）。
- [ ] 指定负责人、评审人、回滚决策人。

---

## 1. 存量体检与证据归档

- [ ] 输出“高风险大文件”清单（按 LOC、函数复杂度排序）。
- [ ] 输出“重复逻辑清单”（工具函数、事件分发、配置读取、错误处理）。
- [ ] 输出“跨层职责错位清单”（Router/Service/Workflow/Repository）。
- [ ] 输出“状态机分叉点清单”（normal/resume、fallback、多路路由）。
- [ ] 每条问题都有证据（文件路径+行号+现象描述）。

---

## 2. 架构边界治理（先边界后代码）

- [ ] 明确目标分层：`Router -> Application Service -> Domain Service -> Repository`。
- [ ] 明确“谁负责事件分发、谁负责持久化、谁负责降级”的单一真相源。
- [ ] 明确事务边界（数据库事务与外部副作用分离）。
- [ ] 明确异常映射规范（业务异常 -> API 错误码）。
- [ ] 架构文档先更新，再执行代码改造。

---

## 3. 后端治理 Checklist

### 3.1 AI 编排层（Workflow / Chat Service）

- [ ] normal/resume 流式分发逻辑统一，消除双实现分叉。
- [ ] 运行时恢复策略统一入口（feature flag、插件错误识别、降级触发条件）。
- [ ] 多智能体路由规则集中管理（避免隐式散落分支）。
- [ ] 对话落库职责单点化（避免双写、顺序漂移、message_id 不一致）。
- [ ] 大型节点函数分解为可测的纯函数流水线（parse/merge/decide/apply）。

### 3.2 Service 层（去 God Object）

- [ ] `SkillService` 拆分为 parser/importer/versioning/binding/retrieval 子模块。
- [ ] `PermissionService` 拆分为 context loader/evaluator/policy manager。
- [ ] 统一会话 ownership（核心方法显式接收 `db: Session`）。
- [ ] 抽离公共 validator/normalizer，禁止 endpoint 调用私有 service 方法。
- [ ] 抽离通用 CRUD 错误翻译与 `get_or_404` 工具。

### 3.3 API 层（endpoint 瘦身）

- [ ] `data_admin_api` 按子域拆分路由（query_log/train/metric/etl/schema/enrichment_rule）。
- [ ] 路由层仅做参数解析与响应拼装，不承载业务编排。
- [ ] DTO 复用（Base schema + mapper），减少重复字段定义。
- [ ] 统一响应结构（成功/失败/校验错误）。
- [ ] 关键接口补充契约测试。

---

## 4. 前端治理 Checklist

### 4.1 Hook 与状态管理

- [ ] `useSSEStream` 拆分为状态机 Hook + 历史 Hook + 偏好 Hook。
- [ ] submit/resume 共享同一事件处理器，消除复制粘贴。
- [ ] 流生命周期收口为单一出口（done/stop/error 一致）。
- [ ] 中断恢复流程状态可追踪（idle/streaming/interrupted/error）。
- [ ] 请求竞态具备防护（旧请求不得覆盖新状态）。

### 4.2 API 与协议处理

- [ ] 抽离统一 `http-client`（认证注入、401 策略、错误归一化）。
- [ ] 抽离统一 `sse-parser`（chat 与 admin-overview 共用）。
- [ ] `backend.ts` 去大一统（按领域拆分 API 服务文件）。
- [ ] 错误信息标准化（不再出现大量 `xxx failed` 无上下文）。
- [ ] UI 层仅消费结构化事件，不做协议细节拼接。

### 4.3 管理台组件拆分

- [ ] 超大组件按业务域拆分（如 DataAdminPanel、AdminOverviewCockpit）。
- [ ] 抽离通用异步状态组件（loading/error/empty/retry）。
- [ ] 抽离重复策略编辑器组件（白名单/黑名单/schema）。
- [ ] 组件 props 与副作用边界清晰（避免多层状态互相写）。
- [ ] 管理台关键流程有最小可运行回归用例。

---

## 5. 质量门禁 Checklist

### 5.1 测试门禁

- [ ] 新增或重构逻辑均有对应单元测试。
- [ ] 关键链路具备集成测试（stream/resume/interrupt/fallback）。
- [ ] API 契约测试覆盖关键 admin 接口。
- [ ] 前端至少通过 lint + build + 关键交互用例。
- [ ] 所有测试在同一基线环境可重复执行。

### 5.2 可观测与回归证据

- [ ] 新旧实现对比日志齐全（关键事件序列可追踪）。
- [ ] 复杂度下降有量化证据（函数长度、圈复杂度、重复片段数）。
- [ ] 性能退化检查完成（延迟、错误率、空结果率）。
- [ ] 异常路径验证完成（取消、超时、插件失败、空结果）。
- [ ] 回归报告已归档到 `workdocs/归档/正文/设计/`。

## 6. Team 模式执行 Checklist（多工位并行）

- [ ] 任务切分满足“互不冲突、可并行”。
- [ ] 每个 worker 有明确文件所有权边界。
- [ ] 每个 worker 提交前完成本地验证并附证据。
- [ ] Leader 做交叉审查，防止重复改动与设计漂移。
- [ ] 合并顺序遵循依赖关系（基础层 -> 服务层 -> 组件层）。

---

## 7. 发布与回滚 Checklist

- [ ] 每个阶段均有可执行回滚方案（开关/配置/版本）。
- [ ] 发布批次有变更摘要与风险说明。
- [ ] 灰度期间设置观察窗口与告警阈值。
- [ ] 触发阈值时自动停止推进并执行回滚。
- [ ] 复盘结论记录“根因、修复、预防”三段。

---

## 8. 终验标准（Go / No-Go）

- [ ] 重复逻辑显著减少（关键重复点已合并）。
- [ ] 关键大文件复杂度下降并可解释。
- [ ] 跨层职责边界稳定（无新一轮边界塌陷）。
- [ ] 关键链路测试通过且无行为回归。
- [ ] 文档、代码、测试三者一致。

> 放行规则：以上任一项不满足，本轮结论必须为 **No-Go**。
