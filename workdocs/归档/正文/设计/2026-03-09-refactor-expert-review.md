### 架构可行性评分

| 方案 | 评分 | 关键问题 |

### 关键风险

1. **State 瘦身后的会话一致性风险**
   - `skill_*` 和 `decomposed_goals` 外移后，Checkpointer 无法自动恢复

   - 缓解：不要删除所有 try-except，只统一业务错误处理

   - `multi_agent_graph.py`：从 < 500 行调整到 **800-1000 行**

2. **调整执行顺序**：P4 → P1 → P3 → P0 → P5 → P2

3. **补充灰度发布策略**：每个方案完成后进行灰度验证

## 六、最终推荐方案

### 方案 A：分阶段混合架构（推荐 ⭐⭐⭐⭐⭐）

#### 阶段 1：低风险重构（2-3 周）

**目标**：快速见效，建立信心

- ✅ P4 配置管理统一（2-3 天）
- ✅ P5 Prompt 瘦身（3-4 天）
- ✅ P2 部分：增加统一错误日志（不删除 try-except）

**预期收益**：
- 配置读取路径从 4 层减少到 2 层
- Prompt 从 265 行减少到 < 100 行
- 错误日志统一格式

#### 阶段 2：中风险重构（4-6 周）

**目标**：消除硬编码，拆分职责

- ✅ P1 消除硬编码词表（保留词表作为快速路径）
- ✅ P3 部分：外移纯函数到 utils/
- ✅ P2 部分：逐步替换 try-except 为统一错误边界

**预期收益**：
- 删除 7 个硬编码词表常量
- `multi_agent_graph.py` 从 5642 行减少到 3000 行
- try-except 从 46 个减少到 20 个

#### 阶段 3：高风险重构（8-12 周）

**目标**：State 瘦身，职责外移

- ⚠️ P0 State 瘦身（目标：15-20 字段，保留关键字段）
- ⚠️ P3 职责外移（目标：800-1000 行）

**保留的关键字段**：
```python
# 不可删除的核心字段
pending_handoff: Dict
handoff_queue: List[Dict]
completed_handoffs: List[Dict]
loaded_skill_registry: Dict[str, Dict]
decomposed_goals: List[Dict]
```

**预期收益**：
- State 从 39 字段减少到 15-20 字段
- `multi_agent_graph.py` 从 3000 行减少到 800-1000 行

#### 混合架构设计

**核心原则**：State 缓存 + 服务持久化

```python
class TaskOrchestrator:
    @staticmethod
    def get_next_handoff(state: MultiAgentState) -> Optional[Dict]:
        # 优先从 State 读取（内存缓存）
        queue = state.get("handoff_queue") or []
        if queue:
            return queue[0]

        # 缓存未命中，从 DB 恢复
        thread_id = state.get("thread_id")
        return TaskOrchestrator.load_from_db(thread_id)
```

**优势**：
- 保持内存语义，性能无损
- DB 作为持久化层，支持会话恢复
- 降低重构风险

- 执行顺序：从 P0→P1→P2→P3→P4→P5 调整到 **P4→P1→P3→P0→P5→P2**

**关键原则**：
