### 1.2 现状问题

2. 运行时仍可回退 legacy 表路径，不满足“Skill 跟用户走”的强隔离目标。
3. 新用户没有统一 Skill 初始化模板，后续维护成本高。
4. 前端缺少用户自维护入口和管理员模板治理入口。

## 2. 用户故事

1. 作为平台管理员，我希望维护全员统一的 Skill 初始模板，以便新用户开通即有稳定能力基线。
2. 作为普通用户，我希望只维护自己的 Skill 生效配置（启停、优先级、触发词覆盖），且不会影响他人。
3. 作为系统运维，我希望检索链路按 `user_id` 严格隔离，并具备灰度与回滚手段，避免线上中断。
4. 作为架构负责人，我希望保留版本发布/回滚与后续“自我升级建议流”的演进空间。

---

## 3. 目标、范围与边界

### 3.1 目标

1. 新用户创建后自动绑定统一 Skill 模板。
2. 检索主链路切换到严格用户源模式（发布版本 + 用户绑定）。
3. 提供用户自维护与管理员治理闭环。
4. 提供可观测灰度与可回滚策略。

### 3.2 范围（本期）

1. 后端：Skill 运行时源切换、模板读取与用户初始化、用户与管理员 API。
2. 前端：管理员模板/覆盖管理页、用户“我的 Skills”管理页。
3. 文档与测试：requirements + implementation_plan + 测试用例矩阵。

### 3.3 边界（本期不做）

1. 普通用户直接修改全局 Skill 正文内容。
2. 全自动“自我升级并自动发布”。
3. 引入新存储引擎或跨库架构迁移。

## 5. 验收标准

### 5.1 功能性（Happy Path）

1. 管理员可配置统一模板（含默认版本、启停、priority/trigger 覆盖）。
2. 创建用户后自动生成该用户的 `t_user_skill_bindings` 初始数据。
3. 同一查询在不同用户下可命中不同 Skill 组合。
4. 用户可在“我的 Skills”中调整本人配置并立即生效。
5. 管理员可查看任意用户覆盖并执行回滚到模板默认。
6. strict_user 开启后，检索主链不再依赖 legacy 回退。

### 5.2 异常与边界

1. 模板配置非法时拒绝保存并返回可读错误。
2. 新用户初始化失败时不阻塞用户创建，记录告警与补偿入口。
3. 用户越权修改他人配置返回 403。
4. strict_user 下若缺失绑定，按默认发布版本兜底，不可 silent fail。
5. embedding 服务短时失败时，hybrid 可降级关键词检索。

### 5.3 性能与稳定性

1. 检索主链 P95 不高于现网同量级 20%。
2. 用户初始化绑定在单用户创建路径内额外耗时 < 200ms（不含外部 embedding）。
3. 管理端列表查询支持分页，P95 < 300ms。

## 6. 非功能需求

### 6.1 安全

1. 用户 API 强制绑定 `current_user.id`。
2. 管理 API 仅 `admin` 可访问。
3. 所有模板与绑定变更写审计日志（操作者、变更前后、trace_id）。

### 6.2 一致性

1. `user_id + skill_id` 唯一约束确保隔离。
2. 模板更新与用户覆盖互不覆盖，采用“模板默认 + 用户显式覆盖”合并口径。
3. 版本发布与绑定变更具备可回滚语义。

### 6.3 可观测性

1. 检索日志必须记录 `user_id`、`mode`、候选与选中 Skill。
2. strict_user 模式需有独立标记字段，便于筛查。
3. 初始化失败告警可关联 user_id 与模板版本。

## 8. 风险与约束

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 版本表回填不完整 | strict_user 命中异常 | 上线前执行回填校验脚本 + 对账 |
| 模板配置漂移 | 新老用户能力不一致 | 模板版本化 + 审计 + 批量对齐工具 |
| 前后端口径不一致 | 用户认知混乱 | 统一 API 契约与字段定义文档 |
| 降级策略缺失 | 故障放大 | 明确开关与回滚 SOP |

---

## 9. 需求结论

本期以方案 B 落地，先完成“统一模板 + 严格用户源 + 用户/管理员治理闭环”，确保 Skill 生命周期从“全局共享”过渡到“以用户为中心”的可控运行模型。
