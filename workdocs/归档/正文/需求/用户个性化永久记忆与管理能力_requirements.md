# 用户个性化永久记忆与管理能力需求基线（LLM 异步判定版）

> 文档日期：2026-03-04
> 文档定位：定义“用户个性化永久记忆”从对话沉淀、检索召回到后台治理的统一需求基线
> 上游设计输入：`workdocs/归档/正文/设计/2026-03-03-user-personalized-memory-llm-async-design.md`

---

## 1. 背景与问题定义

当前系统已经具备文档化记忆两表（`t_user_memory_document` + `t_user_memory_chunk`）与混合检索能力，但存在三个结构性问题：

1. 记忆触发仍混有关键词路径，语义覆盖不足，且维护成本高。
2. 记忆沉淀逻辑与主对话链路耦合，目标上要求“零阻塞”但机制不闭环。
3. 记忆管理能力（查询、治理、审计、重建）尚未形成统一产品化能力，运维排障效率受限。

本轮需求目标是：在不牺牲主对话时延前提下，实现“LLM 判定 + 异步沉淀 + 可治理可审计”的用户个性化永久记忆能力。

---

## 2. 目标、范围与边界

### 2.1 目标（Goal）

1. 将记忆判定从关键词规则升级为 LLM 语义判定，输出 `permanent/daily/none`。
2. 记忆沉淀改为异步执行，主对话只入队不等待判定结果。
3. 永久记忆按槽位治理，支持覆盖、归档、反向撤销与审计追踪。
4. 提供后台查询与管理能力，支持按 `user_id` 定位、调试和运维处置。

### 2.2 范围（In Scope）

1. 对话侧：消息入队、异步 worker 判定、文档化写入、embedding 补偿触发。
2. 数据侧：记忆任务队列表与文档层字段扩展（含并发与乱序保护字段）。
3. 检索侧：FTS + 向量混合检索与引用注入口径统一。
4. 管理侧：列表查询、详情查看、归档删除、检索调试、重建与重试。
5. 治理侧：敏感信息过滤、背压熔断、可观测指标与发布门禁。

### 2.3 非范围（Out of Scope）

1. 不引入外部向量数据库或新消息中间件作为首期强依赖。
2. 不开放普通终端用户的记忆自助编辑能力（首期仅管理员治理）。
3. 不承诺“同轮可见”，仅承诺异步链路 SLO。

---

## 3. 用户故事（User Stories）

### US-01（最终用户）

作为普通用户，我希望系统能记住稳定偏好与关键事实，并在后续对话中使用这些记忆提升回答个性化。

### US-02（平台管理员）

作为管理员，我希望能按用户查询记忆内容与状态，并能执行归档、删除、重建等治理动作。

### US-03（运维工程师）

作为运维，我希望看到任务队列、失败重试与死信状态，能够定位“为什么这条记忆没生效”。

### US-04（安全合规）

作为安全负责人，我希望敏感信息默认不入库，且所有管理动作可审计可追责。

---

## 4. 功能需求（Functional Requirements）

### FR-01 异步任务入队

1. 用户消息写入后，系统必须创建唯一记忆任务（按 `user_id + source_message_id` 幂等）。
2. 主对话链路不得等待记忆判定结果。
3. 任务记录必须包含可审计上下文（消息、线程、事件时间、重试状态）。

### FR-02 LLM 判定与合同校验

1. Worker 使用模型路由 `lightweight` 执行判定。
2. 判定合同必须至少返回：`level`、`category`、`slot_key`、`canonical_text`、`confidence`。
3. 非核心字段缺失可容错，核心字段非法必须丢弃并记录失败原因。

### FR-03 分层与分类策略

1. 仅允许 `permanent | daily | none` 三层输出。
2. 仅允许 5 类分类：`ai_persona`、`user_preference`、`important_knowledge`、`profile_fact`、`interaction_policy`。
3. `important_knowledge` 必须限定为跨会话长期稳定知识。

### FR-04 槽位治理与冲突覆盖

1. `slot_key` 必须进入服务端归一化映射，禁止自由键直接入库。
2. 同槽位冲突采用“新值覆盖旧值，旧值归档审计”。
3. 多值槽位支持并存，支持集合替换语义。

### FR-05 反向指令与敏感信息处理

1. 仅在“反向意图 + 可定位槽位”成立时执行 archive。
2. 全量清除记忆属于管理动作，不由普通聊天自动执行。
3. 命中高敏信息（证件号、银行卡、密码、验证码等）必须拒绝沉淀。

### FR-06 文档写入与检索注入

1. 记忆正文必须是条目化 `canonical_text`，禁止原文直接追加。
2. 分块后统一置 `embedding_status=pending`，由补偿链路异步向量化。
3. 检索层必须支持 FTS + 向量混合排序与引用输出。

### FR-07 后台查询与管理能力

1. 支持按 `user_id`、`doc_kind`、`status`、关键词查询记忆列表。
2. 支持查看文档详情、分块状态、embedding 失败原因。
3. 支持归档、删除、重试失败向量、重建向量、检索调试。

### FR-08 可观测与门禁

1. 必须采集 `enqueue_ts/claim_ts/decision_done_ts/persist_done_ts/final_status/attempt_count`。
2. 支持队列背压分级（L1/L2/L3）与熔断策略。
3. 仅在门禁指标达标后允许灰度放量。

---

## 5. 验收标准（Acceptance Criteria）

### 5.1 功能性（Happy Path）

1. 用户陈述稳定偏好后，任务在 SLO 内完成，并在下一轮高概率可召回。
2. 用户修正偏好后，新值可覆盖旧值，旧值可在审计记录中查询。
3. 管理员可在后台查到记忆列表、详情、分块状态并执行治理动作。

### 5.2 异常与边界

1. LLM 输出非法 JSON 时，任务不写脏数据，状态可追踪。
2. embedding 服务不可用时，检索可降级为 FTS，主功能不崩溃。
3. 队列积压超阈值时触发背压/熔断，主对话仍可用。
4. 反向意图无法定位槽位时，不得误删，需记录拒绝原因。

### 5.3 性能与稳定性

1. 用户对话接口 P95 与改造前持平（允许可解释微波动）。
2. 记忆异步生效时延 `P95 < 5s`（口径：`enqueue_ts -> persist_done_ts`）。
3. 死信率低于 `0.5%`，超过阈值触发告警。

---

## 6. 非功能需求（NFR）

### NFR-01 性能

1. 异步 worker 支持水平扩容。
2. 混合检索单次查询耗时满足现网对话预算。

### NFR-02 安全

1. 管理 API 必须管理员权限校验。
2. 敏感信息不入库，关键治理动作可审计。

### NFR-03 一致性

1. 幂等：同消息只生成一次成功结果。
2. 乱序保护：旧事件不得覆盖新事件。
3. 并发保护：同槽位并发更新需通过版本校验。

### NFR-04 可运维

1. 支持死信重放与失败重试。
2. 关键指标可观测并可告警。

## 8. 场景约束（架构迁移类）

1. 运行场景约束：异步判定为后台能力，必须与主对话线程解耦。
2. 状态契约约束：`level/category/slot_key` 为核心契约，不允许多口径漂移。
3. 回滚约束：通过开关可快速关闭异步判定并回退到只检索不新增。
4. 发布约束：必须先灰度再全量，且有观测证据支持。

---

## 9. 依赖与风险

1. 依赖：模型路由 `lightweight`、embedding 补偿服务、管理端权限体系。
2. 风险：判定质量抖动、槽位归一化遗漏、队列峰值积压。
3. 对策：合同容错、分级背压、压测门禁、审计闭环。

---

## 10. 需求结论

本需求采用“LLM 异步判定 + 文档化沉淀 + 混合检索 + 后台治理”单一最终方案，不保留并行候选路径。
