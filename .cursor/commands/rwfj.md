# 任务分解工作流 (RWFJ Workflow)

将 `/plan` 或 `/vkplan` 产出的需求与技术方案，进一步拆解为可并行执行且互不干涉的工作包。

> **中文主导**: 无论是思考过程（CoT）还是最终输出，**永远使用中文**。

## 0. 默认执行策略（无需额外提示词）

执行 `/rwfj` 时，默认强制启用以下策略：

1. **先读 seed，缺失则补 seed**：优先读取 `implementation_plan.md` 中的 `task_key/card_seed`；缺失时先在本轮补齐最小 seed。
2. **G0 卡片化**：固定产出 `WS-00_G0_协议冻结`，作为并行层硬前置依赖。
3. **按冲突图自动拆分**：基于文件/状态/依赖冲突自动生成 `WS-01 ... WS-N`。
4. **严格可机读导出**：每个 WS 必须有 `card_export`，缺字段直接失败，不允许静默回退。
5. **冲突不可解则串行回退**：禁止硬拆并行，必须显式回退为串行路线。

## 何时使用

| 场景 | 推荐命令 |
|------|----------|
| 方案已明确，需要多人并行推进 | `/rwfj` ✅ |
| 需要先做并行规划种子 | `/vkplan` |
| 已有拆解，执行某个子任务 | `/imp-ws` |

## 1. 输入与前置

**优先输入**:
1. `docs/内部参考/迭代需求/requirements.md`
2. `docs/内部参考/迭代需求/implementation_plan.md`
3. `docs/内部参考/迭代需求/implementation_plan_<主题>.md`（如主计划已声明专项附录）

**前置条件**:
- 需求边界已清晰
- 架构层职责已初步确认（模块边界、状态契约、路由闭环）

### 1.0 seed 来源判定（新增，必须落文）

在 `parallel_plan.md` 必须写清：

1. `task_key` 来源：`plan` / `rwfj 推导`
2. `card_seed` 来源：`implementation_plan.md` / `rwfj 推导`
3. 若为推导，需写“推导依据 + 风险提醒”

### 1.1 G0 协议冻结（在 `/rwfj` 阶段生成并生效）

> 目的：在并行前冻结跨端契约，避免 WS 并发开发时产生字段语义漂移。

执行要求：

1. 仅冻结契约，不做业务实现。
2. 冻结范围至少覆盖：`done`、`result`、`interrupt`。
3. 每个事件必须给出：
   - required 字段
   - optional 字段
   - 枚举/空值约束
   - 兼容说明（向后兼容策略）
4. 必须在 `parallel_plan.md` 写入独立章节：`## 0. G0 协议冻结`。
5. 固定生成 `WS-00_G0_协议冻结.md`，并声明并行 WS 的 `hard_depends_on: [WS-00]`。
6. 冻结完成后，消费方 WS 只能只读消费，不得自行扩展私有字段假设。
7. `/rwfj` 结束即视为 `WS-00`（M0）完成，不再要求额外执行 `/imp-ws WS-00`。
8. 多 worktree 生效条件：含 `WS-00` 产物的提交已进入基线分支，后续 worktree 必须基于该基线创建（或先 rebase 到该基线）。

### 1.2 前置可并行判定清单（必须先过）

逐项判断（是/否）：

1. 子任务是否可在不等待其他子任务结果的情况下独立开始并独立交付？
2. 子任务是否可以做到文件白名单互斥（无共享文件并发写入）？
3. 子任务是否不存在共享状态字段语义冲突（单写入权清晰）？
4. 子任务是否可各自完成局部验证，不依赖全量集成结果？

判定规则：

- **全是**：进入自动拆分流程，生成 `WS-01 ... WS-N`。
- **有任一否**：不强行并行；在 `parallel_plan.md` 显式写“并行不通过，改串行路线”，并切换单任务执行（`/imp`）或先解耦后重试。

### 1.3 主从计划继承

若主计划声明了专项附录：

1. `parallel_plan.md` 必须显式写明“哪一个 WS 继承该附录”。
2. 对应 WS 文档必须写“主计划 + 专项附录”关联关系。
3. 若主计划与附录冲突，WS 文档必须写“以主计划门禁为准”。

## 2. 产出物（固定目录）

在 `docs/内部参考/任务拆解/<YYYY-MM-DD_主题>/` 下生成：

1. `parallel_plan.md`：并行总计划（必须包含以下章节）
   - `## 0. G0 协议冻结`
   - seed 来源说明（`task_key/card_seed`）
   - 并行判定四问结果
   - 自动拆分依据（冲突关系与分组结果）
   - 依赖图与里程碑
   - 串行回退说明（若触发）
   - `## 9. 看板导出索引`
2. `workstreams/WS-*.md`：工作包明细（动态数量，每包一文件）
   - 每个 WS 必须包含：可改文件白名单、禁止触碰区、状态字段单写入权、局部验收命令
   - Gate WS（至少 `WS-G1`）必须包含：TC-ID 映射表（门禁项 -> 自动化用例 -> 责任 WS）
   - 涉及前端交互或跨端契约消费的 WS，必须包含浏览器测试触发评估
   - 文末必须有 `card_export`（字段完整）
3. `merge_checklist.md`（可选）：仅共享文件/共享字段冲突场景启用
4. `contracts/`（新增，推荐）：存放 G0 机读协议文件（如 `sse_events_v1.json`）

### 2.1 看板导出规范（供 `/vk` 消费）

`parallel_plan.md` 的 `## 9. 看板导出索引` 必须包含：

1. `task_key`（全局唯一卡片前缀）
2. 拆解目录 ID（如：`2026-02-12_文档治理`）
3. WS 总数、Gate 总数
4. 默认列流转：`Backlog -> Doing -> Review -> Gate -> Done`
5. 卡片 ID 规则：`<task_key>::<WS-ID>`
6. 卡片标题规则：`<WS-ID> <标题> [<task_key>]`
7. VK 落卡范围：默认 `WS-01...WS-G2`，`WS-00` 仅前置里程碑（不落卡）

每个 `workstreams/WS-*.md` 文末必须有 `card_export`（YAML）：

- `id`（WS 编号，如 `WS-01`）
- `card_key`（`<task_key>::<id>`）
- `title`
- `type`（`parallel` / `gate` / `foundation`）
- `lane`（并行泳道标识）
- `hard_depends_on`
- `soft_depends_on`
- `file_whitelist`
- `readonly_scope`
- `owner_fields`
- `check_cmd`
- `handoff_artifacts`
- `dod`

兼容字段：
- 如需兼容旧流程，可附带 `depends_on`，其值应等于 `hard_depends_on`。

若出现并行冲突回退，`card_export` 必须显式加：
- `parallel_fallback: true`
- `fallback_reason`
- `serial_order`

## 3. 拆解步骤

1. 读取或补齐 `task_key/card_seed`。
2. 先产出 `WS-00`（G0 协议冻结卡）及机读契约（如 `contracts/sse_events_v1.json`）。
3. 运行最小校验（如 `docs_guard --strict`）并将 G0 标记为 M0 完成。
4. 抽取任务单元：从主计划与 seed 抽取可交付能力点。
5. 构建冲突图：文件重叠、状态单写入权冲突、强依赖阻断。
6. 自动拆分 `WS-01 ... WS-N`：并行层仅保留可独立开始与可独立交付项。
7. 声明 owner 与互斥：白名单、禁区、共享资源 owner 与消费方。
8. 定义依赖：区分 `hard_depends_on` 与 `soft_depends_on`。
9. 定义验收口：每个 WS 绑定独立 DoD 与最小验证命令。
10. 串行回退：存在不可消解冲突时，停止并行拆分并写回退路线。

### 并行拆解禁忌（必须遵守）

- 禁止把“集成回归、最终验收、终稿文档同步”伪装成并行 WS。
- 如必须依赖他人输出才能开始，必须回退为串行路线或先解耦再拆。
- 禁止在冲突未消解时强行生成并行 WS。
- 禁止缺失 `card_export` 仍继续流转 `/vk`。

## 4. 互不干涉硬约束（必须显式写入）

1. **文件白名单互斥**：同一文件只能归属一个 WS（共享文件需指定唯一 owner）。
2. **状态字段单写入权**：关键字段只能由一个 WS 改写语义。
3. **接口契约先冻结**：输入/输出结构先定稿，再并行开发（通过 `WS-00` 落文）。
4. **路由收敛不退化**：任何 WS 不得引入“重复澄清”循环。
5. **合并顺序固定**：先并行交付层，再串行门禁层。

## 5. 协作模式（默认无总控）

- 默认采用 **无总控** 协作：按 WS 文档一对一分配给协作者执行。
- 每个协作者需在对应 `WS-*.md` 末尾填写“协作者自检卡”。
- `merge_checklist.md` 默认为可选，仅在共享资源冲突时启用。

## 6. 与其他命令关系

推荐最短链路：`/plan -> /vkplan（= /rwfj） -> /vktodo（或 /vkkb） -> /imp-ws -> /review -> /test`

- `/plan`：提供需求、架构与 seed 真理来源
- `/vkplan`：用户入口，语义等价 `/rwfj`
- `/rwfj`：底层并行编排实现（拆包/边界/依赖/合并）
- `/vk`：可选预览命令（查看建卡 payload + 导入提示词）
- `/vktodo` / `/vkkb`：默认看板落地命令
- `/imp-ws`：负责单 WS 实现

## 7. 简化用法（默认即可）

直接执行：`/rwfj`

补充建议：
- 若已确定要并行，优先先执行 `/vkplan`，可减少 `/rwfj` 推导误差。

## 8. 30 秒人工验收清单（执行 `/rwfj` 后必看）

1. `parallel_plan.md` 含独立章节：`## 0. G0 协议冻结`。
2. 存在 `WS-00_G0_协议冻结.md`，且其他并行 WS 对其 `hard_depends_on`。
3. 文档包含并行四问结论（通过或不通过）。
4. 文档包含自动拆分依据（文件冲突/状态冲突/依赖阻断）。
5. 工作包编号为 `WS-01 ... WS-N` 动态数量。
6. 每个 `WS-*.md` 都有白名单、禁区、单写入权、局部验收命令。
7. Gate WS 含 TC-ID 映射表，失败项可追溯到责任 WS。
8. 涉及前端交互/跨端契约消费的 WS 含浏览器测试触发评估。
9. 若并行不通过，必须有串行回退路线与原因。
10. 每个 `WS-*.md` 文末包含 `card_export`，且字段齐全。
11. `parallel_plan.md` 包含 `## 9. 看板导出索引` 与 `task_key`。
12. 卡片唯一键满足：`<task_key>::<WS-ID>`。
