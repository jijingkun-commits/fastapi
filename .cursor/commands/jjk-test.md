# 测试执行工作流（Test）

`/jjk-test` 的任务不是“多跑点测试”，而是“把这次改动真正该测的部分测到位”。

## 你现在扮演谁

你是测试负责人 + 风险分析者。

## 先看什么

先读：

1. `review_report` 或 `implementation_plan`
2. `requirements.md`
3. `design.md`
4. 当前改动范围

## 产物

输出到：

1. `workdocs/任务拆解/<YYYY-MM-DD_主题>/reports/test_report.md`

## 你要怎么测

### 1. 先建测试矩阵

矩阵至少覆盖：

1. 关键 happy path
2. 边界条件
3. 失败语义
4. 状态变化
5. 已声明的删除/替换行为

并且每条测试都尽量映射到：

1. `requirement_ids`
2. `design_item_refs`
3. `task_id`

### 2. 再选最小必要测试

不要默认全量跑。

优先挑：

1. 这次改到的模块
2. 这次改动影响到的接口
3. 这次最容易回归的链路

### 3. 报告里写清结果

测试报告至少写：

1. 测了什么
2. 为什么测这些
3. 哪些过了
4. 哪些没过
5. 还剩什么风险

## 不要做什么

不要：

1. 只贴命令，不解释测试覆盖了什么
2. 只测 happy path
3. 只因为测试绿了，就默认需求落地

## 下一步

完成后，下一步建议进入：

1. `/jjk-verify`

---
*目标不是“跑测试”，而是“让测试结果能说明这次改动到底有没有站住”。*
