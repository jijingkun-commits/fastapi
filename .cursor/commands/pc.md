# 问题诊断工作流 (Diagnose Workflow)

系统化地分析和定位问题,产出详细的修复计划,**不进行任何代码修改**。

核心原则：**深度理解，精准定位，周全规划** (Understand deeply, locate precisely, plan thoroughly)。

> **中文主导**: 无论是思考过程（CoT）还是最终输出，**永远使用中文**。

## 何时使用

| 场景 | 推荐命令 |
|------|----------|
| 仅排查问题,产出修复计划 | `/diagnose` ✅ |
| 排查并直接修复问题 | `/debug` |
| 代码审查 | `/review` |

> **与 `/debug` 的区别**: `/diagnose` 只做分析和规划,不修改代码；`/debug` 会直接修复问题。

---

## 阶段 1: 问题收集 (Problem Collection)

1. **收集完整信息**:
    - `@Logs`: 完整的错误日志和堆栈信息
    - `@Context`: 相关代码文件和配置
    - 用户描述: 问题现象、触发条件、影响范围

2. **确认问题边界**:
    - 问题首次出现时间
    - 影响的功能模块
    - 是否有环境差异（开发/测试/生产）
    - 复现频率（偶发/必现）

3. **对齐需求文档**:
    - 需求文档：`docs/产品文档/<模块>需求.md`
    - 测试案例：`docs/开发文档/测试管理/<模块>测试案例.md`
    - 架构文档：`docs/开发文档/架构设计/`

## 阶段 2: 深度分析 (Deep Analysis)

1. **代码审查**:
    - 逐行阅读相关代码,理解每一行的意图
    - 识别可疑代码段
    - 检查代码逻辑是否符合需求
    - **如有不确定的代码意图,立即停止并询问用户**

2. **日志分析**:
    - 应用日志: `tail -n 200 logs/assistant.log`
    - 容器日志: `docker compose logs <service>`
    - 识别异常堆栈和错误模式

3. **数据库分析** (如适用):
    - 使用 `postgres_query` 工具查询相关数据
    - 检查数据完整性和一致性
    - 分析数据流向

4. **依赖分析**:
    - 检查第三方库版本
    - 分析模块间依赖关系
    - 识别潜在的兼容性问题

5. **架构分析**:
    - 理解全局架构
    - 分析问题在架构中的位置
    - 评估影响范围

## 阶段 3: 根因定位 (Root Cause Analysis)

1. **假设验证**:
    - 列出所有可能的根因假设
    - 逐一验证每个假设
    - 排除不可能的原因

2. **确定根本原因**:
    - 明确问题的直接原因
    - 分析深层次的设计或架构问题
    - 识别是否有类似的潜在问题

3. **影响评估**:
    - 问题影响的功能范围
    - 数据一致性风险
    - 性能影响
    - 安全隐患

## 阶段 4: 修复计划产出 (Fix Plan Output)

**产出**: `docs/内部参考/迭代需求/fix_plan.md` (Artifact)

**必须包含**:

### 1. 问题摘要
- 问题描述
- 根本原因
- 影响范围
- 严重程度评级

### 2. 修复方案
- **方案概述**: 修复的核心思路
- **涉及文件**: 列出需要修改的所有文件
- **修改点清单**:
    ```markdown
    #### [文件路径](file:///absolute/path/to/file)
    - [ ] 修改点 1: 具体描述
    - [ ] 修改点 2: 具体描述
    ```
- **数据库变更** (如适用): DDL/DML 语句
- **配置变更** (如适用): 需要修改的配置项

### 3. 风险评估
- 修复可能引入的新问题
- 需要特别注意的边界情况
- 回滚方案

### 4. 验证计划
- **单元测试**: 需要新增或修改的测试
- **集成测试**: E2E 测试场景
- **手动验证**: 验证步骤清单
- **性能验证** (如适用): 性能指标要求

### 5. 预防措施
- 需要补充的测试覆盖
- 需要添加的日志
- 代码规范改进建议
- 架构优化建议

### 6. 实施建议
- 修复优先级
- 建议的实施顺序
- 预计工作量
- 是否需要分阶段实施

## 阶段 5: 文档关联 (Documentation Link)

在 `docs/内部参考/迭代需求/fix_plan.md` 中关联相关文档:

- [ ] 需求文档: `docs/产品文档/<模块>需求.md`
- [ ] 测试案例: `docs/开发文档/测试管理/<模块>测试案例.md`
- [ ] API 文档: `docs/API文档/接口文档.md` (如涉及 API 变更)
- [ ] 数据库设计: `docs/开发文档/架构设计/数据库设计.md` (如涉及数据库变更)
- [ ] 架构文档: `docs/开发文档/架构设计/` (如涉及架构变更)

## 阶段 6: 用户确认 (User Confirmation)

产出 `docs/内部参考/迭代需求/fix_plan.md` 后:

1. **向用户展示修复计划**
2. **询问用户**:
    - 计划是否合理？
    - 是否有遗漏的风险点？
    - 是否需要调整优先级？
    - 是否立即执行修复？

3. **下一步行动**:
    - 用户确认后,可执行 `/imp` 或 `/debug` 进行实际修复
    - 或用户自行修复,使用计划作为指导

---

## 核心原则

1. **绝不修改代码**: 本工作流只做分析和规划
2. **深度理解**: 每一行代码都要理解其意图
3. **遇到不确定立即停止**: 不清楚的地方必须询问用户
4. **全局视角**: 考虑架构、性能、可读性
5. **周全规划**: 修复计划要详尽、可执行

---

## 如何使用

```
/diagnose 生产环境出现 500 错误,日志如下...
```

*使用 `/diagnose` 触发。适合在需要深度分析问题但暂不修复时使用。*
