# 任务澄清 (Clarify Task)

通过结构化问答快速澄清需求，确保理解一致后再行动。

> **中文主导**: 无论是思考过程（CoT）还是最终输出，**永远使用中文**。

## 何时使用

| 场景 | 推荐命令 |
|------|----------|
| 需求模糊，想快速确认理解 | `/jjk-clarify` ✅ |
| 需要深度澄清并产出上下文文档 | `/jjk-clarify --deep` ✅ |
| 需要产出正式需求文档 | `/jjk-plan` |
| 一站式完成从需求到交付 | `/jjk-feature` |

> **与 `/jjk-plan` 的区别**: `/jjk-clarify` 是轻量级问答，默认不产出文档；`--deep` 模式产出 `<topic>_context.md` 供 `/jjk-plan` 消费。

---

## 模式选择

### 默认模式（快速对齐）

`/jjk-clarify <需求描述>`

- 2-4 个问题快速对齐
- 不产出文档
- 适用于简单需求确认

### Deep 模式（深度澄清）

`/jjk-clarify --deep <需求描述>` 或 `/jjk-clarify -d <需求描述>`

- 领域感知的灰色地带分析
- 每个领域 4 问深挖
- 产出 `docs/内部参考/迭代需求/<topic>_context.md`
- 适用于复杂需求、多人协作前的对齐

---

## 默认模式执行步骤

### 1. 提出澄清问题

使用 2-4 个问题澄清：

- **目标**: 用户想要达成什么？
- **范围**: 涉及哪些模块/页面？
- **边界**: 异常情况如何处理？
- **优先级**: 哪些是必须的，哪些是可选的？

### 2. 复述确认

```markdown
## 我的理解

1. 目标: [xxx]
2. 范围: [xxx]
3. 边界条件: [xxx]

请确认是否正确，或补充说明。
```

### 3. 确认后再行动

用户确认后，询问：
- "需要我生成正式需求文档吗？" -> 转 `/jjk-plan`
- "现在可以开始实现吗？" -> 转 `/jjk-imp` 或 `/jjk-feature`

---

## Deep 模式执行步骤

### 1. 领域分析（自动）

分析任务描述，识别任务类型并生成领域特定的灰色地带：

| 任务类型 | 灰色地带方向 | 示例问题 |
|---------|-------------|---------|
| 用户看到的（UI/页面） | 布局、信息密度、交互状态、空状态 | "列表为空时显示什么？" |
| 用户调用的（API） | 响应格式、错误码、认证、版本兼容 | "并发请求如何处理？" |
| 用户运行的（脚本/CLI） | 输出格式、参数、错误处理、幂等性 | "重复执行是否安全？" |
| 数据处理的（ETL/分析） | 数据口径、时间窗口、异常值、精度 | "跨月数据如何切分？" |
| 流程编排的（AI/Workflow） | 状态流转、超时、重试、降级策略 | "LLM 超时后走什么分支？" |
| 架构变更的（重构/迁移） | 兼容性、回滚、灰度、数据迁移 | "旧接口保留多久？" |

根据任务类型生成 3-4 个领域特定的灰色地带，不使用泛化问题。

### 2. 灰色地带展示与选择

```markdown
## 识别到的灰色地带

根据分析，这是一个 [任务类型] 类型的任务，以下领域需要澄清：

1. [灰色地带 A]: [简要说明为什么需要澄清]
2. [灰色地带 B]: [简要说明]
3. [灰色地带 C]: [简要说明]

请选择需要深入讨论的领域（可多选，如 "1,3"）。
```

### 3. 逐领域深挖

对每个选中的领域：

1. 提出 4 个递进式问题（从宏观到细节）
2. 记录用户的每个回答
3. 4 问后确认："关于 [领域 A] 还有需要补充的吗？还是进入下一个领域？"
4. 若用户要求继续，再追加 4 问

### 4. 范围守卫（强制）

- 讨论只澄清"怎么做"，不扩展"做什么"
- 若用户提出新功能："这属于独立需求，我先记下来，不在本次范围内。"
- 延伸想法记录到 `_context.md` 的"延伸想法"段，不丢失也不执行

### 5. 产出 Context 文档

产出 `docs/内部参考/迭代需求/<topic>_context.md`：

```markdown
# <topic> 上下文澄清

## 任务类型
[识别到的任务类型]

## 澄清结论

### [领域 A]
- 决策 1: [具体结论]
- 决策 2: [具体结论]

### [领域 B]
- 决策 1: [具体结论]

## 延伸想法（不在本次范围）
- [想法 1]: [简要描述]

## 下游消费
本文档供 `/jjk-plan` 读取，作为需求分析的输入上下文。
```

### 6. 衔接下游

- "需要我基于这些澄清生成正式需求文档吗？" -> 转 `/jjk-plan`（自动读取 `_context.md`）
- "现在可以开始实现吗？" -> 转 `/jjk-imp` 或 `/jjk-feature`

---
*使用 `/jjk-clarify` 触发。`--deep` 模式适合复杂需求的深度对齐。*
