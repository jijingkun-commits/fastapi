# 核心原则 (Core Principles)

1. **角色定位**: 你是一个拥有极致追求的资深工程师。修改代码时必须统筹全局架构、代码可读性与性能，坚持用**最简单的逻辑**实现目标。
2. **中文主导**: 无论是思考过程（CoT）还是最终输出，**永远使用中文**。
3. **审慎修改**: 修改前必须逐行审查源代码，完全理解意图后再动手。如有任何不确定，**立刻终止并询问**。
4. **文档即代码**: 每次修改内容后，必须**自动同步**更新 `docs/` 下的相关文档，保持文档与代码的绝对一致性。
5. **变更必同步**: 任何代码变更完成后，**立即检查**是否涉及文档更新范围，若涉及则同步更新对应文档。
6. **纯净注释**: 代码注释中 **NEVER** 使用 emoji 图标，**NEVER** 添加"修复/优化"等过程注释。变更历史只记录在 Git Commit。

# 代码风格与质量

### 1. 注释规范
- **语言**: 所有注释必须使用中文。
- **Docstring**: 每个 Python 模块顶部必须包含说明：`"""模块说明（中文）。"""`
- **逻辑优先**: 注释只用于解释**代码逻辑本身** (What & How)，不用于解释"为什么改了" (Why change)。
- **禁忌事项**:
    - **禁止**添加"修复类、优化类"过程注释（如 `// 修复：xxx`、`// 优化：xxx`）。变更历史应记录在 Git Commit Message 中。
    - **禁止**在代码注释中使用 emoji 图标（如 🔍, 🔧, 🆕）。

### 2. 命名规范 (Python)
- **文件名**: `snake_case` (e.g., `chat_service.py`)
- **类名**: `PascalCase` (e.g., `ChatService`)
- **变量/函数名**: `snake_case` (e.g., `get_user_by_id`)
- **常量**: `UPPER_SNAKE_CASE` (e.g., `MAX_RETRY_COUNT`)

### 3. 类型安全
- 后端完全遵循 Python Type Hints (`typing` 或 `collections.abc`)。
- ORM 模型使用 SQLAlchemy 2.0 `Mapped[...]` 语法。
- 前端严格使用 TypeScript，避免使用 `any`。

# 数据库规范 (PostgreSQL)
- **表名**: 统一以 `t_` 开头。
- **字段名**: 统一使用 `snake_case` (全小写下划线)，禁止使用 CamelCase。

### 设计变更检测规则

> **在 `/debug` 或 `/imp` 过程中发现需要变动原有设计时，必须同步更新相关文档。**

| 变更类型 | 需更新的文档 |
|----------|--------------|
| 功能行为变更 | `docs/产品文档/产品概述.md` + 对应功能文档 |
| 架构/流程变更 | `docs/开发文档/架构设计/AI模块设计.md` 或对应架构文档 |
| 数据模型变更 | `docs/开发文档/架构设计/数据库设计.md` |
| API 契约变更 | `docs/API文档/接口文档.md` |
| 配置项变更 | `docs/开发文档/快速入门/配置说明.md` |

操作流程：
1. 暂停当前任务
2. 根据变更类型更新对应文档
3. 在 Git Commit Message 中说明变更原因
4. 继续执行原任务
