## 1. 概述

统一智能附件系统允许用户在聊天中上传图片、表格、文档等多种文件。当前架构的重点不是“把附件提示词硬塞进 Prompt”，而是先把附件收口成结构化合同，再由 `supervisor` 结合用户目标做 planning。

一句话版：
- `chat_service` 负责把附件整理成 `attachment_manifest + lightweight_probe`
- `multi_agent_graph.preprocess` 负责产出 `planning_route`
- 真正执行仍由 `direct_tool / data_workflow / research_subagent / todo_workflow / mixed` 决定

## 2. 系统流程

### 2.1 文件上传

1. **上传接口**: `POST /api/v1/upload`
2. **存储**: 文件上传到 MinIO `assets` 桶
3. **返回**: 返回内部代理 URL，例如 `/api/v1/assets/proxy/...`

### 2.2 限制与规范

- **文件大小**: 单个文件最大 **50MB**
- **支持格式**:
  - **图片**: JPG, PNG, GIF, WEBP
  - **文档/数据**: Excel, CSV, PDF, Word, TXT, JSON

### 2.3 结构化附件合同

当用户发送带附件的消息时，系统不再把附件信息当成主合同拼进 Prompt，而是先生成两份结构化输入：

1. **`attachment_manifest`**：附件客观元数据
2. **`lightweight_probe`**：轻量预检事实

#### `attachment_manifest`

最小字段：

| 字段 | 说明 |
|---|---|
| `attachment_id` | 附件唯一标识，优先使用 `object_key` |
| `name` | 文件名 |
| `mime` | MIME 类型 |
| `size_bytes` | 文件大小 |
| `uri` | 附件访问地址 |
| `derived_kind` | 归一类别：`image` / `tabular` / `document` / `binary` |

#### `lightweight_probe`

最小字段：

| 字段 | 说明 |
|---|---|
| `attachment_id` | 关联附件 |
| `probe_status` | 预检状态 |
| `summary` | 给 supervisor 看的轻量摘要 |

按类型可选补充：

- `tabular`: `sheet_names`, `column_names`, `row_count_estimate`, `sample_types`
- `document`: `title`, `page_count`, `section_hints`, `ocr_needed`
- `image`: `vision_hint`, `ocr_hint`, `chart_like`

### 2.4 supervisor 附件规划

`preprocess` 节点会基于以下输入做附件 planning：

1. `user_goal`
2. `conversation_state`
3. `attachment_manifest`
4. `lightweight_probe`

输出为 `attachment_planning`，其中核心字段是 `planning_route`。

#### `planning_route`

| 路由 | 适用场景 |
|---|---|
| `direct_tool` | 单附件、单动作、直接读取或识图 |
| `data_workflow` | 表格/数据分析/统计/聚合/可视化 |
| `research_subagent` | 多来源资料总结、对比、证据归纳 |
| `todo_workflow` | 从附件提炼待办，或进入待办确认闭环 |
| `mixed` | 同一轮存在多个子目标，owner 仍是 `supervisor` |

规划结果至少包含：

| 字段 | 说明 |
|---|---|
| `attachment_planning.planning_route` | 本轮附件路由 |
| `attachment_planning.selected_attachment_ids` | 本轮真正消费的附件 |
| `attachment_planning.attachment_roles` | 每个附件扮演的角色，例如 `data_source` / `evidence_source` / `image_input` |
| `attachment_planning.planner_reason` | 规划原因 |
| `attachment_planning.requires_user_confirmation` | 是否需要用户确认 |

## 3. 关键组件

### 3.1 Upload API (`upload_api.py`)

- 校验文件类型和大小
- 生成 UUID 文件名防止冲突
- 对接 MinIO SDK 进行流式上传

### 3.2 Chat Service (`chat_service.py`)

- `stream` 接收 `attachments`
- 构建 `attachment_manifest + lightweight_probe`
- 将结构化附件合同写入 graph 输入状态
- 不再把 prompt hint 当成附件主合同

### 3.3 MultiAgentGraph (`multi_agent_graph.py`)

- `preprocess` 读取附件合同并生成 `planning_route`
- 将附件规划摘要写入 `system_context`
- `mixed` 场景仍由 `supervisor` 汇总，不允许子 workflow 接管主会话

### 3.4 Agent / Tool 边界

- `read_uploaded_file` / `analyze_image` 继续是 atomic tool
- `todo_workflow` / `data_workflow` 只消费 supervisor 规划结果
- `research_subagent` 只做一次性研究任务，不持有跨轮会话 owner

## 4. 设计原则

1. **先定用户目标，再定附件去向**，不能只看文件类型硬路由
2. **附件规划 owner 是 supervisor**，不是 workflow
3. **Prompt hint 只能做辅助手段，不能做唯一合同**
4. **mixed 只能由 supervisor 持有执行计划**
