## 2. 基础对话测试

### TC-CHAT-01: 流式响应首 Token

| 属性 | 值 |
|-----|---|
| **前置条件** | 用户已登录，后端正常 |
| **输入** | "你好" |
| **预期行为** | 1. 2 秒内出现首字符<br>2. 过程中显示"正在输入"指示<br>3. 生成完成后指示消失 |
| **验证方法** | 记录发送时间与首字符出现时间差，应 < 2s |
| **数据库验证** | `SELECT * FROM t_message WHERE conversation_id = ? ORDER BY created_at DESC LIMIT 2` — 应有 user + assistant 两条记录 |

### TC-CHAT-02: 对话历史持久化

| 属性 | 值 |
|-----|---|
| **前置条件** | 已发送至少 3 条消息并收到回复 |
| **步骤** | 1. 记录当前消息数量和内容<br>2. 刷新页面（F5）<br>3. 等待页面完全加载 |
| **预期行为** | 1. 历史消息完整显示，无丢失<br>2. 消息顺序与刷新前一致<br>3. 用户消息和 AI 回复的角色标识正确 |
| **验证方法** | 对比刷新前后的消息列表内容、数量、顺序 |

### TC-CHAT-03: 多轮上下文保持

| 属性 | 值 |
|-----|---|
| **前置条件** | 同一对话线程 |
| **步骤** | 1. 发送"我下午有会议"<br>2. 等待 AI 回复<br>3. 发送"它几点开始？"<br>4. 等待 AI 回复<br>5. 发送"帮我总结一下刚才的对话" |
| **预期行为** | 1. 第 2 轮 AI 能理解"它"指代"会议"<br>2. 第 3 轮 AI 能概括前两轮的对话主题 |
| **边界情况** | 超过 10 轮后上下文是否仍准确（受 context window 限制） |

### TC-CHAT-04: 停止生成与反馈

| 属性 | 值 |
|-----|---|
| **前置条件** | 发送一个需要长回复的问题（如"详细介绍中国四大银行的发展历史"） |
| **步骤** | 1. 发送问题，等待 AI 开始流式输出<br>2. 在生成过程中点击"停止"按钮<br>3. 对已生成内容进行点赞<br>4. 对另一条回复进行点踩 |
| **预期行为** | 1. 点击停止后，流式输出立即中断<br>2. 已生成的部分内容被保留展示<br>3. 点赞/点踩图标状态变化正确<br>4. 反馈记录被保存到数据库 |
| **数据库验证** | `SELECT feedback FROM t_message WHERE id = ?` — 应有对应反馈值 |

## 3. 对话同步测试

### TC-SYNC-01: 前后端消息一致性

| 属性 | 值 |
|-----|---|
| **步骤** | 1. 发送消息"测试同步一致性"<br>2. 等待 AI 回复完成<br>3. 通过 API 查询后端存储的消息内容 |
| **预期行为** | 1. 前端展示的消息内容与后端 `t_message` 表中存储的一致<br>2. 消息的 role（user/assistant）标识一致<br>3. 消息时间戳相差不超过 1 秒 |
| **验证方法** | `GET /api/v1/conversations/{id}/messages` 与前端展示对比 |

### TC-SYNC-02: 刷新后消息完整加载

| 属性 | 值 |
|-----|---|
| **前置条件** | 当前对话有 5 条以上消息 |
| **步骤** | 1. 记录当前消息内容列表<br>2. 强制刷新页面（Ctrl+Shift+R）<br>3. 等待对话列表和消息加载完成 |
| **预期行为** | 1. 刷新后消息数量相同<br>2. 消息内容逐条匹配<br>3. Markdown 渲染和代码块格式一致 |

> **与 TC-CHAT-02 区别**: TC-CHAT-02 侧重持久化机制验证（消息是否保存），本用例侧重同步协议验证（前后端数据是否一致）。

### TC-SYNC-03: 快速连续发送

| 属性 | 值 |
|-----|---|
| **步骤** | 1. 在 1 秒内连续发送 3 条消息：<br>  - "第一条"<br>  - "第二条"<br>  - "第三条"<br>2. 等待所有回复完成 |
| **预期行为** | 1. 3 条消息均被正确接收，无丢失<br>2. 消息按发送顺序排列<br>3. 每条消息均有对应的 AI 回复（或后续消息排队等待） |
| **边界情况** | 若系统限制并发，应有友好提示而非静默丢弃 |

### TC-SYNC-04: 长文本响应完整性

| 属性 | 值 |
|-----|---|
| **输入** | "请列出 20 个常见的银行业务术语及其解释"（触发长回复） |
| **预期行为** | 1. 回复内容完整，列出全部 20 项（或模型实际输出的全部内容）<br>2. 末尾无截断（不以 `...` 或不完整句子结束）<br>3. Markdown 格式正常渲染 |
| **验证方法** | 对比前端显示字符数与后端存储的字符数 |

### TC-SYNC-05: 特殊字符处理

| 属性 | 值 |
|-----|---|
| **输入** | 依次测试以下特殊字符输入：<br>1. HTML 标签: `<script>alert('xss')</script>`<br>2. SQL 注入: `'; DROP TABLE t_message; --`<br>3. Emoji: `测试 🎉 消息`<br>4. 中文特殊符号: `【】《》「」` |
| **预期行为** | 1. HTML 标签被转义显示，不执行脚本<br>2. SQL 注入字符串作为普通文本展示<br>3. Emoji 正常显示<br>4. 中文特殊符号正常显示 |

### TC-SYNC-06: 历史结构串兼容回放

| 属性 | 值 |
|-----|---|
| **前置条件** | 历史消息中存在遗留结构串（如 `[{'type': 'text', 'text': '...'}]`） |
| **步骤** | 1. 调用 `GET /api/v1/chat/threads/{thread_id}/messages` 获取历史消息<br>2. 检查返回的 `content` 字段 |
| **预期行为** | 1. 接口返回可读正文文本，不暴露内部结构串<br>2. 非结构串普通文本保持原样输出 |
| **自动化覆盖** | `tests/api/test_chat_api.py::test_get_messages_normalizes_legacy_structured_content` + `tests/unit/test_chat_repo_serialization.py` |

### TC-SYNC-07: 首次点击“新建会话”应直接进入空会话

| 属性 | 值 |
|-----|---|
| **前置条件** | URL 带 `threadId`（已处于历史会话） |
| **步骤** | 1. 打开 `/chat?threadId=<existing>`<br>2. 点击右上角“新建会话”按钮 |

| **自动化覆盖** | `web/e2e/chat-thread-switch.spec.cjs`（`TC-CHAT-THREAD-01`） |

### TC-SYNC-08: 历史列表左侧区域点击可直接切换会话

| **预期行为** | 1. 一次点击即可切换到目标会话<br>2. URL `threadId` 与目标会话一致 |

## 4. 异常处理测试

### TC-CHAT-ERR-01: 网络中断恢复

| 属性 | 值 |
|-----|---|
| **步骤** | 1. 发送一条消息<br>2. 在 AI 生成过程中断开网络（DevTools → Network → Offline）<br>3. 等待 5 秒<br>4. 恢复网络连接 |
| **预期行为** | 1. 断网后显示网络错误提示<br>2. 恢复网络后，用户可重新发送消息<br>3. 之前的对话历史不丢失 |

### TC-CHAT-ERR-02: 后端服务异常

| 属性 | 值 |
|-----|---|
| **前置条件** | 后端服务不可用或 LLM API 返回错误 |
| **步骤** | 发送消息 |
| **预期行为** | 1. 前端显示友好错误提示（非白屏/堆栈）<br>2. 错误消息有明确指引（如"服务暂时不可用，请稍后重试"）<br>3. 输入框恢复可用状态，不卡死 |

### TC-CHAT-ERR-03: 认证过期

| 属性 | 值 |
|-----|---|
| **前置条件** | 用户 Token 已过期 |
| **步骤** | 1. 手动清除或篡改 localStorage 中的 token<br>2. 尝试发送消息 |
| **预期行为** | 1. 返回 401 错误<br>2. 自动跳转到登录页或显示重新登录提示<br>3. 不暴露敏感信息 |

### TC-CHAT-ERR-04: 空消息与超长消息

| 属性 | 值 |
|-----|---|
| **步骤** | 1. 尝试发送空消息（仅空格/换行）<br>2. 尝试发送超长消息（10000 字符以上） |
| **预期行为** | 1. 空消息：发送按钮不可点击或提示"请输入内容"<br>2. 超长消息：前端有字符限制提示，或后端返回明确错误 |

### TC-CHAT-ERR-05: 老 `.doc` 上传时统一提示转换为 `.docx`

| 属性 | 值 |
|-----|---|
| **前置条件** | 准备一个老 `.doc` 文件 |
| **步骤** | 1. 在聊天输入区选择 `.doc` 文件<br>2. 观察前端提示与附件预览区<br>3. 如请求已发到后端，检查接口返回文案 |
| **预期行为** | 1. 前端立即提示 `暂不支持 .doc，请先转换为 .docx`<br>2. `.doc` 文件不进入输入区附件预览列表<br>3. 若后端命中 `.doc`，返回文案与前端保持完全一致，不再出现“前端说不支持、后端又放行”的双口径 |
| **自动化覆盖** | `web/e2e/chat-attachment-history.spec.cjs` + `tests/unit/test_uploaded_docx_reader.py::test_read_uploaded_file_should_ask_to_convert_legacy_doc` |

### TC-CHAT-ERR-06: 损坏 `.docx` 的反馈应归类为读取失败

| 属性 | 值 |
|-----|---|
| **前置条件** | 准备一个扩展名为 `.docx`、但内容损坏的文件 |
| **步骤** | 1. 通过 `read_uploaded_file` 读取损坏 `.docx`<br>2. 观察返回结构中的 `status` 与 `message` |
| **预期行为** | 1. 返回结果明确为读取失败，而不是“格式不支持”<br>2. 错误消息中包含 `DOCX`，用户能看懂是文件损坏或解析失败<br>3. 不把 `.docx` 错误归到老 `.doc` 转换提示上 |
| **自动化覆盖** | `tests/unit/test_uploaded_docx_reader.py::test_read_uploaded_file_should_report_invalid_docx` |

## 5. 银行业务场景测试

### TC-CHAT-BIZ-01: 银行业务咨询

| 属性 | 值 |
|-----|---|
| **角色** | 银行新员工 |
| **步骤** | 1. 发送"什么是对公存款和零售存款的区别？"<br>2. 等待 AI 回复<br>3. 追问"分行在统计时应该注意什么？" |
| **预期行为** | 1. AI 能准确解释对公/零售存款概念<br>2. 多轮追问中上下文保持连贯<br>3. 回复使用银行专业术语但通俗易懂 |

### TC-CHAT-BIZ-02: 跨 Agent 路由（银行场景）

| 属性 | 值 |
|-----|---|
| **角色** | 分行经理 |
| **步骤** | 1. 发送"帮我查一下上月各支行的存款余额"（应路由到问数助手）<br>2. 发送"创建一个待办：下周一提交分行月报"（应路由到待办助手）<br>3. 发送"AI 助手有哪些功能？"（应由通用 Agent 回答） |
| **预期行为** | 1. 数据查询请求被正确路由到问数助手<br>2. 待办创建请求被正确路由到待办助手<br>3. 通用问题由默认 Agent 回答<br>4. 各次路由之间上下文不互相干扰 |

### TC-CHAT-BIZ-03: 合规边界（敏感信息处理）

| 属性 | 值 |
|-----|---|
| **角色** | 客户经理 |
| **步骤** | 1. 发送包含客户身份证号的消息（如"客户张三，身份证号 110101199001011234，需要办理贷款"）<br>2. 发送包含银行卡号的消息 |
| **预期行为** | 1. AI 回复中不应明文重复敏感信息<br>2. 如果系统有脱敏机制，敏感信息应被部分遮蔽（如 `1101****1234`）<br>3. 对话历史中存储的消息应符合数据安全规范 |
| **合规要求** | 符合银行业个人信息保护相关规定 |
