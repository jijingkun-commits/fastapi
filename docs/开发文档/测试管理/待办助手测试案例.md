### TC-RECUR-01: 设置每日重复任务

| 属性 | 值 |
|-----|---|
| **前置条件** | 用户已登录；存在待办 `A`（有 `due_date`） |
| **操作** | 调用 `POST /api/v1/todo/{A.id}/recurring`，body: `{\"pattern\":\"daily\",\"interval\":1}` |
| **预期行为** | 1. 返回 `success=true`<br>2. `todo.is_recurring=true`<br>3. 返回 `next_instance`，其 `parent_recurring_id=A.id` 且 `is_recurring=false` |
| **数据库验证** | `SELECT is_recurring, recurrence_pattern FROM t_todo WHERE id=A.id` 应为 `TRUE, 'daily'` |

### TC-RECUR-02: 设置每周重复任务（银行场景）

| 属性 | 值 |
|-----|---|
| **前置条件** | 用户已登录；存在待办 `B`：例如“分行对公存款余额周报”，`due_date` 为周一 09:00 |
| **操作** | 调用 `POST /api/v1/todo/{B.id}/recurring`，body: `{\"pattern\":\"weekly\",\"interval\":1,\"days\":[1]}` |
| **预期行为** | 1. 返回 `success=true`<br>2. `todo.recurrence_pattern='weekly'` 且 `recurrence_days=[1]`<br>3. 返回 `next_instance`，其 `due_date` 为下一个周一 09:00 左右（与 B 相差 7 天） |
| **验证点** | weekly 模式必须提供 `days`，未提供时返回 400 |

### TC-RECUR-03: 跳过一次重复任务实例

| 属性 | 值 |
|-----|---|
| **前置条件** | 已存在重复任务模板 `T`（is_recurring=true）且已生成实例 `I`（`parent_recurring_id=T.id`） |
| **操作** | 调用 `POST /api/v1/todo/{I.id}/skip-occurrence` |
| **预期行为** | 1. 返回 `success=true`<br>2. 实例 `I` 状态更新为 `cancelled`<br>3. 返回新的 `next_instance`，其 `parent_recurring_id=T.id` |
| **数据库验证** | `SELECT status FROM t_todo WHERE id=I.id` 应为 `cancelled` |

### TC-RECUR-04: 取消重复设置（含合规边界）

| 属性 | 值 |
|-----|---|
| **前置条件** | 存在模板待办 `T`（`is_recurring=true`） |
| **操作** | 1. 所有者调用 `DELETE /api/v1/todo/{T.id}/recurring`<br>2. 另一个用户尝试对 `T.id` 调用同一接口 |
| **预期行为** | 1. 步骤1返回 success=true，且模板 `is_recurring=false` 并清空 recurrence 字段<br>2. 步骤2必须失败（返回 404 或等价错误），且不泄露他人待办数据 |

### TC-MULTI-05: 复杂多项目压力场景（多轮对话回放）

**测试目标**：验证多项目、多约束、多变更下的状态保持、冲突校验、优先级重排与结构化输出能力。

**背景设定**：用户是城商行科技部开发中心经理，事务多且频繁插入新任务，容易推翻旧决定。

**对话脚本（回放顺序）**：

**Round 1**
- 用户：最近事情太多了，帮我把接下来要做的事情理一理。
- 期望：不直接生成待办，进入澄清模式，询问任务来源/时间范围/是否工作相关。

**Round 2**
- 用户：工作的为主吧。大概有几个项目：预售资金系统投标材料、AI 中台方案、零碎临时事。
- 期望：识别为多项目待办，对每个项目分别追问，不混在一起。

**Round 3**
- 用户：预售资金挺急，这周内要给。AI 中台不那么急，领导下周可能要听汇报。零碎先不管。
- 期望：解析“这周/下周”相对时间，标记紧急程度差异；识别“汇报”可能需要材料准备。

**Round 4**
- 用户：技术方案我负责，商务公司部给。技术方案要写系统架构、信创适配、实施计划。
- 期望：自动拆解为子任务；标记他人依赖（商务方案）；记录等待输入。

**Round 5**
- 用户：人力系统全行测评初稿这周要出，可能顺延；办公室又催了。
- 期望：识别延期与催办冲突，追问是否要重排优先级。

**Round 6**
- 用户：人力系统放到下周二之前吧，但周一我全天开会。
- 期望：解析“下周二之前”，识别周一不可用，推理有效工作时间窗口。

**Round 7**
- 用户：AI 中台不是写方案那么简单，先理落地路线图，顺便组织模式。
- 期望：将任务升级为复合任务并拆分为路线图与组织模式。

**Round 8**
- 用户：明天下午要“AI + 金融场景落地”1 页简要说明。
- 期望：插入高优先级临时任务，评估工作量小但时限极短，自动调整优先级。

**Round 9**
- 用户：AI 中台路线图先不做太细，和明天的 1 页说明能合并一部分吗？
- 期望：支持任务合并，调整范围，保留“后续补全”标记。

**Round 10**
- 用户：可以，按优先级给我。
- 期望：输出结构化待办清单（高/中/低优先级），包含依赖与约束。

**期望输出结构（示例）**：

- 高优先级（本周）
  - AI + 金融场景落地 1 页说明（截止：明天下午；可复用 AI 中台路线图部分）
  - 预售资金投标技术方案（子任务：系统架构/信创适配/实施计划；依赖：商务方案）
- 中优先级（下周）
  - 人力系统全行测评初稿（截止：下周二；约束：周一不可用）
  - AI 中台落地路线图（简化版；后续补充组织模式）
- 低优先级
  - 零碎临时事务（待补充）

**验证点清单**：
1. 多轮状态保持与任务拆解
2. 相对时间解析与工作日约束推理
3. 冲突识别与澄清追问
4. 任务合并与范围调整
5. 优先级重排与结构化输出

## 11. 已知问题与修复记录

### 11.1 问题：前端默认模型硬编码导致 402 错误

**问题描述**：
- 所有 LLM 调用返回 `402 Insufficient Balance` 错误
- 错误信息：`Error code: 402 - {'error': {'message': 'Insufficient Balance', ...}}`

**根本原因**：
前端 `web/src/lib/model-config.ts` 硬编码了默认模型：
```typescript
export const DEFAULT_MODEL_ID = "deepseek-chat";  // 硬编码 DeepSeek 原生渠道
```
导致所有请求都使用 `deepseek-chat`（DeepSeek 原生渠道，余额不足），而非数据库配置的默认模型 `deepseek-v3.2`（阿里通义渠道）。

**解决方案**：
1. 修改 `web/src/lib/model-config.ts`：
   ```typescript
   export const DEFAULT_MODEL_ID: string | undefined = undefined;
   ```
2. 修改 `web/src/hooks/use-model-config.ts`：忽略 localStorage 中的旧值 `deepseek-chat`

**验证方法**：
1. 刷新前端页面
2. 清除浏览器 LocalStorage 中的 `chat:selectedModel`
3. 发送测试消息，检查后端日志应显示 `model_name: 'deepseek-v3.2'`

**修复日期**：2026-01-31

### 11.2 配置建议

为避免类似问题，建议：
1. **前端不硬编码模型 ID**：使用 `undefined` 让后端决定默认模型
2. **后端统一管理默认模型**：通过 `t_llm_model.is_default` 字段配置
3. **监控 LLM 余额**：定期检查各 LLM 服务商账户余额
