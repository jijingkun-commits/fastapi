# 文档信息架构

> 更新时间：2026-03-12 CST
> 适用范围：整个仓库的文档目录与导航
> 目标：让人和 AI 都能快速判断“这份文档属于哪里、现在该看哪里、以后该落哪里”

## 1. 结论先行

当前仓库的文档体系，统一按两个维度理解：

1. 生命周期：`最终文档` / `过程文档` / `运行态产物`
2. 消费方式：`给人读` / `给机器读`

最终落地后的判断规则很简单：

| 生命周期 | 给人读 | 给机器读 |
|---|---|---|
| 最终文档 | `docs/产品文档`、`docs/开发文档`、`docs/API文档`、`docs/内部参考` | `contracts` |
| 过程文档 | `workdocs/需求/`、`workdocs/设计/`、`workdocs/任务拆解/` 根目录与 `workstreams/`、`workdocs/归档/` | `workdocs/**` 下的 `contracts/`、`reports/`、过程 Markdown/JSON |
| 运行态产物 | `none` | `.artifacts/**` |

一句话记忆：

- `docs/` 回答“人现在以什么为准”
- `contracts/` 回答“机器现在以什么契约为准”
- `workdocs/` 回答“这件事是怎么推进的”
- `.artifacts/` 回答“脚本当前跑到了哪一步”

## 2. 目录职责矩阵

| 路径 | 角色 | 是否进入主导航 | 典型内容 | 备注 |
|---|---|---|---|---|
| `docs/产品文档/` | 最终文档 / 给人读 | 是 | 功能需求、产品能力边界 | 单一真理源 |
| `docs/开发文档/` | 最终文档 / 给人读 | 是 | 架构、工作流、测试、规范、快速入门 | 单一真理源 |
| `docs/API文档/` | 最终文档 / 给人读 | 是 | API 解释、调用说明、事件语义 | 给人读的接口文档 |
| `contracts/` | 最终契约 / 给机器读 | 否 | OpenAPI / AsyncAPI / JSON Schema / 后续 machine contracts | 给工具和生成链读 |
| `docs/开发文档/规范/` | 最终文档 / 给人读 | 是 | 长期有效的工程治理规范 | 稳定规则文档 |
| `docs/开发文档/流程与工具/` | 最终文档 / 给人读 | 是 | 工作流、工具用法、速查清单、治理入口 | 面向开发协作的操作层说明 |
| `docs/内部参考/` | 最终文档 / 给人读 | 选择性 | 决策记录 ADR 正文、长期知识、专题资料 | 不再承载活跃过程材料 |
| `workdocs/需求/` | 过程文档 / 给人读 | 否 | requirements、范围说明、约束 | 活跃需求过程 |
| `workdocs/设计/` | 过程文档 / 给人读 | 否 | design、结构图、技术取舍 | 活跃设计过程 |
| `workdocs/任务拆解/` 根目录与 `workstreams/` | 过程文档 / 给人读 | 否 | `parallel_plan.md`、工作包说明 | task_split 给人读正文 |
| `workdocs/**/contracts/` | 过程文档 / 给机器读 | 否 | 输入合同、规划合同、映射 JSON | 机器消费 |
| `workdocs/**/reports/` | 过程文档 / 给机器读或半机器读 | 否 | 校验结果、消费报告、同步结果 | 默认不进主导航 |
| `workdocs/归档/` | 历史过程文档 / 给人读 | 否 | 测试报告、治理专题、旧过程正文 | 默认不进主导航 |
| `.artifacts/**` | 运行态产物 / 给机器读 | 否 | state、run、generated、lock、jsonl | 不属于文档阅读路径 |

### 2.1 `docs/开发文档/` 二级目录固定口径

这一层不再继续长出新的平级分类，固定只保留 6 类：

| 二级目录 | 负责什么 | 不负责什么 |
|---|---|---|
| `快速入门/` | 安装、部署、环境、初始化、配置上手 | 长期架构解释 |
| `架构设计/` | 稳定架构设计、模块边界、系统结构 | 临时实现过程 |
| `代码解读/` | 解释已有机制、协议、关键链路 | 操作手册 |
| `流程与工具/` | 工作流、工具用法、速查清单、治理入口 | 业务架构设计 |
| `测试管理/` | 测试指南、案例库、证据注册表 | 运行时产物 |
| `规范/` | 长期有效的工程规范与治理规则 | 项目过程正文 |

一句话判断：

- 回答“系统怎么搭”进 `架构设计/`
- 回答“代码怎么理解”进 `代码解读/`
- 回答“开发时怎么做”进 `流程与工具/`

## 3. 推荐目录结构

```text
docs/
├── README.md
├── SUMMARY.md
├── 产品文档/                 # 最终文档 / 给人读
├── 开发文档/                 # 最终文档 / 给人读
├── API文档/                  # 最终文档 / 给人读
└── 内部参考/                 # 长期有效内部知识

contracts/
├── api/                      # 最终契约 / 给机器读
└── streaming/                # 最终契约 / 给机器读

workdocs/
├── README.md
├── 需求/                     # 过程文档 / 给人读
├── 设计/                     # 过程文档 / 给人读
├── 任务拆解/                 # 过程正文 + topic 下 contracts/reports
└── 归档/
    ├── 正文/                 # 历史需求 / 设计 / 实施计划
    ├── 报告/                 # 历史测试 / 验收 / 审查 / 调试 / 重构 / 机读校验
    ├── 任务拆解/             # 历史 task bundle
    └── 专题/                 # 治理 / 研究 / 工作流规划 / 架构历史

.artifacts/
├── states/                   # 运行态 / 给机器读
├── runs/                     # 运行态 / 给机器读
└── generated/                # 运行态 / 给机器读
```

## 4. 过程文档怎么细分

### 4.1 给人读的过程文档

这类文档通常是 Markdown，目的是让人理解当前任务推进到了哪里。

推荐放法：

```text
workdocs/需求/<topic>/requirements.md
workdocs/设计/<topic>/design.md
```

### 4.2 给机器读的过程文档

这类文档通常是结构化合同、执行报告、JSON、YAML 或半机器读 Markdown。

推荐放法：

```text
workdocs/<某过程主题>/<topic>/contracts/*.json
workdocs/<某过程主题>/<topic>/reports/*.json
workdocs/任务拆解/<topic>/contracts/*.json
workdocs/任务拆解/<topic>/reports/*.json
workdocs/任务拆解/<YYYY-MM-DD_主题>/contracts/implementation_plan.md
workdocs/任务拆解/<YYYY-MM-DD_主题>/contracts/uat_cases.md
workdocs/任务拆解/<YYYY-MM-DD_主题>/reports/review_report.md
workdocs/任务拆解/<YYYY-MM-DD_主题>/reports/test_report.md
workdocs/任务拆解/<YYYY-MM-DD_主题>/reports/verify_report.md
workdocs/任务拆解/<YYYY-MM-DD_主题>/reports/debug_report.md
```

默认规则：

1. 机器读过程文件不要混在稳定文档目录里
2. 机器读过程文件优先和对应主题放在一起
3. 如果一份 JSON 只是运行中间态，而不是过程合同，放 `.artifacts/`

## 5. 当前仓库的迁移期判断

目前仓库还存在一些迁移期旧路径：

| 旧路径 | 当前角色判断 | 后续方向 |
|---|---|---|
| `workdocs/归档/正文/` | 历史正文归档 | 承接原历史需求 / 设计 / 实施计划正文 |
| `workdocs/归档/报告/` | 历史报告归档 | 承接原历史测试 / 验收 / 审查 / 调试 / 重构 / 机读结果 |
| `workdocs/归档/专题/` | 历史专题归档 | 承接治理专题、研究报告、工作流规划、架构历史 |
| `docs/api/` | 旧的机读契约目录 | 机读 API 契约已迁到 `contracts/api/` |
| 旧需求入口页 | 旧入口说明页 | 主体正文已迁到 `workdocs/归档/`，当前只保留 README |
| 旧任务拆解入口页 | 旧入口说明页 | 当前只保留 README，不再承载活跃内容 |

迁移期规则：

1. 新增过程文档优先进入 `workdocs/`
2. `workdocs/归档/` 固定收敛为 `正文 / 报告 / 任务拆解 / 专题` 四个一级桶，`docs/内部参考/*` 下旧入口只保留说明页，不再继续长胖
3. 主导航不继续扩大对旧过程目录的引用

## 6. 如何快速判断一份文件应该放哪

按下面顺序判断：

1. 这份内容是不是“当前有效事实”？
2. 如果不是，它是不是“人需要追过程”的材料？
3. 如果也不是，它是不是“脚本/工具要消费”的合同或报告？
4. 如果连过程材料都不是，而是运行状态或缓存，那就进 `.artifacts/`

简化判断：

- 想回答“现在到底以什么为准” → `docs/`
- 想回答“这个主题怎么推进到现在的” → `workdocs/`
- 想回答“脚本此刻跑到了哪一步” → `.artifacts/`

## 7. 这轮最推荐的执行顺序

1. 先把目录职责写清楚
2. 再把入口文档改清楚
3. 再开始迁存量过程文档
4. 最后收紧门禁和自动校验

原因：

1. 如果地图没先画清楚，迁移只会制造新的混乱
2. 如果先改门禁，现有存量债务会让日常维护很痛苦
3. 先让人和 AI 都能判断“该放哪”，再搬内容，成本最低

## 8. 参考依据

- Diátaxis：文档应该按用户需求和文档类型组织，而不是把教程、操作、参考、解释混成一锅。
  来源：[Diátaxis Start Here](https://diataxis.fr/start-here/)
- Google Technical Writing：大文档和大文档集合都需要清晰层级、渐进披露和明确范围说明。
  来源：[Organizing large documents](https://developers.google.com/tech-writing/two/large-docs)
- Write the Docs：Docs as Code 强调文档和代码一样需要版本控制、评审和自动化，但这不代表稳定文档、过程文档、运行态文件可以混住。
  来源：[Docs as Code](https://www.writethedocs.org/guide/docs-as-code/)
- OpenAPI 学习站点：机器可读契约的价值在于自动生成、校验和避免文档漂移，因此机器契约应有稳定、清晰、可定位的目录。
  来源：[Learn OpenAPI Introduction](https://learn.openapis.org/introduction.html)
