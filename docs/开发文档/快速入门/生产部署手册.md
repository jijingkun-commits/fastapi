### 2.1 SQL 修正台忽略功能热修（2026-02-08）

若 SQL 修正台出现以下错误：

- 前端提示 `Failed to fetch`
- 后端日志出现 `column t_data_query_log.is_ignored does not exist`

请执行以下任一修复方案：

```bash
# 方案 A（推荐）：执行 Alembic 迁移
LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 alembic upgrade head

# 方案 B：执行增量 SQL
psql -d chat_db -f install/scripts/init_postgres.sql/024_add_query_log_ignore_flag.sql
```

执行后可通过以下 SQL 验证：

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 't_data_query_log' AND column_name = 'is_ignored';
```

## 三、离线环境部署（银行内网）

> 适用于无法访问外网的银行生产环境。

### 3.1 整体流程

```mermaid
flowchart LR
    subgraph Online [联网环境]
        A1[克隆代码] --> A2[安装依赖]
        A2 --> A3[构建前端]
        A3 --> A4[打包部署包]
    end
    
    subgraph Offline [离线环境]
        B1[传输部署包] --> B2[解压]
        B2 --> B3[配置环境变量]
        B3 --> B4[启动服务]
    end
    
    A4 --> B1
```

### 3.2 联网机器准备（一次性）

```bash
# 1. 克隆代码
git clone <repo-url> /tmp/deploy-prep
cd /tmp/deploy-prep

# 2. 后端依赖打包
pip download -r requirements.txt -d ./wheels
tar -czvf backend-wheels.tar.gz wheels requirements.txt

# 3. 前端依赖打包
cd web
rm -rf node_modules
npm ci                          # 安装所有依赖
npm run build                   # 构建生产包
tar -czvf frontend-deploy.tar.gz .next node_modules package.json next.config.ts public

# 4. 打包完整部署包
cd ..
tar -czvf full-deploy-$(date +%Y%m%d).tar.gz \
    app/ \
    install/ \
    scripts/ \
    config/ \
    deploy.sh \
    .env.example \
    requirements.txt \
    backend-wheels.tar.gz \
    web/frontend-deploy.tar.gz
```

### 3.3 离线机器部署

```bash
# 1. 传输并解压
scp full-deploy-*.tar.gz user@offline-server:/opt/
ssh user@offline-server
cd /opt && tar -xzvf full-deploy-*.tar.gz

# 2. 安装后端依赖（离线）
tar -xzvf backend-wheels.tar.gz
pip install --no-index --find-links=./wheels -r requirements.txt

# 3. 部署前端（无需 npm install）
cd web
tar -xzvf frontend-deploy.tar.gz
# node_modules 和 .next 已包含，可直接启动

# 4. 配置环境变量
cp .env.example .env.prod
vim .env.prod  # 修改数据库、MinIO 等配置

# 5. 初始化数据库
./deploy.sh prod migrate

# 6. 启动服务
./deploy.sh prod start

# 7. 启动前端
cd web && npm run start  # 生产模式，端口 3000
```

### 3.4 部署包清单

| 文件 | 大小约 | 说明 |
|------|--------|------|
| `backend-wheels.tar.gz` | ~200 MB | Python 依赖包（whl 格式） |
| `frontend-deploy.tar.gz` | ~300 MB | node_modules + .next 构建产物 |
| `app/` | ~5 MB | 后端代码 |
| `install/` | ~2 MB | SQL 迁移脚本 |

### 3.5 版本更新流程

**仅代码更新（无依赖变化）**：

```bash
# 联网机器
tar -czvf code-update-$(date +%Y%m%d).tar.gz app/ install/ scripts/

# 离线机器
tar -xzvf code-update-*.tar.gz
./deploy.sh prod restart
```

**包含依赖更新**：

重新执行完整的 3.2 和 3.3 流程。

### 3.6 注意事项

1. **Python 版本一致**：联网和离线机器的 Python 版本必须一致（推荐 3.11.x）
2. **Node.js 版本一致**：推荐 18.x LTS
3. **架构一致**：打包和部署机器的 CPU 架构需一致（x86_64 / arm64）
4. **依赖锁定**：必须保留 `package-lock.json` 和 `requirements.txt`，确保版本一致

## 七、技能系统

技能系统（Skills RAG）为 AI Agent 提供动态专业知识注入能力。

### 6.1 工作原理

1. **启动同步**：应用启动时自动扫描 `app/ai/skills/*/SKILL.md`，同步到 `t_agent_skills` 表
2. **向量检索**：对话时根据用户消息语义检索相关技能（top_k=2）
3. **上下文注入**：匹配的技能内容注入到 Agent 的 `skill_context` 中

### 6.2 目录结构

```
app/ai/skills/
├── knowledge-search/      # 知识库检索
│   └── SKILL.md
├── sql-expert/            # SQL 专家
│   └── SKILL.md
├── fastapi-expert/        # FastAPI 专家
│   └── SKILL.md
└── ...                    # 共 23 个技能
```

### 6.3 添加新技能

```bash
# 1. 创建目录
mkdir app/ai/skills/my-new-skill

# 2. 创建 SKILL.md（支持 YAML frontmatter）
cat > app/ai/skills/my-new-skill/SKILL.md << 'EOF'
---
name: My New Skill
description: 简短描述，用于向量检索匹配
---

# My New Skill

详细的技能指导内容...
EOF

# 3. 重启服务（自动同步）
./deploy.sh prod restart
```

### 6.4 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `skill_similarity_threshold` | 0.55 | 相似度阈值，低于此值不加载 |
| `top_k` | 2 | 每次对话最多加载的技能数 |

**调试日志**：技能检索会输出候选技能及相似度分数：

```
技能检索: 阈值=0.55, 候选=[sql-expert(0.72), knowledge-search(0.61)], 匹配=2个
```

### 6.5 管理接口

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/v1/skill-admin/skills` | GET | 获取所有技能 |
| `/api/v1/skill-admin/search` | GET | 技能检索测试 |
| `/api/v1/skill-admin/vector-status` | GET | 向量化状态 |
| `/api/v1/skill-admin/regenerate-embeddings` | POST | 重新生成所有向量 |

> **注意**：技能同步在应用启动时自动执行，无需手动触发。如需强制刷新向量，使用 `regenerate-embeddings` 接口。

## 八、RAGFlow 部署

RAGFlow 是可选的知识库检索服务，用于企业文档的语义搜索。

### 6.1 Docker 部署（推荐）

```bash
# 1. 克隆 RAGFlow
git clone https://github.com/infiniflow/ragflow.git
cd ragflow

# 2. 启动服务
docker compose -f docker-compose.yml up -d

# 3. 等待初始化（首次需要 10-15 分钟）
docker logs -f ragflow-server
```

**默认端口**:

| 服务 | 端口 | 说明 |
|------|------|------|
| RAGFlow Web | 9380 | 管理界面和 API |
| Elasticsearch | 9200 | 向量搜索后端 |
| MinIO | 9001 | 文档存储 |
| MySQL | 3306 | 元数据存储 |

### 6.2 配置知识库

1. **访问管理界面**: `http://ragflow-server:9380`

2. **创建 API Key**:
   - 进入 `设置` > `API 密钥`
   - 点击 `创建密钥`，复制生成的 Key

3. **创建知识库**:
   - 进入 `知识库` > `新建`
   - 配置名称、描述、Embedding 模型
   - 上传文档并等待解析完成

4. **获取知识库 ID**:
   - 在知识库列表中，点击知识库进入详情
   - URL 中的 ID 即为 `RAGFLOW_DATASET_IDS`
   - 多个知识库用逗号分隔

### 6.3 集成配置

在 `.env.prod` 中配置：

```bash
# RAGFlow 服务地址
RAGFLOW_BASE_URL=http://ragflow.prod:9380
RAGFLOW_API_URL=http://ragflow.prod:9380/api/v1

# API 密钥
RAGFLOW_API_KEY=ragflow-xxxxxxxxxxxxxxxx

# 知识库 ID（逗号分隔多个）
RAGFLOW_DATASET_IDS=477fe71b0cab11f19b77cb24f29cf9fe

# 检索参数
RAGFLOW_SIMILARITY_THRESHOLD=0.2  # 相似度阈值（0-1）
RAGFLOW_TOP_K=5                   # 返回结果数量
RAGFLOW_VECTOR_WEIGHT=0.6         # 向量权重（混合检索）
```

### 6.4 验证集成

```bash
# 测试 RAGFlow API 连通性
curl -X POST "$RAGFLOW_API_URL/retrieval" \
  -H "Authorization: Bearer $RAGFLOW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "dataset_ids": ["'$RAGFLOW_DATASET_IDS'"],
    "question": "测试查询",
    "top_n": 3
  }'

# 预期返回：包含检索结果的 JSON
```

### 6.5 图片代理说明

RAGFlow 知识库中的图片通过本系统代理访问：

| 原始路径 | 代理路径 |
|----------|----------|
| RAGFlow 内部图片 ID | `/api/v1/assets/proxy/ragflow/{image_id}` |

代理由后端自动处理，前端无需关心 RAGFlow 的直接访问。

### 6.6 常见问题

**RAGFlow 连接超时**:

```bash
# 检查服务状态
docker ps | grep ragflow

# 检查网络连通性
curl -v $RAGFLOW_BASE_URL/api/v1/health
```

**检索结果为空**:

1. 确认知识库中有已解析的文档
2. 检查 `RAGFLOW_DATASET_IDS` 是否正确
3. 降低 `RAGFLOW_SIMILARITY_THRESHOLD` 阈值

**图片无法显示**:

1. 确认图片代理端点正常：`curl localhost:8000/api/v1/assets/proxy/ragflow/{image_id}`
2. 检查 `RAGFLOW_BASE_URL` 配置是否正确

## 十一、数据分析模块部署

数据分析模块（问数功能）需要额外的业务数据库配置和指标数据导入。

### 9.1 数据库准备

#### 创建数据分析数据库

```bash
# 创建 data_db 数据库
psql -U postgres -c "CREATE DATABASE data_db;"

# 创建 schema
psql -U postgres -d data_db -f install/data_import/01_create_fdmdata_schema.sql
psql -U postgres -d data_db -f install/data_import/02_create_sdmdata_schema.sql
```

#### 创建业务表

```bash
# 创建核心业务表（按覆盖度优先级排序）
psql -U postgres -d data_db -f install/data_import/03_create_business_tables.sql
```

DDL 脚本包含 **69 张业务表**，按覆盖度优先级排序。主要表分类：

**核心指标表（fdmdata schema）**：
- `f_mid_index_result` - 指标结果表（解锁最多指标）
- `f_mid_index_result_derive` - 派生指标结果表
- `f_mid_index_result_dim` - 维度指标结果表
- `f_mid_index_result_dim_derive` - 维度派生指标表
- `f_mid_org_tree_k` - 机构树快照表
- `f_mid_loan_k_tb` / `f_mid_dep_k_tb` - 贷款/存款快照表

**业务基础表（sdmdata schema）**：
- `s_ods_g_b_cif_*` - 客户信息系列表
- `s_ods_g_b_ln_*` - 贷款业务系列表
- `s_ods_g_b_dep_*` - 存款业务系列表
- `s_ods_g_b_org_*` - 机构信息系列表
- `s_rrs_rd_*` - 监管报表系列表

完整表清单见 `03_create_business_tables.sql` 文件注释。

### 9.2 指标数据导入

#### 准备数据文件

确保以下数据文件存在于 `data/` 目录：

| 文件 | 说明 | 来源 |
|------|------|------|
| `dmp_show_ind_info_*.txt` | 指标元数据 | DIDP 导出 |
| `DIDP_PROJECT_WORKSPACE/` | SQL 模板和表结构 | DIDP 项目工作空间 |

#### 导入指标元数据

```bash
# 导入指标定义（约 2,600+ 条）
python install/data_import/04_import_metrics.py

# 关联指标 SQL 模板（约 1,500+ 条）
python install/data_import/05_link_metric_sql.py
```

#### 导入表元数据（提升问数准确率）

```bash
# 导入表/字段元数据到 t_meta_tables 和 t_meta_columns
python install/data_import/07_import_table_metadata.py

# 生成表元数据的 embedding 向量
python install/data_import/07_import_table_metadata.py --generate-embeddings
```

#### 生成指标 Embedding（必选，启用指标语义匹配）

```bash
# 为 t_metric_definition 表生成 embedding 向量
python install/data_import/08_generate_metric_embeddings.py
```

> **重要**：此步骤必须执行，否则指标语义匹配功能无法工作。
> 
> 向量检索用于三条并行检索分支：
> - **DDL 检索**：基于 `t_meta_tables` 的 embedding 匹配相关表
> - **指标检索**：基于 `t_metric_definition` 的 embedding 匹配业务指标
> - **历史问答**：基于 `t_data_query_log` 的 embedding 检索训练过的问答

### 9.4 训练数据管理

问数功能支持**持续学习**，通过用户反馈和人工修正不断优化 SQL 生成质量。

#### 自动向量化（推荐）

正常使用问数功能时，系统会自动：
1. 记录每次查询到 `t_data_query_log`
2. 自动生成 `question_embedding`（在记录时完成）
3. 管理员标记 `trained=true` 后即可被检索

#### 批量导入训练数据

如需批量导入历史训练数据：

```bash
# 1. 先通过 SQL 导入数据（question, generated_sql, is_correct=true）
# 2. 生成 embedding
python install/data_import/09_generate_training_embeddings.py

# 3. 标记为已训练
UPDATE t_data_query_log SET trained = true WHERE is_correct = true;
```

#### 训练 API

通过管理 API 进行训练操作：

```bash
# 训练指定日志
POST /api/v1/data-admin/train
{"log_ids": [1, 2, 3]}

# 训练所有待训练日志
POST /api/v1/data-admin/train/all-pending
```

### 9.5 数据同步

业务表创建后需要从生产数据仓库同步数据：

```bash
# 示例：使用 pg_dump/pg_restore 同步单表
pg_dump -h source_host -U user -t fdmdata.f_mid_index_result data_db | \
  psql -h target_host -U user data_db

# 或使用 ETL 工具定期同步
```

### 9.5 常见问题

**指标查询返回空**:

1. 检查业务表是否有数据
2. 确认日期参数格式正确（如 `2025-06-30`）
3. 验证指标 SQL 模板是否正确

**覆盖率低于预期**:

1. 确认所有业务表已创建
2. 运行 `06_verify_coverage.py` 查看缺失的表
3. 根据提示创建缺失的表
