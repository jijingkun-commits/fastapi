# 流式通信与状态同步设计

> [!NOTE]
> 本文档详细阐述了 Chat 系统中 `stream_mode="custom"` 的设计哲学、双写架构（Dual Write）以及协议实现细节。

---

## 🚀 为什么选择 Custom Mode？

在构建复杂 Agentic 应用（如待办助手、多智能体协作）时，LangGraph 默认提供的流式模式存在局限性：

1.  **`values` / `messages` 模式**: 暴露了 Graph 的内部状态（State）。前端如果要根据 State 变化来渲染 UI，需要处理大量复杂的业务逻辑（如：如何从 Message List 中提取出最新的 ToolCall？如何判断当前是 Thinking 还是 Generating？）。
2.  **UI 与 State 的不匹配**: 用户界面往往需要比 State 更丰富的信息（如："正在分析图片..."的状态提示，或者结构化的待办确认卡片），而这些信息并不适合持久化在 State 中。

因此，我们采用了 **Custom Mode**，本质上是一种 **BFF (Backend for Frontend)** 模式：

*   **State**: 关注逻辑正确性、历史回溯、断点续传。
*   **Custom Stream**: 关注用户体验、UI 渲染、实时反馈。

---

## 🏗️ 核心架构：CQRS 与双写模式

用户可能会发现：**即使使用了 Custom Mode，数据依然被写入了 LangGraph 的 State 中。**

这是一个特意为之的设计，采用了 **CQRS (Command Query Responsibility Segregation)** 和 **Dual Write** 的思想：

| 组件 | 角色 | 职责 | 持久性 |
| :--- | :--- | :--- | :--- |
| **Graph State** | **Source of Truth (里)** | 保存对话历史、上下文、Checkpoint。保证系统可恢复、可回溯。 | **持久化** (SQLite/MySQL) |
| **Custom Stream** | **View Projection (表)** | 生成面向用户的实时反馈。负责驱动 UI 渲染（Token、卡片、Loading）。 | **瞬时** (SSE 通道) |

### 双写流程示例 (`execute_operation`)

以待办事项执行节点为例：

```python
def execute_operation(state: TodoAgentState) -> TodoAgentState:
    writer = get_stream_writer()
    
    # ... 执行业务逻辑 ...
    result = create_todo(...)
    
    # 动作 1 (Write to View): 通过 Custom 通道发送给前端渲染
    # 目的：让用户立刻看到炫酷的成功卡片，提升交互体验
    emit_result(writer, "todo_list", {"todos": [result]}, message="创建成功")

    # 动作 2 (Write to State): 更新 Graph State
    # 目的：将操作结果存入历史，确保用户刷新页面或后续对话时，Agent 知道这事儿已经办完了
    state["messages"].append(AIMessage(
        content="创建成功",
        additional_kwargs={"data": result}
    ))
            
    return state
```

> [!IMPORTANT]
> **只写 Custom Stream**: 刷新页面后消息丢失。
> **只写 State**: 流式响应中前端收不到数据，界面卡顿。
> **双写**: 既保证了实时交互体验，又保证了数据的一致性和持久性。

## 📡 协议实现：三层架构

为了规范节点与前端的通信，我们设计了严格的三层架构：

### 1. 协议定义层 (`app/ai/events.py`)

定义了强类型的 `EventType` 和封装好的 `emit_*` 函数。禁止在节点中直接编写裸字典，必须使用 Helper 函数。

```python
# 强制规范数据格式，防止字段拼写错误
def emit_token(writer, content): ...
def emit_result(writer, data_type, data): ...
def emit_confirmation(writer, operation): ...
```

### 2. 生产者层 (Graph Nodes)

Graph 中的节点（如 `TodoGraph`, `MultiAgentGraph`）充当生产者。

*   **注入依赖**: 通过 `get_stream_writer()` 获取当前协程的写入器。
*   **语义化发送**: 节点清楚地知道自己处于什么阶段（Thinking, Tool Calling, Clarifying），并主动推送对应事件。

### 3. 消费者层 (`ChatService`)

`app/services/chat_service.py` 是连接 Graph 和 HTTP SSE 的桥梁。

```python
# 统一监听 stream_mode="custom"
async for chunk in graph.astream(..., stream_mode="custom"):
    event_type = chunk.get("type")
    
    # 1. 转发给前端 (SSE)
    yield format_sse(event_type, chunk.get("data"))
    
    # 2. 收集 Token (Side Effect)
    # 虽然 State 已经双写了，但对于纯文本流（Token），
    # Service 层通常会额外收集一份用于最终兜底或日志记录
    if event_type == "token":
        full_answer.append(chunk.get("data").get("content"))
```

## 🔄 复杂交互场景：Interrupt 与 Resume

在 Human-in-the-loop 场景（如删除待办确认）中，Custom Mode 发挥了关键作用。

### 1. 发起确认 (`ask_confirmation`)

节点通过 Custom Event 发送结构化数据给前端，要求渲染确认卡片：

```python
# 发送 Confirmation Card 数据
emit_confirmation(writer, {
    "action": "delete",
    "todo_id": 123,
    "title": "重要会议"
}, "确认删除吗？")
```

此时，Graph 进入 `wait_for_confirmation` 节点并触发 `interrupt`，挂起执行。

### 2. 恢复执行 (`resume`)

前端用户点击“确认”后，调用 `/chat/resume` 接口。

```python
# Resume 请求携带用户决策数据
decision = {"type": "accept", "confirmed": True}

# 恢复 Graph 执行
async for chunk in graph.astream(Command(resume=decision), ...):
    # 继续产生新的 Custom Event
    ...
```

`wait_for_confirmation` 节点苏醒，接收到 `decision`，更新 `State` 中的 `user_confirmed` 字段，流转到 `execute_operation` 节点。

## 📊 对比总结

| 特性 | Standard Checkpoint 模式 | Custom Event 模式 (当前架构) |
| :--- | :--- | :--- |
| **数据源** | State 快照 | 主动 Emit 的事件 |
| **控制力** | 低，难以控制可见性 | 高，只发送想让用户看到的 |
| **UI 复杂度** | 低，仅文本流 | 高，支持复杂 JSON 组件 |
| **前端开发** | 需解析复杂的 Graph State | 仅需处理标准化的事件列表 |
| **状态回溯** | 完美支持 | 依赖双写机制支持 |
