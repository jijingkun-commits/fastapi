# 流式通信与状态同步设计

> [!NOTE]
> 本文档详细阐述了 Chat 系统中 `stream_mode="custom"` 的设计哲学、双写架构（Dual Write）以及协议实现细节。

> [!IMPORTANT]
> 事件类型清单、字段定义与 `done` 约束请以 `docs/开发文档/代码解读/SSE事件协议.md` 为权威来源。

## 🚀 为什么选择 Custom Mode？

在构建复杂 Agentic 应用（如待办助手、多智能体协作）时，LangGraph 默认提供的流式模式存在局限性：

1.  **`values` / `messages` 模式**: 暴露了 Graph 的内部状态（State）。前端如果要根据 State 变化来渲染 UI，需要处理大量复杂的业务逻辑（如：如何从 Message List 中提取出最新的 ToolCall？如何判断当前是 Thinking 还是 Generating？）。
2.  **UI 与 State 的不匹配**: 用户界面往往需要比 State 更丰富的信息（如："正在分析图片..."的状态提示，或者结构化的待办确认卡片），而这些信息并不适合持久化在 State 中。

因此，我们采用了 **Custom Mode**，本质上是一种 **BFF (Backend for Frontend)** 模式：

*   **State**: 关注逻辑正确性、历史回溯、断点续传。
*   **Custom Stream**: 关注用户体验、UI 渲染、实时反馈。

---

## 🏗️ 核心架构：CQRS 与双写模式

用户可能会发现：**即使使用了 Custom Mode，数据依然被写入了 LangGraph 的 State 中。**

这是一个特意为之的设计，采用了 **CQRS (Command Query Responsibility Segregation)** 和 **Dual Write** 的思想：

| 组件 | 角色 | 职责 | 持久性 |
| :--- | :--- | :--- | :--- |
| **Graph State** | **Source of Truth (里)** | 保存对话历史、上下文、Checkpoint。保证系统可恢复、可回溯。 | **持久化** (PostgreSQL) |
| **Custom Stream** | **View Projection (表)** | 生成面向用户的实时反馈。负责驱动 UI 渲染（Token、卡片、Loading）。 | **瞬时** (SSE 通道) |

### 双写流程示例 (`execute_operation`)

以待办事项执行节点为例：

```python
def execute_operation(state: TodoAgentState) -> TodoAgentState:
    writer = get_stream_writer()
    
    # ... 执行业务逻辑 ...
    result = create_todo(...)
    
    # 动作 1 (Write to View): 通过 Custom 通道发送给前端渲染
    # 目的：让用户立刻看到炫酷的成功卡片，提升交互体验
    emit_result(writer, "todo_list", {"todos": [result]}, message="创建成功")

    # 动作 2 (Write to State): 更新 Graph State
    # 目的：将操作结果存入历史，确保用户刷新页面或后续对话时，Agent 知道这事儿已经办完了
    state["messages"].append(AIMessage(
        content="创建成功",
        additional_kwargs={"data": result}
    ))
            
    return state
```

> [!IMPORTANT]
> **只写 Custom Stream**: 刷新页面后消息丢失。
> **只写 State**: 流式响应中前端收不到数据，界面卡顿。
> **双写**: 既保证了实时交互体验，又保证了数据的一致性和持久性。

## 📡 协议实现：三层架构

为了规范节点与前端的通信，我们设计了严格的三层架构：

### 1. 协议定义层 (`app/ai/events.py`)

定义了强类型的 `EventType` 和封装好的 `emit_*` 函数。禁止在节点中直接编写裸字典，必须使用 Helper 函数。

```python
# 强制规范数据格式，防止字段拼写错误
def emit_token(writer, content): ...
def emit_result(writer, data_type, data): ...
def emit_confirmation(writer, operation): ...
```

### 2. 生产者层 (Graph Nodes)

Graph 中的节点（如 `TodoGraph`, `MultiAgentGraph`）充当生产者。

*   **注入依赖**: 通过 `get_stream_writer()` 获取当前协程的写入器。
*   **语义化发送**: 节点清楚地知道自己处于什么阶段（Thinking, Tool Calling, Clarifying），并主动推送对应事件。

### 3. 消费者层 (`ChatService`)

`app/services/chat_service.py` 是连接 Graph 和 HTTP SSE 的桥梁。

```python
# 统一监听 stream_mode="custom"
async for chunk in graph.astream(..., stream_mode="custom"):
    event_type = chunk.get("type")
    
    # 1. 转发给前端 (SSE)
    yield format_sse(event_type, chunk.get("data"))
    
    # 2. 收集 Token (Side Effect)
    # 虽然 State 已经双写了，但对于纯文本流（Token），
    # Service 层通常会额外收集一份用于最终兜底或日志记录
    if event_type == "token":
        full_answer.append(chunk.get("data").get("content"))
```

## 🔄 复杂交互场景：Interrupt 与 Resume

在 Human-in-the-loop 场景（如删除待办确认）中，Custom Mode 发挥了关键作用。

### 1. 发起确认 (`ask_confirmation`)

节点通过 Custom Event 发送结构化数据给前端，要求渲染确认卡片：

```python
# 发送 Confirmation Card 数据
emit_confirmation(writer, {
    "action": "delete",
    "todo_id": 123,
    "title": "重要会议"
}, "确认删除吗？")
```

此时，Graph 进入 `wait_for_confirmation` 节点并触发 `interrupt`，挂起执行。

### 2. 恢复执行 (`resume`)

前端用户点击“确认”后，调用 `/chat/resume` 接口。

```python
# Resume 请求携带用户决策数据
decision = {"type": "accept", "confirmed": True}

# 恢复 Graph 执行
async for chunk in graph.astream(Command(resume=decision), ...):
    # 继续产生新的 Custom Event
    ...
```

`wait_for_confirmation` 节点苏醒，接收到 `decision`，更新 `State` 中的 `user_confirmed` 字段，流转到 `execute_operation` 节点。

### 3. 消息去重机制：`is_intermediate` 标记

在 Interrupt 场景中，消息可能被保存两次：
1. **Interrupt 时**：`ChatService` 保存当前 AI 回复（如"确认创建待办吗？"）
2. **Resume 后**：`postprocess` 节点保存最终 AI 回复

为避免重复显示，采用 `is_intermediate` 标记机制：

```python
# chat_service.py: Interrupt 时标记为中间消息
self._save_conversation_fallback(
    thread_id=thread_id,
    ai_content=ai_content,
    is_intermediate=True,  # 历史加载时会被排除
    scenario="Interrupt",
)

# chat_repo.py: 历史加载时排除中间消息
if exclude_intermediate:
    query = query.filter(
        ~is_intermediate_value.in_(["true", "True"])
    )
```

### 4. 拒绝操作的消息生成

当用户拒绝操作时，`execute_operation` 需要生成明确的取消消息，避免 postprocess 保存与 interrupt 相同的内容：

```python
# todo_graph.py: 用户拒绝时生成取消确认消息
if user_confirmed is False:
    updates["messages"] = [AIMessage(content="好的，已取消操作。有其他需要帮助的吗？")]
    return updates
```

这确保了：
- Interrupt 消息（标记 `is_intermediate=true`）在历史加载时被排除
- 最终保存的是取消确认消息，而非重复的确认提示

## 🔒 数据同步保障机制

为确保前端展示与数据库保存的一致性，系统实现了多层保障机制：

### 1. 同步追踪日志 (`[SYNC-TRACE]`)

在流式输出、数据库保存、历史加载三个关键环节添加了统一格式的追踪日志：

```python
# 流式输出完成时
logger.info("[SYNC-TRACE] 流式输出完成: thread_id=%s, content_len=%d, content_hash=%s, additional_kwargs_keys=%s")

# 数据库保存时
logger.info("[SYNC-TRACE] 数据库保存完成: thread_id=%s, ai_len=%d, ai_hash=%s, extra_data_keys=%s")

# 历史加载时
logger.info("[SYNC-TRACE] 历史加载: thread_id=%s, msg_id=%d, ai_len=%d, ai_hash=%s, extra_data_keys=%s")
```

通过对比三处日志的 `content_hash`，可快速定位数据不一致的环节。

### 2. 结构化数据单通道机制（`result`）

2026-02 协议切换后，结构化数据只通过 `result` 事件传递；`done` 仅用于生命周期收口与消息 ID 绑定。

```python
# ChatService：result 事件直接转发给前端
elif event_type == "result":
    if event_data.get("message"):
        full_answer.append(event_data["message"])
    yield self._format_sse("result", event_data)

# done 仅承载生命周期字段
done_payload = {"thread_id": thread_id}
done_payload["message_id"] = last_saved.id
yield self._format_sse("done", done_payload)
```

```typescript
// 前端在 result 阶段保存结构化数据
onResult: (data) => {
  message.additional_kwargs = {
    data_type: data.data_type,
    data: data.data,
  };
}

// done 仅用于收口与绑定消息 ID
onDone: (threadId, messageId) => {
  bindMessageId(aiId, messageId);
}
```

### 3. 基于 Hash 的去重机制

使用内容的 MD5 短 hash（8位）进行去重，避免空格、换行等微小差异导致重复保存：

```python
def _content_hash(content: str) -> str:
    """计算内容的短 hash，用于日志对比和去重。"""
    if not content:
        return "empty"
    normalized = content.strip()
    return hashlib.md5(normalized.encode()).hexdigest()[:8]

# 去重检查改为基于 hash 匹配
for msg in recent_messages:
    if _content_hash(msg.content or "") == content_hash:
        # 消息已存在，跳过保存
        break
```

### 4. Thinking 内容统一处理

确保思考内容在保存和加载时格式一致：

```python
# 保存时：如果 ai_content 中没有 <think> 标签但有 thinking 内容，将其包装后添加
if thinking and "<think>" not in ai_content:
    ai_content = f"<think>\n{thinking}\n</think>\n\n{ai_content}"

# 加载时：前端从 <think> 标签中提取思考内容
const { content, thinking } = extractThinkingContent(rawContent);
```

### 5. extra_data 更新机制

当消息内容 hash 匹配但 `extra_data` 不同时，会更新已存在消息的 `extra_data`，确保结构化数据不丢失：

```python
if existing_ai and extra_data and existing_ai.extra_data != extra_data:
    existing_ai.extra_data = extra_data
    db.commit()
```

## 📊 对比总结

| 特性 | Standard Checkpoint 模式 | Custom Event 模式 (当前架构) |
| :--- | :--- | :--- |
| **数据源** | State 快照 | 主动 Emit 的事件 |
| **控制力** | 低，难以控制可见性 | 高，只发送想让用户看到的 |
| **UI 复杂度** | 低，仅文本流 | 高，支持复杂 JSON 组件 |
| **前端开发** | 需解析复杂的 Graph State | 仅需处理标准化的事件列表 |
| **状态回溯** | 完美支持 | 依赖双写机制支持 |
| **数据一致性** | 自动保证 | 依赖同步追踪 + 去重机制 |
