# Bugfix 最小变更规范

## 目标

在缺陷修复场景中，优先消除根因并控制改动规模，避免通过叠加代码掩盖问题，降低回归风险和长期维护成本。

## 适用范围

- 适用于所有以修复缺陷为目标的任务（本地修复、热修复、线上缺陷修复）。
- 不适用于明确标记为架构重构或功能迭代的任务；此类任务应单独建卡并拆分 PR。

## 执行流程（强制）

1. 根因定位（禁止直接改代码）
   - 输出复现路径、影响范围、根因结论。
   - 明确“为什么不是其他候选根因”。
2. 失败测试先行
   - 先新增或补充能稳定复现问题的失败测试，再进行实现修复。
   - 若无法补测试，必须在 PR 中写明原因和替代验证方案。
3. 最小实现修复
   - 仅在根因所在层级改动，不跨层堆叠策略。
   - 禁止为“可能复用”提前引入抽象层或新基建。
4. 减法审查
   - 提交前必须回答“本次改动可删除什么”。
   - 优先选择可读性更高、变更面更小的等价实现。

## 变更预算（默认）

| 指标 | 默认上限 | 说明 |
| --- | --- | --- |
| 修改代码文件数 | 3 | 默认仅统计非文档类文件 |
| 净新增行数（added - deleted） | 80 | 防止“越修越胖” |
| 总新增行数（added） | 140 | 防止大量增删互抵掩盖复杂度 |

超出预算时，必须满足以下全部条件：

1. 在 PR 中明确超预算原因与不可拆分依据。
2. 提供拆分方案（至少说明可拆分边界和后续计划）。
3. 经评审明确同意后再合并。

## PR 必填项

每个 bugfix PR 必须包含：

- 复现步骤（修复前）。
- 根因说明（现象与根因分离）。
- 最小修复点说明（为什么只改这些文件）。
- 变更预算结果（文件数、净新增、总新增）。
- 回归验证证据（测试命令与结果摘要）。

## 本地与 CI 门禁

- 本地提交前执行：
  - `python3 scripts/ci/check_bugfix_budget.py --cached --strict`
- CI 在 PR 中自动执行：
  - `.github/workflows/bugfix-guard.yml`

## 度量与复盘建议

每周至少复盘一次以下指标：

- Bugfix 平均修改文件数。
- Bugfix 平均净新增行数。
- 修复后 7 天内同类问题回归率。
- “超预算 PR”占比与成因分布。
