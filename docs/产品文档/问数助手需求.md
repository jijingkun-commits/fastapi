## 1. 目标与边界

### 1.1 目标

1. 支持贷款/存款/分行维度等银行核心分析场景。
2. 支持多轮补充（时间、维度、筛选）而不丢失上下文。
3. 支持结果增强规则（lookup）与后台可配置治理。
4. 严格执行数据权限与双数据库隔离策略。

### 1.2 非目标

1. 不在本模块内处理通用聊天 UI 交互。
2. 不在本模块内实现前端渲染组件细节。
3. 不在本模块内承载待办业务语义。

---

## 2. 典型用户故事

1. **分行经营分析师**：我想查“本月贷款余额按分行 Top10”，然后补充“只看对公客户”。
2. **管理层秘书**：我想把“贷款余额”切换成“存款余额”，沿用上一轮维度和时间。
3. **合规审核员**：我希望系统自动拒绝敏感表与系统 schema 访问。
4. **数据管理员**：我希望通过后台配置结果增强规则，让结果自动补齐客户名称。

---

## 3. 功能需求

### 3.1 会话意图与上下文

1. 必须支持回合行为分类（`NEW_QUERY/SUPPLEMENT/CORRECTION/CONFIRM`）。
2. 必须支持会话帧归并（`current > handoff > state > default`）与来源映射。
3. 补充轮应优先复用上轮已确认的指标、时间、维度。
4. `data.query` 的 `query_shape/ranking`（如 TopN limit、排序方向）必须作为结构化 contract 贯穿 `handoff -> session_frame/query_context -> SQL 生成`，不得只靠重建自然语言摘要再二次猜测。
5. 库表元数据问句（如“数据库有几张表”“有哪些字段”）应直达 schema 查询路径，不得追问指标和时间范围。

### 3.2 SQL 生成与执行

1. 支持总量、维度、TopN 三类查询形态。
2. TopN/排名查询必须同时满足结构化排序合同与执行 SQL 的 `ORDER BY + LIMIT`，不得被会话摘要重写后退化为普通分组查询。
3. 支持 schema 路由与 SQL 安全校验。
4. 结果为空时支持空结果恢复重写策略。
4. 流式问数响应必须同轮返回 `data_type='sql_result'` 结构化事件，前端无需刷新历史消息即可渲染结果表。
5. `sql_result.data` 至少包含 `rows`、`columns`、`total_rows`、`sql` 字段，避免前端在流式阶段缺字段崩溃。
6. 结果解释文案需与展示行数一致：仅当 `total_rows > display_limit` 时展示“已展示前 N 条”。

### 3.3 结果增强（Result Enrichment）

1. 规则模型需支持：`rule_code`、优先级、启停、来源表与字段映射。
2. 后台提供规则列表、新增、更新、启停、优先级调整、规则测试、缓存刷新。
3. 规则执行顺序由优先级决定，需具备审计记录。

### 3.4 权限与合规

1. 分析查询默认走 `ANALYTICS_DATABASE_URL` 对应链路。
2. 系统表、敏感表、系统 schema 必须拦截。
3. 允许有限元数据视图（`information_schema.tables/columns/...`）只读访问。
4. 访问控制配置键主写统一为 `askdata.*`，历史 `data_access.*` 仅兼容读取。
5. 权限判定采用双角色模型：`sys_role` 仅用于系统管理鉴权，问数权限统一使用 `data_role`。
6. 默认行级策略固定为 `dept_code = user.dept_code`，`sys_role=admin` 不得绕过该策略。
7. 用户缺失 `dept_code` 时必须拒绝查询，并返回可解释拒绝原因。
8. SQL 决策顺序必须遵循 `deny > allow > role_template > default`。

### 3.5 权限治理与可观测

1. 管理后台需提供 `data_role` 策略模板治理能力，支持按角色全量更新表级/行级/列级规则。
2. 管理后台需提供 SQL 试跑能力，输出原 SQL、重写 SQL、拒绝阶段、拒绝原因与策略命中轨迹。
3. 策略更新后需清理本地缓存，保障配置变更快速生效。
4. 审计日志需记录 `user_id`、`data_role`、命中规则类型与拒绝阶段，支持问题追溯。

## 4. 共享能力引用（单一真理来源）

1. **会话意图内核**：以 `session_intent_kernel.py` 为统一语义来源。
2. **SSE 协议**：事件名和 payload 以聊天系统协议为准，不在问数模块发明新事件规范。
3. **模型路由**：SQL 生成与轻量任务模型走统一路由配置键。
4. **技能检索能力**：问数场景复用技能系统自动触发与注入能力，能力定义以 `docs/产品文档/技能系统需求.md` 为准。

## 5. 验收标准

### 5.1 Happy Path

1. “贷款余额 → 分行维度 → Top10 → 图表切换”多轮链路可收敛。
2. 单条 SQL 结果（如权限过滤后仅剩 1 个机构）默认不渲染柱状图，保留结果文本与表格展示。
3. 用户补充条件后，系统不丢失已有上下文。
4. 结果增强规则生效后，可见补齐字段。

### 5.2 边界与异常

1. 非法 SQL/越权表访问时返回明确错误。
2. schema 路由失败时可回退默认 schema，并保留日志。
3. 空结果场景可触发重写或给出可解释提示。
4. `dept_code` 缺失时问数请求必须被拒绝，不得降级为全量查询。
5. `sys_role=admin` 且 `data_role=staff` 时，权限结果应与普通 `staff` 一致。
6. 用户提问库表元数据时，即使模型返回澄清建议，也不得回退为“请补充指标和时间范围”。

### 5.3 稳定性

1. 同一会话连续追问不应出现意图震荡。
2. 结果增强规则异常时应降级而非阻断主链路。

## 6. 非功能需求

1. **性能**：关键查询链路支持超时保护与重试策略。
2. **可观测**：保留 thread_id、turn_act、schema 选择、规则命中日志。
3. **一致性**：指标语义、字段命名、返回结构在多轮中稳定。

## 9. 单目标强数据语义与补充回合约束

### 9.1 需求描述

1. 对“贷款/存款/余额/金额/数量/分布”等明确银行问数语义的单目标请求，运行态目标不得退化为 `general.reply`。
2. planner 模型主判定仍为首选，但当模型给出过宽泛的通用目标时，规则层必须在单目标强语义场景执行纠偏。
3. 同线程补充回合若仅追加图表、维度、时间或筛选条件，且上一轮已形成 `data.query` 上下文，则活动目标必须继承为 `data.query`，不得降级成 `general.reply`。
4. 问数链路的失败收口应返回结果性提示，不得把内部补齐状态转译成“请回复继续”。

### 9.2 验收标准

1. 输入“查询 2025 年 6 月 30 日各机构的贷款余额分布”等强数据语义单目标问题时，活动目标为 `data.query`。
2. 在同一线程先完成 TopN 问数，再输入“以柱状图方式展示”等补充诉求时，活动目标仍为 `data.query`，并继承上一轮指标/时间上下文。
3. 当 supervisor 产生 `data_expert` 委派但 `frame.query_text` 缺失时，编排层必须基于已有 `frame`、`task_description` 或当前轮用户问句编译 canonical `frame.query_text` 后再进入 router guard，禁止继续放行 `frame=null` 的 data handoff。
4. 数据结果缺失时，系统允许返回稍后重试提示，但不再显示“问题回复”“继续补齐”等内部兜底语义。
5. 该纠偏不应把“查询一下待办清单”之类待办问句误扩为 `data.query`，也不应把“好的”等确认短句误扩为 `data.query`。
