## 1. 目标与边界

### 1.1 目标

1. 在自然语言对话中完成待办创建、更新、完成、删除。
2. 支持隐式指代（这个/上一个/那个任务）与多轮补充。
3. 支持澄清、确认、执行三段式闭环，避免重复确认循环。

### 1.2 非目标

1. 不承载问数 SQL 语义与数据分析能力。
2. 不承载系统级用户权限管理策略。

---

## 2. 典型用户故事

1. **客户经理**：我说“把这个任务改到明天下午”，系统应识别 `current_todo_id` 并给出确认卡片。
2. **支行主管**：我说“把上一个任务标记完成”，系统应基于上下文准确定位目标任务。
3. **运营专员**：我说“帮我补充这条待办的描述和优先级”，系统应进入补充轮而不是重复创建。

---

## 3. 功能需求

### 3.1 意图识别与状态机

1. 必须支持 `NEW_QUERY/SUPPLEMENT/CORRECTION/CONFIRM` 四类行为识别。
2. 必须维护 `pending_operation` 并在确认后执行。
3. 必须维护澄清状态字段（`clarify_fsm_state/clarify_round`）以避免死循环。

### 3.2 隐式指代链路

1. 前端发送消息时携带 `current_todo_id`（如有）。
2. 后端需将 `current_todo_id` 注入 workflow state 并优先用于目标定位。
3. 请求发起后才可清理前端选中态，防止 ID 丢失。

### 3.3 确认卡片与交互

1. 对 create/update/delete/complete 操作输出结构化确认数据。
2. 前端确认卡片的数据类型必须与后端 payload 对齐。
3. 用户确认/拒绝/编辑后，可通过 resume 链路继续执行。

### 3.4 取消后补充恢复（新增）

1. 创建待办进入确认卡片后，若用户先执行拒绝，再发送补充信息（如时间/同行人/地点），系统应优先判定为“恢复同一创建草稿”，而非转为 update 并要求待办 ID。
2. 恢复创建仅在以下条件同时满足时生效：
   - 当前轮为补充语义（`SUPPLEMENT`）
   - Handoff 上下文明确指向创建（`create`）
   - 当前无 `todo_id` 锚点
3. 恢复后应重新进入 `need_confirm`，并展示合并后的确认摘要。

### 3.5 Supervisor 工具信息补全（新增）

1. 当用户已选中待办（`current_todo_id`）并提出“补充天气/股价/汇率”等信息时，系统应识别为待办更新场景，而非超范围请求。
2. Supervisor 可先调用其可用工具（如联网搜索）获取信息摘要，再将摘要通过结构化 handoff 传给待办专家。
3. 待办专家需将来自 Supervisor 的工具摘要并入 `description` 或 `progress_notes`，并进入确认流程。
4. 外部工具失败时，应返回可解释降级提示（如“外部信息暂不可用”），但不应中断待办更新链路。
5. 当不存在待办上下文时，天气/股价等请求仍按 Supervisor 通用问答处理，不强制进入待办流程。

## 4. 共享能力引用（单一真理来源）

1. **会话意图内核**：待办与问数共享 turn_act 与 frame 合并逻辑。
2. **SSE 协议**：确认、澄清、interrupt、done 事件按统一协议消费。
3. **模型路由**：待办中的轻量意图提取遵循统一路由配置。

---

## 5. 验收标准

### 5.1 Happy Path

1. 用户在同一线程中完成：创建 → 补充 → 确认 → 执行。
2. 隐式指代补充轮能够命中正确待办目标。
3. 中断后 resume 不重复创建消息，不丢失状态。

### 5.2 边界与异常

1. 当缺失关键槽位（标题/时间）时，进入澄清而非直接执行。
2. 取消操作后状态清理正确，不污染下一轮。
3. 无效目标 ID 时返回可解释错误。
4. 拒绝后若用户明确“彻底取消”或切换到新话题，不得恢复旧创建草稿。
5. 在“已选中待办 + 外部信息补充”场景下，不得返回“当前请求不属于待办管理”。

### 5.3 稳定性

1. 连续多轮操作不应进入重复澄清循环。
2. 触发 interrupt 时，前端状态切换为等待确认并可恢复。

---

## 6. 非功能需求

1. **可观测性**：记录 `pending_operation` 生命周期与状态迁移日志。
2. **一致性**：同一线程内目标任务 ID 解析保持一致。
3. **可维护性**：确认卡片类型收敛，不使用危险断言绕过类型系统。
