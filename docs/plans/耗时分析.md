# AI 回答响应时间深度分析报告

> **分析日期**: 2026-03-04  
> **分析范围**: FastAPI + LangGraph 多智能体系统  
> **目标**: 识别性能瓶颈并提供系统性优化方案

---

## 📋 执行摘要

### 核心发现

- **简单对话场景**: 平均响应时间 **9.6秒**，其中 Supervisor LLM 推理占 **1.5-4秒**
- **待办助手场景**: 平均响应时间 **13.6秒**，额外增加 Todo Expert LLM 调用
- **问数助手场景**: 平均响应时间 **23.8秒**，Vanna SQL 生成链路占 **3.5-6秒**

### 优化潜力

通过 P0+P1 优化方案，预计可实现：
- 简单对话: **9.6秒 → 5.0秒** (减少 48%)
- 待办助手: **13.6秒 → 8.5秒** (减少 37%)
- 问数助手: **23.8秒 → 15.5秒** (减少 35%)

    ├─ Todo Expert → todo_graph (500-2000ms LLM + 100-500ms 工具)
    └─ Data Expert → data_graph
        ├─ 意图分析 LLM (800-2500ms)

## 🔥 核心瓶颈排名

### TOP 1: Supervisor LLM 推理（1.5-4秒）⭐⭐⭐⭐⭐

**问题描述**:
- 每次对话都要经过 Supervisor 进行意图识别
- 即使是简单问候也要调用 LLM
- 上下文裁剪（trim_messages）每次重新计算 token 数

**代码证据**:
```python
# multi_agent_graph.py:2292
pruned_messages = trim_messages(
    messages,
    max_tokens=max_tokens,
    token_counter=count_tokens_approximately,  # 🔴 CPU 密集型
    strategy="last"
)

# 然后调用 Supervisor LLM
response = await supervisor_llm.ainvoke(prepared_messages)  # 🔴 1.5-4秒
```

**影响范围**: 所有场景

**优化方向**:
1. 意图预判缓存（基于消息相似度）
2. Token 计数增量缓存
3. 轻量级意图分类器（GLM-4-Flash）

---

### TOP 2: Vanna SQL 生成链路（3.5-6秒）⭐⭐⭐⭐⭐

**问题描述**:
- **问题 Embedding**（500-1500ms）: 同步调用，阻塞主流程
- **DDL 向量检索**（300-800ms）: 查询 `t_meta_tables` 的 embedding 列
- **列信息查询**（200-600ms）: 串行查询 `t_meta_columns`
- **SQL 生成 LLM**（1500-3500ms）: 最终 LLM 推理

**代码证据**:
```python
# vanna_client.py:78
embedding = self.generate_embedding(question)  # 🔴 同步调用
embedding_str = str(embedding)

# 向量检索
table_sql = text("""
    SELECT id, schema_name, table_name, ...
    FROM t_meta_tables 
    WHERE embedding IS NOT NULL
    ORDER BY embedding <=> :embedding  # 🔴 PGVector 查询
    LIMIT 5
""")

# 串行查询列信息
col_sql = text("""
    SELECT column_name, data_type, ...
    FROM t_meta_columns 
    WHERE table_id = :table_id  # 🔴 逐表查询
""")
```

**影响范围**: 问数助手场景

**优化方向**:
1. DDL 预热 + 缓存（高频表）
2. 异步并行查询表和列
3. Embedding 结果缓存

### TOP 5: 上下文裁剪重复计算（200-500ms）⭐⭐⭐

**问题描述**:
- 每次请求都要重新计算全部历史消息的 token 数
- `count_tokens_approximately` 是 CPU 密集型操作
- 没有缓存机制

**代码证据**:
```python

pruned_token_estimate = int(count_tokens_approximately(pruned_messages) or 0)

```

**影响范围**: 所有场景

**优化方向**:
1. 消息级 token 缓存（message_id → token_count）
2. 增量计算（只计算新消息）
3. 使用更快的 token 计数算法

## 🎯 优化方案路线图

### P0 - 立即见效（1周内，减少 3-5秒）

#### 1. Supervisor 意图预判缓存

**实现方案**:
```python
# 新增 app/ai/cache/intent_cache.py
from cachetools import TTLCache

class IntentCache:
    _cache: TTLCache = TTLCache(maxsize=10000, ttl=300)  # 5分钟
    
    def get_cached_intent(self, user_id: int, message: str) -> Optional[str]:
        """基于消息相似度的意图缓存"""
        cache_key = f"{user_id}:{hash(message[:100])}"
        return self._cache.get(cache_key)
    
    def set_intent(self, user_id: int, message: str, intent: str):
        cache_key = f"{user_id}:{hash(message[:100])}"
        self._cache[cache_key] = intent

intent_cache = IntentCache()
```

**改造点**:
- `multi_agent_graph.py` Supervisor 节点调用前先查缓存
- 缓存命中直接跳过 LLM 推理

**预期收益**: 减少 1-2秒（缓存命中率 >40%）

#### 2. Token 计数增量缓存

**实现方案**:
```python
# 新增 app/ai/cache/context_cache.py
class MessageTokenCache:
    _cache: Dict[str, int] = {}  # message_id -> token_count
    
    def get_total_tokens(self, messages: List[BaseMessage]) -> int:
        """增量计算 token 数"""
        total = 0
        for msg in messages:
            msg_id = getattr(msg, 'id', None)
            if msg_id and msg_id in self._cache:
                total += self._cache[msg_id]
            else:
                count = count_tokens_approximately([msg])
                if msg_id:
                    self._cache[msg_id] = count
                total += count
        return total

token_cache = MessageTokenCache()
```

**改造点**:
- `multi_agent_graph.py:2292` 替换 `count_tokens_approximately` 调用

**预期收益**: 减少 200-500ms
