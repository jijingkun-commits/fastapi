# 聊天停止后并发占用稳定性修复 设计说明

## 1. 需求澄清结论
- 目标: 修复用户点击停止后，后续请求持续出现 `another command is already in progress` 的稳定性故障。
- 范围: 仅后端运行时链路，覆盖 `chat_service` 收口流程与 `postgres_checkpointer` 连接管理。
- 边界: 本轮不做前端多会话体验重构，不改业务语义，不新增业务接口。
- 成功标准: 停止后重试可恢复、并发会话下不再出现持续占用、具备可回滚策略与可观测证据。

## 2. 方案对比（2-3个）
| 方案 | 优点 | 缺点 | 成本 | 推荐度 |
|---|---|---|---|---|
| A: 仅止血（断连后跳过高风险状态回读） | 改动最小、恢复最快 | 只能缓解，不解决长期并发稳定性 | 低 | 中 |
| B: 仅改 checkpointer 池化 | 面向根因，长期收益高 | 一次性改动风险高于止血 | 中 | 中高 |
| C: 双阶段（先A后B） | 先恢复可用，再完成根因治理，风险可控 | 需要两阶段验证与交付管理 | 中 | 高 |

## 3. 推荐方案与理由
- 推荐: 方案 C（先止血再池化治理）。
- 理由: 当前故障影响在线可用性，先止血可快速止损；随后以池化改造消除单连接并发冲突，兼顾短期恢复与长期稳定。

## 4. 设计概要
- 架构: 在 `chat_service` 加入取消/断连收口守卫，避免触发高风险回读路径；在 `postgres_checkpoint` 引入并发安全初始化与连接池管理。
- 组件: `app/services/chat_service.py`、`app/db/postgres_checkpoint.py`、`app/ai/workflow/multi_agent_graph.py`。
- 数据流: `stop -> cancel/disconnect -> stream 收口 -> checkpointer 获取与状态回读`，通过阶段守卫和池化连接降低冲突。
- 异常与测试考虑: 增加停止后重试、并发会话隔离、resume 恢复链路测试；保留回滚路径（恢复止血前策略或切回单连接）。
