# RAGFlow 工具返回内容过长问题分析

## 问题现象

`knowledge_search` 工具返回内容达到 **20310 字符**（30 个 chunks），远超预期。

## 根本原因

### 1. 多知识库检索
当前配置使用了**多个 RAGFlow 知识库**：
```python
# 从日志看到
datasets=['7c112617e91411f08852712b5dc403b8', '7ada1afbeac811f0a8c5712b5dc403b8']
```

### 2. 每个知识库返回 top_k 结果
虽然配置 `RAGFLOW_TOP_K=5`，但：
- 知识库 1 返回 5 个结果
- 知识库 2 返回 5 个结果
- ...
- **总计：6 个知识库 × 5 = 30 个 chunks**

### 3. 每个 chunk 最多 800 字符
```python
if len(content) > 800:
    content = content[:800] + "..."
```

**预估总长度**：30 chunks × 800 字符 = 24000 字符（接近实际的 20310）

## 对 LLM 的影响

### 超长输入导致的问题：
1. **上下文窗口压力**：占用大量 token
2. **注意力分散**：LLM 难以关注所有细节
3. **自动摘要倾向**：倾向于提取关键信息，忽略格式（如图片 Markdown）
4. **生成延迟**：处理时间更长

### 从日志验证：
```
[supervisor] LLM 输入消息（最后 3 条）:
  [0] type=tool, name=knowledge_search
      content=【0】企业网银新功能介绍...（20310 字符）
      📸 包含图片数量: 23

[supervisor] LLM 输出统计:
  总长度: 2352 字符
  包含图片: 0 张  ← LLM 过滤了所有图片
```

## 优化方案

### 方案 A：减少返回结果数量（推荐）
**修改配置**：
```bash
# .env.dev
RAGFLOW_TOP_K=3  # 从 5 改为 3
```

**效果**：
- 6 个知识库 × 3 = 18 个 chunks
- 预估长度：18 × 800 = 14400 字符（减少 30%）

### 方案 B：限制知识库数量
**只使用最相关的知识库**：
```python
# 配置中只保留核心知识库
RAGFLOW_DATASET_IDS=['7c112617e91411f08852712b5dc403b8']
```

**效果**：
- 1 个知识库 × 5 = 5 个 chunks
- 预估长度：5 × 800 = 4000 字符（减少 80%）

### 方案 C：减少每个 chunk 的长度（不推荐）
```python
# ragflow_tool.py
if len(content) > 500:  # 从 800 改为 500
    content = content[:500] + "..."
```

**缺点**：可能丢失重要信息

### 方案 D：智能过滤（最佳）
**在工具层面智能过滤低相关度结果**：
```python
def _format_retrieval_results(chunks: list, max_chunks: int = 10) -> str:
    # 只保留相似度 > 0.7 的结果，且最多 max_chunks 个
    filtered_chunks = [
        c for c in chunks 
        if c.get("similarity", 0) > 0.7
    ][:max_chunks]
    ...
```

**效果**：
- 自动过滤低质量结果
- 动态控制总长度
- 保留高质量信息

## 建议实施

**组合方案（效果最佳）**：

1. **立即执行**：减少 `RAGFLOW_TOP_K` 到 3
2. **中期优化**：实施方案 D，添加智能过滤
3. **长期优化**：根据实际使用情况，调整知识库配置

## 预期改善

| 指标 | 当前 | 优化后 | 改善 |
|------|------|--------|------|
| Chunks 数量 | 30 | 10-15 | -50% |
| 总字符数 | 20310 | 8000-12000 | -60% |
| LLM 处理质量 | 低（过滤图片） | 高（保留细节） | 显著提升 |

## 其他工具检查

当前项目中可能返回超长内容的工具：

1. ✅ **knowledge_search**：已分析，需优化
2. **tavily_search**：网络搜索，通常短小，无问题
3. **sql_inter**：数据库查询，结果可控
4. **python_inter**：代码执行，输出可控
5. **fig_inter**：图表生成，返回 URL，极短

**结论**：只有 `knowledge_search` 存在超长返回问题。
