# BOJX AI 智能助手 - 项目文档

> 基于 LangGraph 多智能体架构的 AI 助手系统，支持智能对话、待办管理、数据问答等场景。

## 关于本仓库

本仓库同时包含后端、前端与文档；`docs/` 是**稳定文档主入口**，用来回答“当前到底以什么为准”。

如果你只想快速了解项目，直接从本页和 `SUMMARY.md` 开始就够了，不用先通读代码。

> **声明**：文档中出现的企业名称、Logo 及品牌元素均为虚构或借用于网络，仅用于学习演示目的，不代表与任何真实企业存在关联。如有侵权，请联系删除。

## 关于本项目

本项目是一个从零开始、一点一滴完善的 AI 应用，主要目的是**学习 AI 应用开发**。除知识库部分集成了开源的 [RAGFlow](https://github.com/infiniflow/ragflow) 外，其余模块都借助 Vibe Coding 方式逐步搭建完成。

项目还没有正式上线，所以当前最重要的不是“兼容旧口径”，而是把文档和工程结构整理清楚，尽量做到：

- 读者一眼知道当前真理源在哪里
- 过程文档不污染主阅读路径
- 自动化产物不混进稳定文档目录

## 文档分层约定

当前文档体系统一按两个维度理解：

1. 生命周期：最终文档 / 过程文档 / 运行态产物
2. 消费方式：给人读 / 给机器读

所以真正有用的判断表是下面这张：

| 生命周期 | 给人读 | 给机器读 |
|---|---|---|
| **最终文档** | `docs/产品文档/`、`docs/开发文档/`、`docs/API文档/`、`docs/内部参考/` | `contracts/` |
| **过程文档** | `workdocs/需求/`、`workdocs/设计/`、`workdocs/任务拆解/` 根目录与 `workstreams/` | `workdocs/**/contracts/`、`workdocs/**/reports/`、过程 JSON/YAML |
| **运行态产物** | `none` | `.artifacts/**` |

补充约定：

- 活跃过程材料在 `workdocs/`
- 已结束但需要追溯的过程材料在 `workdocs/归档/`
- `docs/` 不再继续承接测试报告、调试报告、审查报告这类过程正文
- `docs/开发文档/` 二级目录固定收敛为：`快速入门 / 架构设计 / 代码解读 / 流程与工具 / 测试管理 / 规范`

当前主导航覆盖**最终真理源**：

- 给人读的稳定文档在 `docs/`
- 给机器读的稳定契约在 `contracts/`

可以直接记成一句话：

- `docs/` 回答“人现在以什么为准”
- `contracts/` 回答“机器现在以什么契约为准”
- `workdocs/` 回答“这件事怎么推进到现在”
- `.artifacts/` 回答“脚本当前跑到哪一步”

`docs/内部参考/` 下仍保留少量旧入口说明页，但它们只负责兼容旧链接，不再承载新的过程正文。

如果你要看完整目录职责说明，优先看：

- [文档信息架构](开发文档/流程与工具/文档信息架构.md)


### AI 协作者规则文档分层

如果当前任务会用到 `Codex` / `AGENTS.md` / `PLANS.md` 这类协作规则，按下面这套方式理解：

| 文档载体 | 角色 | 应该放什么 | 什么时候读 |
|---|---|---|---|
| **根 `AGENTS.md`** | 常驻入口 | 全局硬门禁、输出口径、加载路由 | 几乎每个仓内任务都会生效 |
| **目录级 `AGENTS.md`（如 `app/ai/AGENTS.md`）** | 局部高信号入口 | 只对该目录树生效的补充规则 | 命中对应目录时优先读 |
| **`.cursor/rules/*.mdc`** | 技术规则真理源 | 架构、文档同步、测试质量、MCP 路由、agent authoring 等技术细则全文 | 命中对应主题时按需读 |
| **`PLANS.md`** | 长流程执行手册 | 实现、测试、验证、交付这类多阶段流程 | 复杂任务或长流程任务时再读 |
| **仓库根 `memory-bank.md`** | 项目记忆索引 | 仓库级活跃决策摘要、跨任务默认做法、ADR/真理源跳转链接 | 需要承接跨会话上下文或判断“过去怎么定的”时再读 |

这套分层的核心不是“删规则”，而是**不丢规则内容，但缩小默认加载面**：

- 根 `AGENTS.md` 只保留**总则 + 路由**，不要继续承载所有细则全文。
- 技术细则保留在 `.cursor/rules/*.mdc` 作为**唯一真理源**，避免根文件和平行文档双写。
- 命中 agent 编排或 `app/ai/**` 时，先看 `app/ai/AGENTS.md`，再看 `.cursor/rules/agent_authoring.mdc`；这套 `agent authoring` 规则只负责“以后怎么写”，不替代运行态架构文档。
- 只有在开始实现、跑测试、做验收时，才通过 `AGENTS.md` 路由去读 `PLANS.md` 的长流程。
- 目录越靠近当前工作路径，优先级越高；局部规则优先覆盖全局规则。
- 静态且高复用的说明应尽量短、稳定，避免把无关长清单每轮都塞进上下文。

这样做的目的有两个：

1. **规则内容不丢**：全文仍然保留在真理源文档里。
2. **上下文更聚焦**：模型默认只背最需要的规则，不必每轮重复加载整套长流程和长清单。

参考依据：

- OpenAI 官方 `AGENTS.md` 文档说明：Codex 会按全局、仓库、子目录逐级加载指令，目录越近优先级越高；当项目文档过大时，应拆分到更靠近代码的嵌套目录，而不是继续堆在根文件中。参见：[Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)
- OpenAI Developer Cookbook（2025-10-07）建议：对于多小时、多阶段、需要研究与实施并行推进的任务，可以在 `AGENTS.md` 中声明何时使用 `PLANS.md`，再将长流程放入 `PLANS.md`。参见：[Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans)
- OpenAI 官方 Prompt Caching 建议：稳定且重复的前缀应尽量保持固定，动态内容应尽量后置，以获得更好的缓存与延迟表现。参见：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

## 稳定阅读路径

```text
docs/
├── README.md
├── SUMMARY.md
├── 产品文档/            ← 最终文档 / 给人读
├── 开发文档/            ← 最终文档 / 给人读
├── API文档/             ← 最终文档 / 给人读
└── 内部参考/            ← 长期有效内部知识

contracts/
└── ...                 ← 最终契约 / 给机器读

workdocs/
├── 需求/               ← 过程文档 / 给人读
├── 设计/               ← 过程文档 / 给人读
├── 任务拆解/            ← 过程正文 + contracts/reports
└── 归档/
    ├── 正文/           ← 历史需求 / 设计 / 实施计划
    ├── 报告/           ← 历史测试 / 验收 / 审查 / 调试等报告
    ├── 任务拆解/        ← 历史 task bundle
    └── 专题/           ← 治理 / 研究 / 工作流规划 / 架构历史

.artifacts/
└── ...                 ← 运行态 / 给机器读
```

> `workdocs/` 是 canonical 过程层根目录；历史 `design / requirements / implementation_plan / report` 已逐步沉到 `workdocs/归档/`，`docs/` 不再承接新的过程正文。

## 文档维护规则

代码修改时，优先同步更新对应的**稳定真理源**：

| 修改范围 | 更新文档 |
|---|---|
| 新增功能 | `产品文档/系统需求.md` |
| API 变更 | `API文档/接口文档.md` |
| AI 模块 | `开发文档/架构设计/AI模块设计.md` |
| 数据库 | `开发文档/架构设计/数据库设计.md` |
| 配置项 | `开发文档/快速入门/配置说明.md` |

补充约定：

- 过程文档不能替代稳定真理源。
- 稳定文档默认原位修改，不在文末堆“增量需求 / 实现进展 / 日期补充”。
- 运行态文件、锁文件、生成结果不应进入主导航。

详见 `.cursor/rules/doc_sync.mdc`。
