# 问数双角色权限需求基线（2026-02）

> 文档状态：已澄清基线（`/jjk-plan parallel`）
> 更新时间：2026-02-15
> 关联范围：`app/models/user.py`、`app/services/permission_service.py`、`app/ai/utils/sql_rewriter.py`、`app/api/v1/endpoints/access_admin_api.py`

---

## 1. 背景与目标

当前系统问数权限已具备表级/行级/列级能力，但角色语义仍停留在通用互联网场景（`admin/analyst/user`），与银行组织治理要求不一致。

本轮目标：

1. 建立“系统角色 + 数据角色”双角色模型，避免系统管理权限与问数数据可见范围耦合。
2. 固化“默认最小权限”：未显式放权时，仅可访问本 `dept_code` 数据。
3. 支持按数据角色配置放大范围（本机构/指定机构/指定部门）。
4. 为后续分阶段实施提供可拆解、可追溯、可门禁的统一需求基线。

---

## 2. 范围与非目标

### 2.1 本轮纳入范围

1. 数据权限模型与角色语义重构（双角色）。
2. 问数权限引擎策略重构（移除 admin 默认直通）。
3. 行级默认策略切换为 `dept_code` 隔离。
4. 权限配置与审计能力规划（后续按阶段落地）。

### 2.2 本轮非目标

1. 不在本轮引入复杂组织树计算（如多级汇报关系自动推导）。
2. 不在本轮改造所有业务 API 的鉴权模型（仅问数权限链路）。
3. 不在本轮改变 SSE 主协议（`done/result/interrupt`）字段契约。

---

## 3. 业务角色与用户故事（银行场景）

### 3.1 角色定义

- 系统角色（`sys_role`）：当前统一为 `admin`（用于后台管理能力）。
- 数据角色（`data_role`）：
  - `head_president`（总行行长）
  - `department_gm`（部门总经理）
  - `department_vgm`（部门副总）
  - `staff`（员工）

### 3.2 用户故事

1. 作为**员工（staff）**，我希望默认只能查询本部门数据，避免越权访问。
2. 作为**部门总经理（department_gm）**，我希望在获授权后可查看更大范围（如本机构多部门）。
3. 作为**总行行长（head_president）**，我希望权限由配置决定，而不是默认全行可见。
4. 作为**平台管理员（sys_role=admin）**，我希望通过配置调整数据角色权限，不依赖代码改动。

---

## 4. 功能需求

### 4.1 双角色解耦

1. 用户身份必须区分：`sys_role` 与 `data_role`。
2. `sys_role=admin` 不再自动获得问数数据全权限。
3. 问数权限判定统一使用 `data_role` + 权限配置。

### 4.2 默认行级策略

1. 默认行级规则为：`dept_code = user.dept_code`。
2. 当用户缺失 `dept_code` 时，默认拒绝查询并返回可观测原因。
3. 角色配置可显式放大范围，但不得绕过 deny 规则。

### 4.3 角色放权策略

1. 支持按 `data_role` 配置表级允许范围。
2. 支持按 `data_role` 配置行级范围（本部门/本机构/指定列表）。
3. 支持按 `data_role` 配置列级脱敏。
4. 支持显式拒绝优先（deny_overrides_allow）。

### 4.4 管理与审计

1. 提供权限配置管理接口（后续阶段实现）。
2. 提供 SQL 权限试跑能力，输出重写 SQL 与拒绝原因。
3. 记录策略命中日志，支持问题追溯。

---

## 5. 验收标准

### 5.1 Happy Path

1. `staff` 用户问数 SQL 自动注入 `dept_code` 过滤条件。
2. `department_gm` 在配置放权后可查询配置范围内数据。
3. `sys_role=admin` 且未放权时，仍受 `data_role` 限制。

### 5.2 边界与异常

1. 用户 `dept_code` 为空时，查询被拒绝，错误可解释。
2. 未配置的数据角色使用最小权限模板，不出现全量放开。
3. 规则冲突时遵循：`显式拒绝 > 显式允许 > 默认模板`。

### 5.3 性能与稳定性

1. SQL 权限检查与重写的 p95 延迟相对基线增加不超过 20%。
2. 权限策略加载支持缓存并可主动失效。
3. 配置更新后可在可控时间内生效（缓存刷新）。

---

## 6. 非功能需求

1. **安全**：默认最小权限，严禁“未配置即放开”。
2. **可观测**：日志含 `user_id`、`data_role`、命中规则、拒绝阶段。
3. **一致性**：同一用户同一 SQL 在同配置版本下结果一致。
4. **可维护性**：角色枚举采用代码值存储，前端映射中文展示。

## 8. 风险与待决策清单

1. **角色演进风险**：当前仅冻结四类数据角色，后续新增角色需避免破坏现有规则。
2. **历史数据风险**：既有用户全部 `admin`，需要安全回填 `data_role` 模板。
3. **策略复杂度风险**：范围放大规则若设计过度复杂，会影响运维可理解性。
4. **待决策**：机构编码与部门编码规范是否统一维护字典（建议后续迭代处理）。
