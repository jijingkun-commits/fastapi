# 文档治理执行实施方案（2026-02）

> 文档状态：实施基线（`/jjk-plan core`）
> 日期：2026-02-14
> 对应需求：`docs/内部参考/迭代需求/docs_governance_requirements.md`

---

## 1. 方案概览

本方案面向 `docs/**` 治理落地，按“先准确、再收敛、后机制化”三阶段执行：

1. **Phase 1 / P0**：修复会误导开发动作的失效路径与过期命令。
2. **Phase 2 / P1**：按已拍板决策收敛信息结构与权威来源边界。
3. **Phase 3 / P2**：补治理机制，降低后续回归成本。

本轮采用 `core` 模式，不生成并行 `card_seed`。

---

## 2. 架构影响与约束

## 2.1 模块边界

1. `docs/开发文档/架构设计/`：只承载设计决策、模块边界、契约定义（权威源）。
2. `docs/开发文档/代码解读/`：只承载实现走读、调用链说明、调试理解（辅助源）。
3. `docs/开发文档/技巧与速查/`：高频入口与速查，不替代权威设计文档。
4. `.cursor/commands/*.md`：命令细节权威来源；速查文档保留索引和使用建议。

## 2.2 状态契约

1. 文档治理状态字段统一为：`P0/P1/P2`、`批次 A/B`、`已拍板/待确认`。
2. “已拍板决策”仅在一处权威维护（`文档梳理与重构方案`），其余文档引用该结论。
3. 命名规范状态：保持 `内部参考/迭代需求` 当前目录结构，仅统一命名规则，不新增归档层。

## 2.3 路由闭环

治理闭环固定为：

`问题识别 -> 决策拍板 -> 文档修订 -> SUMMARY 索引同步 -> docs_guard 门禁 -> 结果回填`

禁止跳过 `SUMMARY` 更新直接结束文档改动。

## 2.4 端到端链路

1. 入口文档（`README/SUMMARY/AI协作速查表`）更新后，必须核对到目标权威文档的可达性。
2. 权威文档变更后，需反向检查速查与工作流文档是否产生口径偏差。
3. 每批次完成后，统一执行门禁并在方案文档回填状态。

## 2.5 可测试性

1. 静态门禁：`python3 scripts/docs_guard.py --strict`
2. 路径抽检：对 `app/`、`web/`、`scripts/` 关键引用做存在性核对。
3. 语义抽检：至少覆盖 1 个银行业务路径（如“分行贷款余额”）和 1 个合规边界路径（权限/脱敏）。

## 3. 详细实施步骤

## 3.1 Phase 1（P0，建议 1 天）

目标：消除误导性失准。

执行项：

1. 修正 `README` 仓库定位。
2. 修正 `多智能体工作流`、`待办Agent设计`、`数据库设计`、`测试指南`、`vibe-coding开发技巧` 的失准点。
3. 为 `开发工作流` 模板代码补“示例占位”标注。

通过条件：

1. P0 清单归零。
2. 门禁通过。

## 3.2 Phase 2（P1，建议 1~2 天）

目标：按拍板决策收敛结构。

执行项：

1. `vibe-coding开发技巧.md` 保持全量百科定位，增加权威来源说明。
2. 明确 `代码解读/` 与 `架构设计/` 边界，去除重复架构描述。
3. 统一 `内部参考/迭代需求` 命名规则，并补索引说明。

通过条件：

1. 关键入口文档无冲突口径。
2. `SUMMARY` 覆盖率保持 100%。

## 3.3 Phase 3（P2，建议 1 天）

目标：机制化防回归。

执行项：

1. 形成文档月度校准清单。
2. 评估是否扩展 `docs_guard` 的路径存在性检查（仅在确认低误报后启用）。

通过条件：

1. 校准清单可复用。
2. 不引入额外门禁噪音。
