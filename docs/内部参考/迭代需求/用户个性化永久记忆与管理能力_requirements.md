# 用户个性化永久记忆与管理能力需求基线

> 文档日期：2026-03-01  
> 文档定位：定义“用户个性化永久记忆”在管理后台的可查询、可治理、可审计需求  
> 上游设计输入：`docs/plans/2026-03-01-user-personalized-memory-management-design.md`

---

## 1. 背景与问题定义

当前系统已具备“用户个性化永久记忆”的核心能力：

1. 对话链路可将用户事实沉淀到 `t_user_memory_document` + `t_user_memory_chunk`。
2. 对话召回已支持 `memory_search -> memory_get` 混合检索。
3. 已有基础运维 API（向量重建、状态、失败重试）。

但在“管理可用性”上仍有明显缺口：

1. 缺少按用户维度的记忆列表与详情查询。
2. 缺少文档级治理动作（归档、删除、复算、调试检索）。
3. 缺少后台可视化入口，运维对 API 可见性不足。
4. 缺少结构化审计与统一错误口径，存在治理盲区。

本需求旨在补齐“查管闭环”，且不破坏现有主对话稳定性。

---

## 2. 目标、范围与边界

### 2.1 目标（Goal）

1. 管理员可按 `user_id` 快速查询用户个性化永久记忆。
2. 管理员可执行安全可回滚的记忆治理动作。
3. 运维可查看向量化状态与召回调试结果，快速定位问题。
4. 对外命名统一“记忆（memories）”语义，对内保留 document/chunk 实现。

### 2.2 范围（In Scope）

1. 后端管理 API：列表、详情、分块状态、归档、删除、召回调试、向量重建闭环。
2. 管理后台页面：筛选、浏览、详情抽屉、治理动作。
3. 权限与审计：管理员权限校验、关键操作审计日志。
4. 配置治理：通过 feature 开关灰度启停管理能力。

### 2.3 非范围（Out of Scope）

1. 不引入外部向量数据库。
2. 不做跨集群记忆复制。
3. 不做普通用户自助编辑记忆（仅管理员治理）。
4. 不重构现有两表主模型。

---

## 3. 用户故事（User Stories）

### US-01（平台管理员）

作为管理员，我希望按用户快速查看其永久记忆列表与详情，以便判断召回行为是否符合预期。

### US-02（运维工程师）

作为运维，我希望看到向量状态（pending/ready/failed）和失败原因，并可重试或重建。

### US-03（安全与治理）

作为安全负责人，我希望关键管理动作可审计、可追踪、可回放，以满足问题追责与合规要求。

### US-04（产品与算法）

作为产品/算法，我希望有召回调试入口，能看到分数与引用，持续优化记忆质量。

## 4. 方案对比与选型

| 方案 | 优点 | 缺点 | 成本 | 推荐度 |
|---|---|---|---|---|
| A. 仅补后端 API（无页面） | 交付快，改动小 | 非研发角色不可自助使用 | 低 | ⭐⭐⭐ |
| B. 后端 API + 管理后台 MVP | 查管闭环完整，风险可控 | 需要前后端联调 | 中 | ⭐⭐⭐⭐⭐ |
| C. 全治理平台（含报表中心） | 一次性能力完整 | 周期长，首期复杂度高 | 高 | ⭐⭐⭐ |

结论：本期采用 **方案 B**，分阶段交付，先满足查询治理，再逐步增强审计与体验。

## 5. 功能需求（Functional Requirements）

### 5.1 查询类需求

1. `FR-01` 记忆列表查询：支持 `user_id/doc_kind/status/source/date_range/keyword` 过滤，支持分页与排序。
2. `FR-02` 记忆详情查询：返回文档正文、版本、来源、范围、更新时间。
3. `FR-03` 分块状态查询：返回 chunk 行号、状态、重试次数、错误摘要。
4. `FR-04` 状态聚合查询：返回用户或文档维度向量状态统计。
5. `FR-05` 召回调试查询：输入 query，返回片段、text_score、vector_score、final_score、citation。

### 5.2 管理类需求

1. `FR-06` 归档记忆：支持按 memory_id 归档，默认查询不展示 archived。
2. `FR-07` 删除记忆：支持安全删除（文档 + chunk 级联），删除操作必须记录审计。
3. `FR-08` 向量重建：支持按 user/doc 触发 pending/failed 分块重建。
4. `FR-09` 失败重试：支持失败分块重置与重跑。
5. `FR-10` 批量操作（一期可选）：支持批量归档/重建的接口预留。

### 5.3 管理后台页面需求

1. `FR-11` 页面入口：在管理员后台提供“用户个性化永久记忆”菜单。
2. `FR-12` 筛选面板：支持 user_id、文档类型、状态、日期范围、关键词。
3. `FR-13` 列表展示：展示标题、更新时间、revision、chunk 统计、ready 比例。
4. `FR-14` 详情抽屉：展示正文、引用区间、chunk 状态表。
5. `FR-15` 操作反馈：所有治理动作需有明确成功/失败反馈和错误码。

### 5.4 安全与审计需求

1. `FR-16` 权限控制：管理 API 仅管理员可访问。
2. `FR-17` 审计留痕：归档/删除/重建/重试/调试操作必须留审计记录。
3. `FR-18` 数据隔离：所有查询和操作均需明确用户边界，禁止跨用户越权读取。

## 6. 验收标准（Acceptance Criteria）

### 6.1 Happy Path

1. `AC-01` 管理员输入 `user_id` 可返回该用户记忆列表。
2. `AC-02` 管理员打开详情可查看正文与分块状态。
3. `AC-03` 管理员触发重建后，状态统计中 `ready` 数量增长。
4. `AC-04` 管理员执行归档后，默认列表不再显示该条记忆。
5. `AC-05` 召回调试可返回分数与引用信息，便于定位召回质量。

### 6.2 异常与边界

1. `AC-06` 非管理员调用管理接口返回 403。
2. `AC-07` 不存在 memory_id 的归档/删除返回 404。
3. `AC-08` 超大分页参数会被服务端限流到安全范围。
4. `AC-09` embedding worker 未开启时，重建接口返回可解释错误（409）。
5. `AC-10` 数据库异常时返回统一错误码并记录结构化日志。

### 6.3 性能与稳定性

1. `AC-11` 列表查询 P95 <= 300ms（常规过滤 + 分页）。
2. `AC-12` 详情查询 P95 <= 350ms（含 chunk 状态统计）。
3. `AC-13` 管理操作接口具备幂等保护（重复归档/重试不产生脏数据）。

---

## 7. 非功能需求（NFR）

1. **性能**：索引充分利用，不允许全表扫描成为常态路径。
2. **安全**：仅管理员访问；日志与响应禁止泄露跨用户敏感内容。
3. **一致性**：删除/归档后文档与 chunk 状态一致，避免悬挂记录。
4. **可观测性**：关键操作写入结构化日志与审计事件。
5. **可回滚性**：支持通过 feature 开关快速禁用管理能力。

---

## 8. 场景约束（平台/架构任务）

本任务属于“平台治理与架构增强”，执行时必须满足：

1. 不修改对话主链路协议（SSE 输出格式不变）。
2. 不引入第三套记忆主存储；以两表方案为唯一主真相源。
3. 管理能力与用户对话能力解耦，管理失败不影响对话主流程。
4. 兼容现有 KV 偏好记忆控制层，不改变其职责边界。

## 10. 发布完成定义（DoD）

1. FR-01 ~ FR-09 必须完成并通过测试。
2. 管理后台页面至少完成查询、详情、归档、重建入口。
3. 文档索引同步完成，`docs_guard --strict` 通过。
4. 回滚开关可验证：关闭后管理 API 不可用但对话正常。
5. 形成发布说明：开关配置、灰度步骤、回滚步骤。
