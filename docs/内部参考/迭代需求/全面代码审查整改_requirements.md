## 1. 背景与问题定义

当前代码审查问题池共 68 项（P0=10、P1=21、P2=37），且报告快照为 `2c1f8a0`，当前代码已迭代到 `a51cb83`。经复测确认，多数高风险问题仍未关闭，已具备“安全+架构+工程质量”混合整改特征，不能按零散缺陷处理，必须以专题实施计划收口。

本轮需求目标：

1. 以“单一整改计划”覆盖 68 项问题，避免分散修修补补。
2. 按风险链路先后推进：先封堵可利用风险，再治理架构债务，最后清理工程质量欠账。
3. 支持后续 `/jjk-vkplan`、`/jjk-vktodo` 串行落卡与自动执行（单卡滚动）。

## 2. 需求范围（必须覆盖）

### 2.1 安全与合规整改

- RCE/注入链：Python 执行工具、SQL 执行链、RLS 重写。
- 访问控制链：用户信息、线程消息、反馈、resume、资产代理、RAGFlow 代理。
- 认证基线：JWT 密钥、登录限流、开发态绕过、初始化弱密码。
- 暴露面收敛：健康检查、CORS、API Key 传输方式、开发工具沙箱能力。

### 2.2 架构整改

- LangGraph 大文件与状态膨胀。
- Service/Repository 边界反转与胖控制器。
- 异步一致性与运行态一致性。

### 2.3 工程质量整改

- 模型/schema 规范化、异常处理、日志规范。
- 前端类型治理与交互一致性。
- 测试体系补齐（重点集成测试与回归矩阵）。

## 3. 用户故事（银行场景）

1. 作为安全负责人，我需要阻断任何可被 Prompt Injection 触发的代码执行与越权数据访问，避免客户数据泄露。
2. 作为对公业务分析人员，我需要系统在“分行/机构维度”查询中只返回本人权限范围的数据，且不可通过 thread_id 越权读取他人会话。
3. 作为平台架构负责人，我需要工作流、服务层、仓储层边界清晰，避免单点文件/类持续膨胀导致回归风险不可控。
4. 作为前端负责人，我需要 SSE/消息/反馈链路行为一致，避免出现“看起来成功但数据状态不一致”的隐形故障。
5. 作为测试与发布负责人，我需要一套能执行的门禁清单，确保每次整改都可验证、可回滚、可审计。

## 4. 验收标准

### 4.1 功能性验收（Happy Path）

- AC-SEC-01: Python 工具链不再执行裸 `eval/exec`，且合法数据分析脚本仍可运行。
- AC-SEC-02: SQL 执行链统一经过“安全检查 + 权限重写 + LIMIT 控制”，并保持问数主流程可用。
- AC-SEC-03: `resume/messages/feedback/assets` 全链路强制归属校验，普通用户无法跨用户读取/写入。
- AC-SEC-04: 生产密钥与认证策略满足基线（JWT、登录策略、默认账号策略）。
- AC-ARC-01: Graph/Service/Repository 结构完成阶段性解耦，关键职责可追溯到单一模块。
- AC-QA-01: `tests/integration/` 建立并落地首批关键链路集成用例。

### 4.2 异常/边界验收

- AC-EDGE-01: 代理接口 404/403/502 不被吞并为 500。
- AC-EDGE-02: MinIO/RAGFlow 不可用时返回受控错误（不泄露内部异常上下文）。
- AC-EDGE-03: 分页参数超限、非法值被框架拒绝（422/400），不进入重查询路径。
- AC-EDGE-04: 取消/恢复/中断场景在 run control 状态机内一致，不出现“假完成”状态。

### 4.3 非功能验收

- AC-NFR-01: P0/P1 安全项复测通过率 100%。
- AC-NFR-02: 关键链路（聊天流、问数流、反馈流、资产流）回归通过率 100%。
- AC-NFR-03: 每个整改卡都具备“实现证据 + 测试证据 + 回滚锚点”。
- AC-NFR-04: 文档与索引同步通过 `python3 scripts/docs_guard.py --strict`。

## 5. 非功能需求（明确指标）

1. 安全: 对应 OWASP A01/A02/A03/A05/A07 与 LLM01/LLM07/LLM08 的核心风险全部进入可验证闭环。
2. 性能: 关键接口整改后 P95 不劣化超过 10%。
3. 稳定性: 代理流式下载、SSE 流式会话在异常注入场景仍保持可恢复。
4. 可维护性: 大文件/胖服务/跨层依赖必须进入拆分计划，不接受“仅注释说明”。
5. 可观测性: 安全关键动作（登录、工具调用、越权拒绝、反馈写入）需具备结构化日志或审计记录。

## 7. 约束与非目标

### 7.1 约束

1. 本轮优先“风险闭环与架构收敛”，不做大规模产品能力扩展。
2. 所有高风险整改必须保留回滚开关或回滚路径。
3. 串行执行模式下保持“同一时刻最多 1 张 scoped 非 done 卡”。

### 7.2 非目标

1. 不在本轮引入全新多租户权限体系。
2. 不在本轮完成全部历史脚本/文档的一次性归档清理。
3. 不把整改范围扩展到与本报告无关的新特性开发。
