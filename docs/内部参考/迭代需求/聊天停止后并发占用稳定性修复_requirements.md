# 需求基线（聊天停止后并发占用稳定性修复）

## 1. 背景与问题陈述

在聊天流式场景中，用户点击停止后，后续请求出现连续报错：

- 错误特征：`sending query and params failed: another command is already in progress`
- 用户体感：停止后本轮和后续多轮请求均可能失败，必须重启服务或等待较长时间恢复
- 风险：影响核心问答可用性，导致“强停止”能力被用户视为不可靠

现有链路已经具备 run 控制与停止接口能力，但在断连/取消收口与 checkpointer 连接管理上存在并发占用风险。

## 2. 目标与非目标

### 2.1 目标
1. 修复停止后连续 busy 错误，保证后续请求可恢复。
2. 在后端并发运行态下提升 checkpointer 稳定性，降低单连接冲突概率。
3. 保持现有 API 契约与前端交互语义不变，优先做兼容修复。

### 2.2 非目标
1. 本轮不实现完整 Codex 式前端多会话工作台改造。
2. 本轮不新增业务能力，不调整问数/待办业务逻辑。
3. 本轮不引入额外数据库对象或跨库结构升级。

## 3. 用户故事

1. 作为业务用户，我在生成中点击“停止”后，希望下一次提问能正常响应，不再连续报系统错误。
2. 作为运营人员，我希望系统在并发会话下仍可稳定处理 stop/cancel，不出现全局连锁失败。
3. 作为维护人员，我希望日志能快速定位是“停止收口问题”还是“连接管理问题”，便于回滚和修复。

## 4. 功能需求（FR）

### FR-01 停止后请求可恢复
1. 用户触发停止后，当前 run 应正确收口，不得污染后续 run。
2. 后续同线程或不同线程请求应可继续执行，不出现持续 busy 错误。

### FR-02 收口语义一致性
1. `stream` 与 `resume` 路径都必须遵守统一的取消/断连收口规则。
2. 在取消态、断连态、正常完成态之间，状态转换需可预测，不允许出现重复收口或异常回读。

### FR-03 checkpointer 并发安全
1. checkpointer 初始化与连接管理应支持并发访问，避免单连接重入冲突。
2. 连接异常或取消场景下，资源能够被回收，不阻塞后续请求。

### FR-04 可观测与运维
1. busy 类错误需有明确日志标识（包含 `thread_id`、`run_id`、阶段信息）。
2. 需要可执行回滚策略，故障时可快速退回到前一稳定版本。

## 5. 非功能需求（NFR）

1. 稳定性：stop/cancel 高频触发下，服务错误率显著下降，避免连续失败。
2. 性能：改造后不引入明显额外延迟（关键链路 P95 不劣化超过 10%）。
3. 一致性：不破坏现有 `run_id` / `thread_id` 状态契约。
4. 可维护性：修复逻辑集中在运行时层，不散落到业务节点。

## 6. 验收标准

### 6.1 功能验收（Happy Path）
1. 发送问题 -> 点击停止 -> 立刻再次发送问题，第二次请求正常返回。
2. 并发会话 A/B 同时运行时，停止 A 不影响 B 的持续输出与收口。

### 6.2 异常/边界验收
1. 连续多次 stop 操作不应导致服务进入持续 busy 状态。
2. resume 路径在取消后应返回一致终态，不出现重复异常堆叠。

### 6.3 可观测验收
1. 日志中可定位 busy 错误来源阶段（stream/resume/cancel_checkpoint）。
2. 回滚后可恢复至变更前行为，且风险可控。

## 7. 测试用例矩阵（预留）

| TC 编号 | 场景 | 预期 |
|---|---|---|
| CHAT-STAB-TC-001 | 停止后立即重试 | 无持续 busy，后续请求成功 |
| CHAT-STAB-TC-002 | 双会话并发 + 停止隔离 | 仅目标会话停止，其他会话不受影响 |
| CHAT-STAB-TC-003 | resume + cancel 交叉 | 终态一致，日志可观测 |
| CHAT-STAB-TC-004 | 连续 stop 压测 | 不出现连接池耗尽或持续错误 |

## 8. 约束与依赖

1. 依赖现有 run control 机制与 SSE 协议契约。
2. 依赖 LangGraph checkpointer 的 Postgres 实现能力。
3. 变更需与已有“聊天断页续跑与强停止”方案保持兼容。
