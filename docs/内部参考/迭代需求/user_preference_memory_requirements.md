# 跨会话用户偏好记忆需求基线（2026-02）

> 文档状态：已澄清基线（`/plan core`）
> 更新时间：2026-02-16
> 关联范围：`app/services/chat_service.py`、`app/services/user_preference_memory_service.py`、`app/models/user_memory.py`、`app/repositories/user_memory_repo.py`

---

## 1. 背景与目标

当前聊天链路具备线程级上下文延续能力（同 `thread_id` 可续聊），但缺少“用户级跨线程偏好记忆”。

在银行业务场景中，同一员工常重复表达固定偏好（如“默认中文回复”“先给结论再给分析”）。若每次都重复声明，会增加交互成本并影响体验稳定性。

本轮目标：

1. 建立用户级偏好记忆能力，在新会话中自动注入已保存偏好。
2. 首期仅支持“显式偏好记忆”（用户明确说“记住/默认/以后都...”）。
3. 保持双数据库边界：记忆数据仅写入 `chat_db`，不进入 `data_db`。

---

## 2. 范围与非目标

### 2.1 本轮纳入范围

1. 新增用户偏好记忆表（`t_user_memory`）及基础索引。
2. 在聊天请求进入时加载偏好并注入系统上下文。
3. 在用户消息保存后提取显式偏好并持久化。
4. 提供开关化配置，支持快速灰度与回退。

### 2.2 本轮非目标

1. 不做“隐式偏好自动推断”（例如从历史行为反推偏好）。
2. 不引入向量库或 RAG 召回链路。
3. 不新增用户侧偏好管理页面/API（后续迭代）。

---

## 3. 用户故事（银行场景）

1. 作为**分行客户经理**，我希望系统记住“默认中文+简短结论”，下次新开会话不用重复说明。
2. 作为**风险分析师**，我希望系统记住“先结论后分析”，提升高压场景下的信息获取效率。
3. 作为**运营人员**，我希望记忆能力可开关，若异常可快速关闭，不影响主对话链路。

---

## 4. 功能需求

### 4.1 偏好写入

1. 仅当用户消息命中显式意图词（如“记住”“默认”“以后都”）时尝试提取偏好。
2. 同一用户同一 `memory_key` 的活跃记录采用覆盖更新策略。
3. 写入时记录来源线程与来源消息，便于追溯。

### 4.2 偏好读取与注入

1. 新会话/新轮次请求时按用户读取活跃偏好。
2. 偏好读取按 `update_time` 倒序，优先使用最近更新项。
3. 同一偏好键若存在冲突记录，应按“最近更新时间优先”去重，仅注入最终值。
4. 偏好以系统上下文方式注入，不污染用户原始输入。
5. 注入条数受上限控制，且需支持摘要压缩，避免 prompt 膨胀。

### 4.3 配置开关

1. 提供总开关控制记忆功能启停。
2. 提供最大注入条数配置。
3. 当记忆模块异常时，降级为“跳过记忆但不阻断聊天”。

---

## 5. 验收标准

### 5.1 Happy Path

1. 用户 A 在会话 X 说“以后默认中文回复”，该偏好落库成功。
2. 用户 A 在会话 Y 提问时，系统自动注入“中文回复”偏好并生效。
3. 用户 B 不受用户 A 偏好影响（用户隔离）。

### 5.2 边界与异常

1. 未登录用户（`user_id` 为空）不启用记忆能力。
2. 记忆查询失败时，聊天主链路继续执行并记录告警日志。
3. 未命中显式偏好规则时，不产生记忆写入。

### 5.3 性能与稳定性

1. 单次记忆读取额外延迟控制在可接受范围（目标 p95 < 50ms）。
2. 记忆写入失败不影响 SSE 事件流完成。
3. 不引入消息重复落库与协议字段变更。
4. 当偏好上下文超过摘要阈值时，自动切换压缩输出，保持输入规模稳定。

---

## 6. 非功能需求

1. **安全性**：仅存“交互偏好”类信息，不存敏感业务数据。
2. **可观测性**：日志可追踪 user_id、命中规则、写入条数。
3. **可维护性**：偏好规则集中在单一服务模块，避免散落在 workflow 节点。

## 8. 风险与待决策

1. **误记忆风险（中）**：规则过宽可能提取到非偏好语句。
2. **上下文膨胀风险（中）**：偏好条目过多会增加 prompt 负担。
3. **待决策**：第二期是否开放用户自助查看/删除偏好 API。
