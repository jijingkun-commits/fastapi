# fix_plan_todo_compound_clarify_loop_20260301

## 1. 问题摘要
- 现象：用户一句话包含“目标 + 必做子动作”（如“回老家过清明，还要订高铁票”）时，待办链路出现反复澄清，且前端同一气泡中澄清文案重复，整体体验表现为“机械、不智能”。
- 用户真实意图澄清（本轮新增）：该表达是**一个目标**，`买票`属于该目标的执行子任务/详情，不应被误判为“两个独立待办”。
- 影响范围：
  - 待办创建多轮对话（`todo_expert`）
  - 多智能体消息分发（`custom + values`）
  - 前端 SSE 消息拼接渲染
- 严重级别：P1（不致命但强烈影响可用性与主观智能感）。

## 2. 根因结论

### 2.1 最终根因
1. **策略层根因（会话理解）**：待办意图提示词将“复合表达”硬约束为“只能单待办+必须澄清”，导致本可一次建单（主目标+子任务）的输入被强制拆成二选一追问。  
2. **状态收敛根因（流程控制）**：补充轮升级为 `need_confirm` 的条件偏严，遇到“先记一个”这类弱结构补充时无法收敛，继续 `need_clarify`。  
3. **呈现层根因（事件协议）**：澄清场景同时发送 `clarification` 与 `token`，前端又将 `message+questions` 拼接并对 token 继续追加，出现重复/啰嗦展示。

### 2.1.1 语义契约修正（必须）
- **单目标复合描述**：当句子为“目标 + 实现该目标的必要动作/子步骤”时，必须识别为一个待办。
- 结构化落位建议：
  - `title`：主目标（例如“回老家过清明”）
  - `description/subtasks`：必要动作（例如“购买高铁票（必做）”）
- 仅在以下场景才拆分多待办：
  1) 用户明确要求“拆成两个待办/分开记”；  
  2) 两项工作目标彼此独立且互不从属；  
  3) 时间/责任主体明显分离且用户确认要独立管理。

### 2.3 已排除假设
- 假设 A：数据库写入或待办 CRUD 异常导致反复澄清。  
  - 结果：FAIL（最终可正常创建，`t_todo` 落库成功，非数据层故障）。
- 假设 B：仅前端渲染导致“看起来重复”，后端其实只发一次语义。  
  - 结果：FAIL（后端确实双通道下发 `clarification + token`，前端只是放大问题）。
- 假设 C：模型偶发波动是唯一原因。  
  - 结果：FAIL（问题可稳定复现，且由固定策略与状态条件触发）。

## 3. 修复方案对比（2-3 方案）

| 方案 | 优点 | 缺点 | 成本 | 推荐度 |
|---|---|---|---|---|
| A. 最小修补：放宽复合创建判定 + 前端去重渲染 | 见效快，改动面小，回归成本低 | 仍是补丁式演进，长期语义一致性一般 | 低 | ⭐⭐⭐ |
| B. 分层重构（推荐）：引入“主目标+子任务”创建语义 + 澄清单通道协议 | 根因层修复，交互更自然，后续扩展（拆解/提醒/子任务）更稳 | 需要同时改 Prompt/状态机/SSE 协议，设计与联调成本较高 | 中 | ⭐⭐⭐⭐⭐ |
| C. 强规则兜底：检测“一个待办”即强制合并并跳确认 | 用户体感提升明显，减少追问 | 容易误判，存在越权自动决策风险 | 中 | ⭐⭐ |

### 推荐方案
- 推荐：**方案 B（分层重构）**。
- 理由：当前问题不是单点 bug，而是“策略-状态-展示协议”三层不一致。仅做 A 会留下结构性债务，后续在更多复合表达场景继续暴露。

## 4. 推荐方案实施清单

### 4.1 代码变更
1. 意图策略层（Todo Prompt/Intent）
   - 将“复合表达”从“必须二选一澄清”调整为：允许归并成单待办（主目标 + 必做子任务/描述）。
   - 增加“单目标复合描述”判定规则（目标-子任务从属关系优先于并列拆分）。
   - 仅在用户明确表达“必须拆成两个独立待办”时再走多待办流程。
2. 状态机层（Todo Graph）
   - 补充轮收敛策略从“必须新增字段”改为“有意图收窄信号 + 有历史 pending_operation”即可进入确认草稿（并显示可编辑确认卡）。
   - 对 `intent` 做枚举约束，过滤 `intent='need_clarify'` 这类无效值。
3. 事件协议层（Streaming/SSE）
   - 澄清场景统一为单通道：要么仅发 `clarification`，要么仅发 `token`，禁止同一语义双发。
4. 前端渲染层
   - 对 `final_source=clarification` 的消息禁用 token 追加，或做事件去重键（turn_id + node + type）。

### 4.2 数据库变更
- 无必须表结构变更。

### 4.3 配置变更
- 评估并上调渐进策略阈值（避免早期注入“重置/果断策略”干扰自然补充轮）。

## 5. 风险与回滚策略
- 风险 1：复合表达自动归并可能导致误建单。  
  - 回滚：增加 feature flag（如 `todo.enable_compound_create_merge`），灰度关闭即回到旧逻辑。
- 风险 2：SSE 单通道调整可能影响其他专家节点消息流。  
  - 回滚：按节点粒度启用（先仅 `todo_expert`），出现异常可回切到原事件策略。
- 风险 3：前端去重策略误吞有效 token。  
  - 回滚：保留日志开关，按 `event_type` 精确放开。
