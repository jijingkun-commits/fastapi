# 需求基线（聊天断页续跑与强停止）

> 主题来源：`/Users/jijingkun/bojxAI/fastapi/docs/plans/2026-03-01-chat-session-continuation-design.md`
> 设计审批：`design_approved: true`（2026-03-01 17:04）

---

## 1. 目标与问题定义

当前聊天链路存在两个体验断点：

1. 用户在流式回复中关闭页面后，后端执行常随连接生命周期耦合，无法稳定保证“本轮任务继续完成并落库”。
2. 用户重新登录后默认进入新会话，无法自动回到最近会话，导致“我刚才那轮结果在哪”成本高。

本需求目标：

1. 支持“断页续跑”：页面关闭不代表任务取消，后端可继续完成本轮处理并持久化结果。
2. 支持“强停止”：用户点击停止按钮时，必须显式取消服务端 run，而不是仅断开前端显示。
3. 支持“最近会话回显”：登录后优先回到最近会话，直接看到最新一轮结果。

---

## 2. 用户故事

1. 作为业务用户，我在 AI 回复中临时离开页面，回来后希望看到刚才那轮已经完成，而不是重问一次。
2. 作为业务用户，我点击“停止”时希望任务真正停掉，不能继续偷偷执行。
3. 作为高频使用用户，我希望登录后自动回到最近会话，减少手动翻找历史的操作。

---

## 3. 范围与边界

### 3.1 本期范围

1. 后端聊天流式链路（`/api/v1/chat/stream`）的连接与执行生命周期解耦。
2. 前端停止按钮升级为“强停止（取消 run）”语义。
3. 最近会话查询与登录后自动定位最近 `thread_id`。
4. 观测与验证：补齐单测/E2E 验证断页续跑与强停止互不冲突。

### 3.2 非目标

1. 不实现“重新打开后继续实时 token 回放”（事件重放能力，后续迭代）。
2. 不改 AI 业务决策策略、模型路由策略与 LangGraph 编排语义。
3. 不改双数据库边界：仅使用 `chat_db`，不涉及 `data_db` 写入。

---

## 4. 功能需求

### FR-01 断页续跑（Disconnect Continue）

1. SSE 客户端断开时，服务端不应将其视为用户取消。
2. 当前 run 应继续执行到自然完成或失败，并完成消息落库与 run 状态收口。
3. 断连后不得继续向已断开的连接写 token，避免无意义输出与异常噪音。

### FR-02 停止按钮强停止（Strong Stop）

1. 前端停止动作必须调用 `POST /api/v1/chat/runs/{run_id}/cancel`。
2. 停止请求成功后，服务端 run 进入 `stopping/stopped`，后续 token 不再回灌。
3. 取消接口失败时，前端自动重试 1 次并提示“停止失败，任务可能仍在后台执行”。

### FR-03 最近会话回显（Latest Thread Reopen）

1. 登录后进入聊天页时，若存在历史会话，默认打开 `updated_at` 最新的 `thread_id`。
2. 若无历史会话，保持当前空白新会话行为。
3. 历史会话加载失败时要有显式提示，并回退到可输入状态。

### FR-04 配置与降级行为

1. 运行态强停止依赖 `ENABLE_RUN_CONTROL=true`。
2. 当 `ENABLE_RUN_CONTROL=false` 时，停止按钮应降级为本地停止并明确提示语义差异。
3. `ENABLE_SSE_STOPPED_EVENT` 保持兼容可选，不作为本期上线前置条件。

### FR-05 可观测性

1. 日志必须可关联 `thread_id` 与 `run_id`。
2. 对“断连继续”“点击停止取消”“取消失败重试”分别输出关键埋点。
3. 异常路径不得吞错，需保留可诊断信息。

## 5. 验收标准

### 5.1 功能性（Happy Path）

1. 用户发起流式对话后关闭页面，后端继续执行并落库 AI 结果。
2. 用户重新登录后自动打开最近会话，能看到最新一轮结果。
3. 用户点击停止后，本轮 run 进入停止态，AI 不再继续生成。

### 5.2 异常/边界

1. 停止接口第一次失败时自动重试一次，仍失败则给出明确 toast。
2. 最近会话查询失败时，页面可继续输入，不出现“永远 loading”。
3. SSE 中断、后端异常、取消竞态下，前端状态可收口到 `idle`。

### 5.3 性能/稳定性

1. 最近会话定位不引入明显首屏阻塞（目标：额外请求可控在 200ms 量级内，超过可异步回填）。
2. 强停止路径不会引入重复取消风暴（同 run 幂等）。
3. 断页续跑不应导致 run 无上限悬挂（沿用 `orphan_timeout_seconds=600`）。

---

## 6. 非功能需求

1. 一致性：严格区分“连接断开”与“用户取消”两类语义。
2. 可维护性：run_id 贯穿前后端，避免靠隐式状态猜测取消对象。
3. 安全性：取消接口继续沿用用户权限校验（仅本人或管理员）。
4. 可回滚：通过开关回退到旧语义（run control 关闭时本地停止降级）。

## 8. 风险与缓解

1. 风险：前端未正确缓存 `run_id`，停止误取消或无法取消。
   - 缓解：`init` 事件补全类型与状态管理，缺失 `run_id` 时阻断强停止并提示。
2. 风险：断页续跑改造引入资源泄漏。
   - 缓解：执行任务统一收口、超时回收、状态埋点。
3. 风险：最近会话自动跳转影响首次空白体验。
   - 缓解：仅在有历史会话时生效，并保留用户手动新建入口。
