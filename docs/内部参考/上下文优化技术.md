# 上下文优化技术

> 这页只回答一件事：**在这个仓库里，Codex / AI 协作者怎么尽量少吃上下文，还不丢关键信息。**
>
> 不展开通用 LangChain / LangGraph 大综述；涉及产品官方能力与最新最佳实践时，以 OpenAI 官方文档为准。

---

## 1. 结论先行

| 优先级 | 默认做法 | 目的 |
|---|---|---|
| P0 | 根 `AGENTS.md` 保持短，只放总则 + 路由 | 减少每轮自动加载的固定前缀 |
| P0 | Codex 命中项目工作流时，默认优先读 `.agents/skills/*/SKILL.md` | 利用 skill 的渐进加载，避免双读镜像 |
| P0 | 搜索先走 `.rgignore` + `rg`，再按 80~200 行窗口读取 | 先缩搜索面，再缩阅读面 |
| P1 | 大真理源文档拆成 hub + 子专题，避免单页过长 | 降低“为了找一点信息整页吞”的概率 |
| P1 | 跨任务只把长期有效决策写进 `memory-bank.md` | 避免把一次性过程塞回公共上下文 |
| P1 | 高频代码区和高频测试区补短导航页 | 让模型先到 owner，再决定读哪几份文件 |

## 2. 这个仓库的默认策略

### 2.1 自动加载内容要短

当前仓库已经把自动加载和高频入口收成这几层：

1. 根 `AGENTS.md`：总则、路由、硬门禁
2. 目录级 `AGENTS.md`：只覆盖本目录树的高信号规则
3. `.agents/skills/*/SKILL.md`：Codex 运行时工作流入口
4. `.cursor/rules/*.mdc`：按主题展开的技术细则
5. `PLANS.md`：只在实现 / 测试 / 验收这类长流程时展开

一句话记住：

- **先短入口，后专题页**
- **先运行入口，后作者真理源**
- **先命中，再展开**

### 2.2 运行入口只保留一套

当前仓库的工作流说明分两套：

| 载体 | 角色 | 默认是否给 Codex 读 |
|---|---|---|
| `.agents/skills/*/SKILL.md` | Codex 运行态入口 | 是 |
| `.cursor/commands/*.md` | 命令定义真理源 | 否，除非在维护命令或查镜像漂移 |

这条边界已经在根规则里固化。

### 2.3 搜索和阅读都先缩面

当前仓库的默认做法不是“先把目录看一遍”，而是：

1. 先让 `.rgignore` 把归档、截图、锁文件、生成物、worktree 噪音排掉
2. 再用 `rg` 精确命中当前真理源、owner 文件和直接依赖
3. 命中后只读 80~200 行窗口
4. 只有明确追历史时，才显式点名归档路径

### 2.4 记忆只保留长期有效信息

`memory-bank.md` 只保留仓库级活跃决策索引，不承接：

- 一次性实现过程
- 调试过程
- 测试报告
- 临时 workaround
- 模块内部细节

这样可以避免后续会话把“历史聊天残渣”当成默认上下文重新吞一遍。

## 4. 常用 `rg` 模板

先给原则：

- 优先搜真理源和 owner
- 命中后再小窗口读
- 不默认扫归档和生成物

### 4.1 先找 AI 主链路 owner

```bash
rg -n "handoff|pending_handoff|display_blocks|skill_context" app/ai docs
```

### 4.2 先找问数链路 owner

```bash
rg -n "data_graph|data_intent|sql_safety|sql_rewriter" app/ai tests/unit docs
```

### 4.3 先找 Todo 链路 owner

```bash
rg -n "todo_graph|todo_enhanced_nodes|confirm|clarify" app/ai tests docs
```

### 4.4 先找技能 / 工作流入口

```bash
rg -n "jjk-verify|jjk-design|jjk-refactor" .agents/skills
```

### 4.5 只有维护命令定义时，才去看命令真理源

```bash
rg -n "jjk-verify|jjk-design|jjk-refactor" .cursor/commands
```

### 4.6 命中后按窗口读取

```bash
sed -n '80,180p' app/ai/workflow/multi_agent_graph.py
sed -n '60,160p' docs/API文档/接口文档_聊天与流式协议.md
```

### 4.7 只有明确追历史时，才显式点名归档

```bash
rg -n "composite-latency|ordered-content-blocks" workdocs/归档/正文/设计
```

## 5. 不建议的做法

| 坏做法 | 为什么不建议 |
|---|---|
| 默认整读大文档 | 很容易为了找 1 个点吞掉几百行无关内容 |
| 普通执行任务同时读 `.agents/skills` 和 `.cursor/commands` | 同一套说明双读，纯浪费上下文 |
| 默认扫 `workdocs/归档/`、`.worktrees/`、报告/截图目录 | 噪音高，命中价值低 |
| 把一次性实现过程写进 `memory-bank.md` | 会污染后续所有会话的默认记忆 |
| 在系统级入口重复粘完整 skill 流程 | 破坏 skill 的渐进加载优势 |

---

## 6. 为什么这样做

这是按 OpenAI 官方建议收出来的仓库本地版做法：

1. `AGENTS.md` 要短、准、可复用，过长时应拆到更靠近代码的位置
2. 可重复工作要优先收成 skill，而不是反复靠长 prompt 手动纠正
3. Prompt caching 要尽量保持稳定前缀，把动态内容后置
4. 长流程应该通过 `PLANS.md` 这类专门入口再展开，不要让根入口越来越胖

对应官方资料：

- [Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md/)
- [Codex best practices](https://developers.openai.com/codex/learn/best-practices/)
- [Customization / Skills](https://developers.openai.com/codex/concepts/customization/#skills)
- [Prompt caching best practices](https://developers.openai.com/api/docs/guides/prompt-caching/#best-practices)
- [Prompt Caching 201: Stabilize the Prefix](https://developers.openai.com/cookbook/examples/prompt_caching_201/#42-stabilize-the-prefix)
- [Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans/)

| 已落地项 | 对应文件 |
|---|---|
| 根规则瘦身为总则 + 路由 | `AGENTS.md` |
| 长流程从根规则下沉 | `PLANS.md` |
| 搜索黑名单默认生效 | `.rgignore` |
| Skill 运行入口与命令真理源分离 | `AGENTS.md`、`.cursor/rules/core.mdc` |
| `app/ai` owner map | `app/ai/AGENTS.md` |
| 高频测试入口索引 | `docs/开发文档/测试管理/测试指南与环境配置.md` |
| 仓库级快速导航 | `docs/项目上下文.md` |
| 活跃决策索引化 | `memory-bank.md` |

如果后面还要继续压上下文，优先顺序建议是：

1. 继续把高频大文拆成 hub + 子专题
2. 给更多高频目录补局部短入口
3. 把重复工作继续收成 skill，而不是再扩根规则
