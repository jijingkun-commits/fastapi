## ADR-001: 采用 Supervisor 多智能体架构

### 背景

需要支持多种类型的任务（数据分析、知识检索、待办管理），单一 Agent 难以处理所有场景。

### 决策

采用 **Supervisor 模式** 的多智能体架构：
- Supervisor 负责意图理解和任务路由
- 专家 Agent 专注于各自领域
- 使用 Handoff Tools 进行任务委派

### 理由

1. **职责分离**: 每个 Agent 专注于特定领域，提示词更精确
2. **可扩展性**: 添加新能力只需注册新 Agent
3. **Token 效率**: Handoff 只传递任务描述，不共享完整历史

### 后果

- 需要维护 `AgentType` 枚举和 `AGENT_DESCRIPTIONS`
- 新增 Agent 需要在 `create_multi_agent_graph()` 中注册
- **更新**: 见 ADR-006，已简化架构

## ADR-002: SSE 事件协议设计

### 背景

需要支持流式输出、工具调用显示、结构化结果渲染等多种交互。

### 决策

设计结构化的 SSE 事件类型：

```
event: {type}
data: {"type": "...", "data": {...}, "node": "..."}
```

### 事件类型

- `token`: 流式文本
- `thinking`: 思考过程
- `tool_start/tool_end`: 工具调用
- `status`: 状态更新
- `result`: 结构化结果
- `confirmation/clarification`: 用户交互
- `interrupt`: 人机协作中断

### 理由

1. **统一格式**: 前端可以用统一的解析逻辑
2. **可扩展**: 添加新事件类型不影响现有逻辑
3. **调试友好**: 每个事件包含来源节点 `node`

### 后果

- 后端使用 `app/ai/events.py` 中的 emit_* 函数
- 前端在 `useSSEStream.ts` 中处理各类事件

## ADR-003: 待办工具返回字符串格式

### 背景

LangChain Tool 的输出需要被 LLM 理解和使用。

### 决策

所有待办工具返回**格式化的字符串**，而非 JSON：

```python
# 成功
"✅ 成功创建待办事项：「周一开会」\n  ID: 123\n  截止: 2024-01-15 09:00"

# 列表
"📋 找到 3 条待办事项：\n\n1. [ID:101] 周一开会 ⏰ 01-15\n..."
```

### 理由

1. **LLM 可读性**: 格式化文本比 JSON 更易于 LLM 理解
2. **直接展示**: 可以直接在对话中展示给用户
3. **包含图标**: 使用 Emoji 增强可读性

### 后果

- 工具不返回结构化数据给 LLM
- 如需结构化显示，使用 `emit_result` 发送额外事件

## ADR-004: MinIO 图片引用机制

### 背景

AI 生成的图片存储在 MinIO，需要在对话中展示。

### 决策

采用**两阶段引用机制**：

1. **工具输出**: 使用 `<<IMG_REF:N:minio://...>>` 元数据
2. **Token 流**: 使用 `##N$$` 占位符
3. **前端处理**: 替换为实际 Markdown 图片

### 数据库存储

使用 `minio://` 协议格式（持久化）：
```
minio://chat-assets/user123/thread456/charts/fig_123.png
```

### 理由

1. **分离关注点**: 工具输出元数据，LLM 生成引用
2. **预签名 URL**: 避免暴露 MinIO 直接地址
3. **过期管理**: 预签名 URL 有过期时间

### 后果

- 使用 `ImageInsertionStreamProcessor` 处理图片替换
- `AssetService` 负责 URL 转换

## ADR-005: Human-in-the-loop 中断恢复机制

### 背景

某些操作（如删除待办、执行 SQL）需要用户确认。

### 决策

使用 LangGraph 的 **Interrupt** 机制：

1. 工具返回 `Command(interrupt=...)` 暂停执行
2. 前端接收 `interrupt` 事件，显示确认 UI
3. 用户决定后调用 `resume` API 继续

### 决定类型

```typescript
type DecisionType = 
  | { type: "accept" }           // 批准
  | { type: "reject", message?: string }  // 拒绝
  | { type: "edit", args: {...} }  // 修改参数
```

### 理由

1. **安全性**: 危险操作需要用户确认
2. **可编辑**: 用户可以修改操作参数
3. **原生支持**: LangGraph 内置 Interrupt 机制

### 后果

- 工具使用 `from langgraph.types import Command, interrupt`
- 前端使用 `CompactApproval` 组件展示确认 UI
- 后端使用 `sse_resume_stream` 恢复流程

### 消息保存职责（2026-01 补充）

**重要约束**：消息持久化遵循以下规则。

| 组件 | 职责 | 保存内容 | 标记 |
|------|------|---------|------|
| `sse_stream` (interrupt) | 保存中间状态 | Human + 中间 AI | `is_intermediate: true` |
| `_postprocess` 节点 | 保存最终消息 | 最终 AI 消息 | 无 |
| `sse_resume_stream` | 流式传输 | ❌ 不保存 | - |
| `get_messages_by_thread` | 查询历史 | 默认过滤中间消息 | - |

**中间消息机制**：
- interrupt 场景的 AI 消息标记 `metadata.is_intermediate: true`
- 查询历史时使用 `COALESCE(metadata->>'is_intermediate', 'false') NOT IN ('true')` 过滤
- 参考：LangGraph 官方 Agent Chat UI 的 `do-not-render-` 前缀设计

> **背景**：早期实现中 `sse_resume_stream` 也保存 AI 消息，导致 interrupt-resume 场景下产生重复记录。修复方案：(1) 移除 resume 层的保存；(2) interrupt 时的中间消息标记为 `is_intermediate`，查询时过滤。

## ADR-006: Supervisor 架构简化

### 背景

原架构中 Supervisor 仅作为路由器，所有任务都需要委派给专家 Agent。这导致：
1. 简单任务（如"画一个圆形"）也需要多次跳转
2. 增加了不必要的延迟和 Token 消耗
3. `knowledge_expert` 实际上只调用一个工具，没有多步推理

### 决策

简化架构：
1. **Supervisor 直接绑定简单工具**：`fig_inter`, `sql_inter`, `knowledge_search`
2. **移除 `knowledge_expert`**：知识库搜索由 Supervisor 直接处理
3. **保留 `data_expert`**：仅用于需要多步骤的复杂分析
4. **保留 `todo_expert`**：保留确认流程

### 架构对比

**旧架构**：Supervisor → [data_expert, knowledge_expert, todo_expert]
**新架构**：Supervisor（含简单工具）→ [data_expert, todo_expert]

### 理由

1. **性能**: 简单任务减少 1-2 秒延迟
2. **Token 效率**: 减少不必要的 Agent 对话
3. **判断标准清晰**: 需要多步推理才委派

### 后果

- `_get_supervisor_tools()` 返回 Supervisor 可直接使用的工具
- `_get_data_expert_tools()` 只返回多步骤分析工具
- Supervisor prompt 需要明确说明何时直接处理、何时委派

## ADR-008: Supervisor Prompt 决策树不可轻易修改

### 背景

2026-01-29 调试 Todo Agent 路由问题时，错误地修改了 `SUPERVISOR_PROMPT` 中的决策树结构，导致所有待办请求无法被正确路由。

### 问题过程

1. **初始症状**：用户发送"列出我的待办"后，未被路由到 Todo Agent
2. **错误诊断**：认为是决策树不够明确，尝试添加"优先判断"节点
3. **错误修改**：
   - 删除原有的"待办事项管理"节点
   - 添加复杂的"优先判断"结构
   - 修改 `multi_agent_graph.py` 的事件流处理
4. **实际结果**：问题加剧，路由完全失效

### 决策

**Supervisor Prompt 决策树属于核心架构，修改需遵循严格流程**：

1. **禁止直接修改**：不能在调试过程中随意修改决策树
2. **先排查配置**：路由问题优先检查环境配置（端口、模块导入等）
3. **保持结构稳定**：原有决策树经过验证，结构已经稳定
4. **修改需评审**：如确需修改，需单独评审并测试

### 正确的调试顺序

| 顺序 | 检查项 | 文件 |
|------|--------|------|
| 1 | 服务状态 | `curl localhost:8089/health` |
| 2 | 端口配置 | `web/.env` |
| 3 | 模块导入 | `app/ai/config/__init__.py` |
| 4 | 日志分析 | `logs/assistant.log` |
| 5 | Prompt 文件 | `agent_prompts.py`（只读检查） |

### 恢复方法

```bash
# 快速恢复核心文件
git checkout app/ai/prompts/agent_prompts.py
git checkout app/ai/workflow/multi_agent_graph.py
```

### 理由

1. **决策树是 LLM 的指令**：微小的格式变化可能导致 LLM 理解偏差
2. **经过验证**：原有结构已在生产环境验证
3. **改动成本高**：修改后需要完整的回归测试

### 后果

- 路由问题排查需遵循标准流程
- 决策树修改需要单独的 PR 和测试
- 调试文档中增加相关警告

## ADR-007: 采用 Clawdbot 技能定义与架构思想

### 背景

项目需要扩充 AI 技能库，且希望保持与社区标准兼容，实现"Self-hosted & Agentic"的愿景。调研发现 Clawdbot 提供了成熟的技能定义和架构模式。

### 决策

1.  **技能定义**: 完全采用 Clawdbot 的 `SKILL.md` 标准 (YAML Frontmatter + Markdown)，位于 `app/ai/skills/<skill_id>/SKILL.md`。
2.  **架构借鉴**: 参考 Gateway 模式，未来支持 WebSocket 网关以连接多渠道 (Telegram/Slack)。
3.  **自我进化**: 远期规划实现 Agent 自行编写 `SKILL.md` 的能力。

### 理由

1.  **生态兼容**: 可直接复用 `awesome-cursorrules` 等社区高质量 Prompt/Skill。
2.  **维护统一**: 系统内置技能与扩展技能结构一致。
3.  **扩展性**: Gateway 模式解决了内网服务对接公网 IM 的问题 (配合 Tailscale)。

### 后果

- 已将 `Clawdbot集成提案.md` 归档并删除。
- 需维护 `skills` 目录结构。

## ADR-009: Todo Agent 工具调用架构选型

### 背景

LangGraph 提供了预构建的 `ToolNode` 用于标准 ReAct Agent 模式。在深度审查 Todo Agent 代码时，评估是否应该采用 ToolNode 重构工具调用。

### 决策

**不采用** LangGraph `ToolNode`，保持当前 `execute_operation` 节点中的手动工具调用方式。

### 备选方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| ToolNode | 标准化、自动错误处理、并发支持 | 不支持执行前确认、结果格式受限 |
| 当前方案 | 完全可控、支持确认流程、自定义结果格式 | 需手动处理并发和错误 |

### 理由

1. **架构不兼容**: 当前是"意图驱动"架构，工具参数来自 `pending_operation.data`（由 `analyze_intent` 构造），而 ToolNode 期望 LLM 直接生成 `tool_calls`

2. **丧失确认流程**: Todo Agent 在执行前有 `ask_confirmation` → `wait_for_confirmation` 环节，ToolNode 无法在工具执行前插入确认逻辑

3. **结果格式限制**: 需要自定义 `ToolResult(data_type, data, message)` 用于前端卡片渲染，ToolNode 返回标准 `ToolMessage(content)` 格式

4. **SSE 事件控制**: 当前通过 `emit_result()` 在 `execute_operation` 集中发送事件，若使用 ToolNode 需将逻辑侵入每个工具内部

### 后果

- 保持 `app/ai/workflow/todo_graph.py` 中 `execute_operation` 节点的实现
- 可借鉴 ToolNode 优点：封装统一的 `ToolExecutor` 类处理错误和日志
- 工具定义继续使用 `@tool` 装饰器 + Pydantic Schema
