## 维度 1：三层真理源设计（L1/L2/L3）

**评分：8/10**

### 优点

1. **层级关系定义清晰**：L1（`_active_task.json`，作用域）> L2（`vk_cards.json`，卡片定义）> L3（`task-runner-state.json`，运行时状态），高层级信息决定低层级的读取范围，这是一个合理的信息级联模型。Ch 3.5 的层级规则表（写入者/读取者）让职责归属一目了然。

2. **冗余字段设计合理**：`task-runner-state.json` 中冗余存储 `task_key` 和 `card_order`（原本从 L1/L2 读取），减少跨文件读取频率。Ch 4.7 的迁移映射表明确标注了哪些是"新增冗余"字段，设计意图透明。

3. **从五方一致性简化为三层层级**：将原来散落在 5 个数据源（含 VK 远程 API）的状态收敛为 3 个本地文件，从根本上消除了远程 API 不可用导致的一致性问题。

### 不足

1. **跨层一致性保障缺失**：当 L1 的 `task_key` 变更时（如切换任务），L3 的 `task_key` 冗余字段如何同步？文档未定义"L1 变更 → L3 级联更新"的触发机制。如果 `scope_guard.py` 检测到 L1 变更但 L3 未更新，会进入什么状态？

2. **L2 的不可变性假设未显式声明**：`vk_cards.json` 由 `/jjk-vkplan` 生成，在任务执行期间是否允许修改？如果用户在执行中途调整卡片顺序或依赖关系，L3 中缓存的 `card_order` 会与 L2 不一致。文档应明确 L2 在任务生命周期内的不可变性约束。

3. **缺少一致性校验入口**：虽然从五方简化为三层，但文档未提供一个统一的"三层一致性校验"函数（类似原来的五方校验），用于 bootstrap_kernel 每轮启动时验证三层数据的一致性。

## 维度 2：hooks-first 触发器架构

**评分：9/10**

### 优点

1. **决策边界极其明确**：Ch 3.2 的三种触发器能力拆分表从 7 个维度（触发延迟、参数控制、会话模式、适用场景、调用方、幂等性、源码位置）对比了 `/hooks/wake`、`/hooks/agent` 和 cron，每个触发器的适用场景无歧义。"wake 覆盖 95%+ 场景"的量化判断有说服力。

2. **降级链设计完整**：Ch 11.4 的四级降级链（L0 正常 → L1 重试 → L2 降级到 agent → L3 cron watchdog 兜底）覆盖了所有故障场景，每级都有明确的触发条件和等待时间。这是全文设计最成熟的部分。

3. **幂等性分析到位**：明确标注 `/hooks/wake` 是幂等的（重复调用安全），`/hooks/agent` 不是（每次创建新 turn），这对调用方的错误处理策略至关重要。

4. **cron 降级为 watchdog 的决策有据可依**：从 `*/3`（每 3 分钟盲触发）改为 `0 * * * *`（每小时巡检），配合 `last_heartbeat_at` 字段检测链路存活，既消除了空转浪费，又保留了最后防线。

### 不足

1. **`/hooks/wake` 的 `mode` 参数语义未完整定义**：Ch 3.2 提到 `mode` 参数但仅使用了 `"now"`，未说明是否存在其他 mode 值及其语义。如果 OpenClaw 支持其他 mode（如 `"queue"`），应在文档中明确排除或说明。

## 维度 3：bootstrap_kernel 8 模块拆分

**评分：7/10**

### 优点

1. **模块职责表清晰**：Ch 5.1 的 8 模块表从输入、输出、失败处理三个维度定义了每个模块的契约，便于独立测试和替换。

2. **`--local-mode` 行为矩阵设计精巧**：Ch 5.3 的矩阵清晰定义了每个模块在两种模式下的行为差异，过渡期策略（Phase 1 默认 local-mode，Phase 3 移除 vk-api-base）渐进合理。

3. **`heartbeat_turn()` 伪代码完整**：Ch 5.4 的伪代码覆盖了所有 action 分支（preflight_blocked、all_done、blocked_depends、seed、activate、dispatch），每个分支都有明确的返回值和副作用。

### 不足

1. **`dispatch_coder4` 的职责边界仍然模糊**：文档说"仅负责触发 OpenClaw/Codex 执行，不包含业务逻辑"，但 Ch 5.6 的时序图显示 `dispatch_coder4` 实际上需要协调 `wt-flow.sh create` → Codex 执行 → `wt-flow.sh merge` 的完整生命周期。这不是简单的"触发"，而是"编排"。建议明确 dispatch_coder4 是"执行编排器"而非"触发器"。

2. **模块间依赖关系未图示化**：8 个模块之间的调用关系（谁调用谁、数据如何流转）缺少一张依赖图。当前只能从 `heartbeat_turn()` 伪代码中推断调用链，不够直观。

3. **错误传播策略不统一**：`load_context` 失败即阻断，`sync_to_vk` 失败静默，`dispatch_coder4` 超时由下一轮重试——三种不同的错误处理策略分散在各模块中，缺少一个统一的错误处理框架或策略枚举。

## 维度 4：task-runner-state.json Schema 设计

**评分：8/10**

### 优点

1. **字段设计完备**：Ch 4.2 的 14 个字段覆盖了任务标识（task_key）、执行状态（current_card、card_status）、执行模式（execution_mode、single_active_card）、健康监控（no_increment_count、last_heartbeat_at）和元信息（schema_version、created_at）。每个字段都有类型、必填、默认值和说明。

2. **状态枚举和迁移图完整**：Ch 4.3-4.5 定义了 5 个状态（todo → in_progress → in_review → done / blocked），状态迁移图用 mermaid stateDiagram 可视化，每条迁移边都有触发条件、执行者和副作用。`in_review` 状态的引入（区分"执行完成"和"验收通过"）是一个好的设计决策。

3. **`schema_version` 字段为未来升级预留**：版本化管理是状态文件的最佳实践，`load_local_card_status()` 中的版本校验（`version.startswith("1.")`）确保了向后兼容。

4. **字段迁移映射表（Ch 4.7）**：从 `coder4_cron_state.json` 到 `task-runner-state.json` 的逐字段迁移映射，标注了"直接迁移"和"新增"，降低了迁移遗漏风险。

### 不足

1. **缺少并发写入保护**：原子写入（Ch 4.6）解决了"写入中断"问题，但未解决"并发写入"问题。如果 cron watchdog 和 hooks 触发的两轮执行同时写入 `task-runner-state.json`，`os.rename` 的原子性只保证单次写入完整，不保证两次写入的顺序正确。建议增加文件锁（`fcntl.flock`）或 PID 文件互斥。

2. **schema 迁移机制未定义**：`schema_version` 字段预留了版本化能力，但文档未定义从 `1.0.0` 升级到 `1.1.0` 或 `2.0.0` 时的迁移脚本或自动升级逻辑。当 Schema 需要新增字段或修改类型时，如何处理已有的状态文件？

3. **`last_heartbeat_at` 的更新时机不明确**：该字段供 watchdog 检测链路存活，但文档未明确是在 `heartbeat_turn()` 入口更新还是出口更新。如果在入口更新，长时间执行的 turn 不会被误判为停滞；如果在出口更新，执行中的 turn 可能被 watchdog 误触发。

## 维度 5：原子写入策略

**评分：8/10**

### 优点

1. **Python 侧实现规范**：Ch 4.6 的 `atomic_write_json()` 实现了完整的原子写入链：备份现有文件（`.bak`）→ 写入临时文件（同目录 `tempfile.mkstemp`）→ `f.flush()` + `os.fsync()` → `os.rename()`。同目录确保同一文件系统（POSIX rename 原子性前提），`fsync` 确保数据落盘。

2. **异常清理完备**：`try/except` 中清理临时文件，防止 `.tmp` 文件泄漏。

3. **`.bak` 备份提供额外安全网**：即使原子写入本身失败，`.bak` 文件可用于手动恢复。

### 不足

1. **bash 侧原子写入存在空输出风险**：交叉审查（worker-2）已指出 Ch 6.3 的 `jq > tmp && mv tmp file` 模式在 `jq` 输出为空时仍会执行 `mv`，导致状态文件被清空。建议采纳审查建议增加 `[[ -s "$state_file.tmp" ]]` 非空校验。

2. **attempt 文件的原子写入未明确**：Ch 7.4 的 `create_attempt()` 调用了 `atomic_write_json()`，但 Ch 6.4 的 `verify` 子命令中 `gate_result.json` 的写入使用了 `echo > file` 直接写入，未使用原子写入。虽然 `gate_result.json` 的损坏影响较小（可重新执行 verify），但应保持一致性。

## 维度 6：3000 字符 payload 分解方案

**评分：7/10**

### 优点

1. **五块语义拆分逻辑清晰**：附录 B.1 将 3000 字符 payload 分解为固定真理源路径（~300）、硬顺序执行协议（~800）、分支决策矩阵（~1000）、硬约束清单（~600）、输出格式模板（~300），每块都有明确的迁移目标。

2. **迁移原则合理**：固定约束 → `AGENTS.md`（不可被 LLM 修改），执行协议 → `WORKFLOW_AUTO.md`（可按需读取），输出模板 → `VK_AGENT_PROMPTS.md` 重写后的 section。这种分层策略确保了关键约束不会被 LLM 在执行过程中意外修改。

3. **迁移后 payload 大幅简化**：从 3000 字符降至 ~500 字符的 watchdog 巡检指令，降低了 cron payload 的复杂度和出错概率。

### 不足

1. **缺少逐条迁移对照 checklist**：交叉审查（worker-1）已指出风险 R8 的缓解措施为"逐条对照迁移"，但文档未提供具体的对照表（原约束编号 → 新位置 → 验证方式）。这是 payload 迁移最大的风险点——遗漏一条关键约束可能导致 LLM 行为偏移。

2. **`AGENTS.md` 的加载机制未说明**：固定约束迁移到 `AGENTS.md` 后，OpenClaw/Codex 如何确保每轮执行都加载该文件？如果 `AGENTS.md` 不在 heartbeat 的上下文窗口中，约束就形同虚设。文档应明确 `AGENTS.md` 的加载路径和优先级。

3. **分支决策矩阵（~1000 字符）的迁移验证难度高**：7 个 action 分支的行为定义从 cron payload 迁移到 `WORKFLOW_AUTO.md` 后，如何验证 LLM 在新上下文中的决策行为与旧 payload 一致？文档提到"A/B 对比测试"但未定义具体的测试方法和通过标准。

## 维度 7：attempt 系统本地化设计

**评分：8/10**

### 优点

1. **能力对比表完整**：Ch 7.3 逐项对比了 VK attempt 的 7 项能力，6 项有本地替代方案，1 项（Web UI 查看）明确标注为"命令行替代"。诚实标注未覆盖的能力比隐瞒更有价值。

2. **`worktree_path` 替代 `container_ref` 设计合理**：VK 的 `container_ref` 指向远程容器，本地方案用 worktree 绝对路径替代，语义等价且更简单。`create_attempt()` 的实现（Ch 7.4）逻辑完整。

3. **attempt JSON Schema 字段丰富**：Ch 7.2 的 Schema 包含 11 个字段，覆盖了执行历史（started_at/ended_at）、结果（result/evidence）、环境（worktree_path/commit_sha）和元信息（trigger/duration_seconds）。`trigger` 字段记录触发方式（hooks_wake/hooks_agent/cron_watchdog）是一个好的可观测性设计。

### 不足

1. **跨会话查询能力降级明显**：VK 提供 Web UI 和 REST API 查询 attempt 历史，本地方案仅支持 `ls` + `cat` + `jq` 命令行查询和 Telegram 查询。对于需要快速浏览多张卡片执行历史的场景，命令行体验远不如 Web UI。

2. **attempt 文件的清理策略未定义**：随着卡片执行轮次增加，`attempts/` 目录下的文件会持续增长。文档未定义清理策略（如保留最近 N 个 attempt、归档已完成卡片的 attempt 等）。

3. **`gate_result.json` 与 `attempt_NNN.json` 的关系不明确**：每张卡片目录下既有多个 `attempt_NNN.json` 又有一个 `gate_result.json`（最近一次 done_gate 结果）。`gate_result.json` 是否应该内嵌到对应的 `attempt_NNN.json` 中？当前设计存在两个文件记录同一次验收结果的冗余。

## 维度 8：分阶段实施路线图（Phase 0-3）

**评分：8/10**

### 优点

1. **Phase 划分逻辑严密**：P0（触发器切换）→ P1（核心本地化）→ P2（仓外清理）→ P3（VK 只读降级），每个 Phase 都有明确的目标、验收标准和回滚方案。Phase 之间的依赖关系合理——P0 验证 hooks 可用性是 P1 的前提，P1 完成本地化是 P2 剥离 VK 语义的前提。

2. **每个 Phase 都有回滚方案**：P0 回滚改 cron expr，P1 回滚移除 `--local-mode`，P2 回滚从 git 恢复仓外文件，P3 回滚禁用 vk_sync。回滚方案的粒度与 Phase 粒度匹配，可操作性强。

3. **Gantt 图可视化依赖关系**：Ch 13.1 的 Gantt 图清晰展示了各步骤的并行和串行关系（如 P1 中 wt-flow.sh 扩展与 bootstrap_kernel 改造可并行），有助于资源调度。

4. **工时估算采用三点估算法**：乐观/悲观/期望值的三点估算比单点估算更可靠，且与评审报告的独立估算做了对照。

### 不足

1. **P2 仓外文件回滚方案依赖手动备份**：P2 的回滚方案是"从 git 恢复仓外文件（需提前备份到 `.omc/backup/`）"，但仓外文件（`~/.openclaw/workspace-dev/`）不在 git 管理范围内。如果忘记提前备份，P2 不可回滚。建议在 P2 开始前增加自动备份步骤。

2. **缺少 Phase 间的验收门禁**：每个 Phase 内部有验收标准，但 Phase 之间的切换条件未明确。例如，P0 的哪些验收标准必须全部通过才能进入 P1？如果 P0.2（`/hooks/agent` 验证）失败但 P0.1 通过，是否可以进入 P1（仅使用 `/hooks/wake`）？

3. **工时估算可能偏乐观**：P2 的 WORKFLOW_AUTO.md（460 行 33 条规则）和 VK_AGENT_PROMPTS.md（628 行 21 个 section）重写估算为 4-5 天，但这些文件直接影响 LLM 行为，每条规则的重写都需要验证 LLM 行为一致性。如果 A/B 测试发现行为偏移，修复周期可能远超估算。

## 维度 9：风险矩阵

**评分：7/10**

### 优点

1. **核心风险已识别**：R1（gateway 不可用）、R2（非原子写入）、R3（LLM 行为偏移）、R8（payload 迁移遗漏）四个高风险项与评审报告的 TOP 3 风险完全对齐，缓解措施具体可操作。

2. **风险热力图可视化**：Ch 12.2 的四象限热力图直观展示了风险分布，便于优先级排序。

3. **缓解措施有优先级和时机**：Ch 12.3 的缓解措施表标注了 P0/P1/P2/P3 的实施时机，确保高优先级缓解措施在对应 Phase 开始前就位。

### 不足

1. **缺少运维类风险**：
   - **R9（未识别）：OpenClaw 升级导致 hooks API 行为变更**。当前方案深度依赖 `/hooks/wake` 和 `/hooks/agent` 的行为（源码位置 `server-http.ts:324-332`、`server/hooks.ts:32-107`），但 OpenClaw 不可修改源码（约束 C1），如果 OpenClaw 升级改变了 hooks API 的行为或参数，整个触发层需要重新适配。
   - **R10（未识别）：`heartbeat.prompt` 字段被 OpenClaw 更新覆盖**。如果 OpenClaw 的配置更新机制会重置 `heartbeat.prompt`，注入的行为约束会丢失。

2. **缺少数据迁移类风险**：
   - **R11（未识别）：`coder4_cron_state.json` → `task-runner-state.json` 迁移期间的状态丢失**。Ch 4.7 定义了字段映射，但未定义迁移脚本和迁移期间的双写策略。如果迁移过程中 cron 触发了一轮执行，可能读到不完整的状态。

3. **风险概率评估缺少依据**：R1（gateway 不可用）标注为"中概率"，但未给出历史故障数据或 SLA 指标。R3（LLM 行为偏移）标注为"中概率"，但 prompt 重写导致行为偏移在实践中是高概率事件。建议补充概率评估的依据。

## 总体评价

### 架构亮点

1. **hooks-first + cron-watchdog 的混合触发架构**是全文最成熟的设计，决策边界清晰、降级链完整、幂等性分析到位，可直接落地。

2. **三层真理源的层级模型**从根本上解决了五方一致性的脆弱性问题，将远程 API 依赖完全消除，是正确的架构方向。

3. **VK 只读降级的 fire-and-forget 策略**优雅地处理了"保留可视化能力但不依赖其可用性"的需求，推送失败不阻断执行是关键的解耦决策。

4. **文档质量高**：1917 行文档结构清晰，每章都有代码示例、mermaid 图和表格，交叉引用准确，交叉审查记录透明。

### 需要加强的领域

1. **并发控制**：多处设计假设了单线程执行（cron watchdog 和 hooks 不会同时触发），但实际运行中并发写入 `task-runner-state.json` 的风险真实存在。建议增加文件锁或 PID 互斥机制。

2. **迁移对照清单**：3000 字符 payload 的逐条迁移是最高风险操作，当前缺少可执行的 checklist。建议在附录 B 中增加"原约束编号 → 新位置 → 验证方式"的三列对照表。

3. **bash 与 Python 的一致性**：Python 侧的原子写入实现规范，但 bash 侧（wt-flow.sh 的 next/verify 子命令）的状态文件操作未达到同等安全级别。建议统一为 Python 调用或在 bash 中增加防护。

4. **运维风险补充**：OpenClaw 升级兼容性、heartbeat.prompt 持久性、状态迁移期间的双写策略等运维类风险需要补充到风险矩阵中。

### 最终结论

总体评分 **7.8/10**。这是一份高质量的可执行设计方案，核心架构决策（hooks-first、三层真理源、VK 只读降级）有充分的前置研究支撑，分阶段实施路线图可落地。主要改进方向集中在并发控制、迁移对照清单和运维风险补充三个领域，均为可操作的增量改进，不影响整体架构的正确性。
