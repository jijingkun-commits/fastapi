## 维度 1：模块边界与职责分离

**v1 评分：8/10 → v2 评分：8.5/10（+0.5）**

### 修正效果评估

**1.1 `scope_guard_check()` 新增（Ch 5.2.2）——职责明确，设计质量良好**

Ch 5.2.2 新增的 `scope_guard_check()` 函数（L543-561）专门处理 `_active_task` 的 ALL_DONE 边界条件。该函数：
- 输入明确：`state`、`card_order`、`card_status` 三个参数，纯计算无副作用
- 输出语义清晰：`SCOPE_COMPLETE`（真正完成）、`GATE_PHASE`（过渡状态）、`CONTINUE`（正常继续）
- 职责单一：仅负责判断作用域状态，不执行任何状态变更

状态组合矩阵（L534-538）覆盖了三种关键场景，特别是"ALL_DONE + Gate 未完成"的过渡状态处理，直接回应了代码实证报告 M2 的发现。`pending_gates` 和 `pending_impl` 的分离判断逻辑清晰。

**不足**：`GATE_PHASE` 返回后的下游处理未在 `heartbeat_turn()` 伪代码（Ch 5.4）中体现。`heartbeat_turn()` 的 `decide_action()` 如何消费 `GATE_PHASE` 信号？当前设计中 `scope_guard_check()` 与 `decide_action()` 的调用关系未显式定义。

**1.2 `_hooks_headers()` 辅助函数（Ch 9.2 L1441-1445）——引入合理，但存在内部不一致**

`_hooks_headers()` 将认证 header 构造逻辑集中到一个函数中，被 `trigger_next_round()`（L1453）和 `trigger_agent_turn()`（L1495）复用。这是正确的职责封装——认证逻辑不应散落在每个调用点。

然而，文档内部存在三处认证 header 构造的实现，风格不统一：
- Ch 9.2 L1441：`_hooks_headers()` 函数，模块级常量 `OPENCLAW_HOOKS_TOKEN`
- Ch 5.4 L675：`_try_trigger_next()` 内联构造，局部变量 `token = os.getenv(...)`
- Ch 14.2 L1901：`_headers()` 函数，模块级常量 `TOKEN`

三处实现语义等价但命名和作用域不同。实施时应统一为 `_hooks_headers()` 单一入口。

**1.3 `dispatch_coder4` 职责澄清（Ch 5.1 + Ch 5.6）——v1 不足已改善**

v1 报告指出 `dispatch_coder4` 的职责边界模糊（"触发"vs"编排"）。修正后方案在 Ch 5.1 明确限定其为"执行委托接口"，Ch 5.6 新增时序图清晰展示了 `dispatch_coder4` → OpenClaw → Codex → `wt-flow.sh` 的完整交互链。关键澄清："dispatch_coder4 的职责是'触发执行'，不是'执行代码'"（L730）。

**1.4 8 模块拆分——v1 优点保持**

Ch 5.1 的 8 模块表（L449-458）从输入、输出、失败处理三个维度定义契约，质量保持。新增的 `sync_to_vk` 模块（#8）明确标注"失败静默"，与 fire-and-forget 策略一致。

### 仍存在的不足

1. **模块间依赖图仍缺失**：v1 指出的"8 个模块之间的调用关系缺少依赖图"问题未修正。虽然 Ch 6.8 的时序图展示了 `bootstrap_kernel` 与 `wt-flow.sh` 的交互，但 8 个内部模块之间的调用链仍需从 `heartbeat_turn()` 伪代码推断。
2. **错误传播策略不统一**：v1 指出的三种不同错误处理策略（阻断/静默/重试）仍分散在各模块中，未提炼为统一的错误处理框架。Ch 11 的错误分类表（L1630-1638）是改善，但与模块定义表（Ch 5.1）未形成显式映射。

- `"next-heartbeat"`：低优先级通知，如 VK 只读同步

### 未提升评分的原因

**2.5 `_hooks_headers()` 的 warning 日志承诺未兑现**

R12 缓解措施（L1723）声称"`_hooks_headers()` 在 token 为空时输出 warning 日志"，但实际代码（L1441-1445）在 token 为空时静默返回空 dict，无任何日志输出。同样，`_try_trigger_next()`（L675-676）和前置验证脚本的 `_headers()`（L1901-1905）也无 warning。

这是文档与代码示例的内部不一致。token 为空时静默发送无认证请求，将收到 401 但错误信息仅在 `except` 块中以通用 warning 输出（L1459："hooks/wake 触发失败"），不会明确指出"token 未配置"这一根因。实施时应在 `_hooks_headers()` 中增加：

```python
if not OPENCLAW_HOOKS_TOKEN:
    logger.warning("OPENCLAW_HOOKS_TOKEN 未配置，hooks 调用将收到 401")
```

**2.6 降级链 L2 层级的认证失败行为未定义**

Ch 11.4 的降级链（L1679-1702）定义了 L0→L1→L2→L3 四级降级。但当 `/hooks/wake` 因 401（认证失败）而非网络超时失败时，重试 3 次（L1 层级）是无意义的——token 错误不会因重试而修复。降级链应区分"可重试错误"（超时、5xx）和"不可重试错误"（401、403），后者应直接跳到 L3（cron watchdog）。

这两个问题使得 v1 的 9 分无法进一步提升，但也不构成降分理由（核心架构正确性不受影响）。

## 维度 4：错误处理与恢复

**v1 评分：8/10 → v2 评分：8.5/10（+0.5）**

### 修正效果评估

**4.1 R12 Token 配置风险缓解——体系完整**

R12（L1723）的缓解措施形成了四层防御：
1. **预防层**：P0 前置验证脚本（Ch 14.2 L1907-1909）在实施前检查 token 配置
2. **检测层**：`_hooks_headers()` 在 token 为空时应输出 warning（虽然代码示例未兑现，但意图正确）
3. **降级层**：hooks 调用失败不阻断主流程（fire-and-forget 模式）
4. **兜底层**：cron watchdog 作为无 token 依赖的兜底路径

特别值得肯定的是"cron watchdog 作为无 token 依赖的兜底路径"这一设计——cron 由 OpenClaw 内部调度，不经过 gateway hooks 认证，因此 token 失效时 cron 仍能正常触发 heartbeat。这是一个精巧的架构决策。

**4.2 hooks 降级链在认证失败场景下的行为——部分覆盖**

如维度 2 中分析，降级链未区分 401（认证失败）和 5xx/超时（可重试错误）。但 L3 兜底层（cron watchdog）的存在确保了即使降级链的 L1 重试浪费了时间，最终仍能恢复。最坏情况是浪费 14 秒（2+4+8 秒指数退避）后等待最多 60 分钟的 cron 触发。

**4.3 并发写入保护——v1 重大缺口已填补**

v1 报告指出"缺少并发写入保护"。Ch 6.7.1（L985-1025）新增了完整的文件锁方案：
- bash 侧：`flock -w 10 200`（L997），10 秒超时
- Python 侧：`fcntl.flock(lock_fd, fcntl.LOCK_EX)`（L1020），`atomic_write_json_locked()` 封装

bash 和 Python 使用相同的 `.lock` 文件路径约定，确保跨语言互斥。这是 v1 评估中"需要加强的领域 #1"的直接回应。

### 仍存在的不足

1. **R11 迁移期间的双写策略仍偏简单**：R11 缓解措施（L1722）是"暂停 cron → 迁移 → 恢复 cron"。这要求迁移窗口内无任何触发，但如果用户通过 Telegram 手动触发了 heartbeat，仍可能读到不完整状态。建议增加迁移锁文件（如 `.omc/state/.migrating`），`load_context()` 检测到该文件时返回 `BLOCKED_MIGRATION`。
2. **`flock` 超时后的行为未定义**：bash 侧 `flock -w 10` 超时后返回错误码 1，但调用方（`update_state()`）仅输出 `ERROR` 并 return 1，未定义上层如何处理。是重试？还是进入 BLOCKED？

### 未提升评分的原因

1. **warning 日志承诺未兑现**（同维度 2 分析）：R12 声称的 token 空值 warning 在代码示例中不存在。
2. **attempt 文件清理策略（Ch 7.1.1）虽已补充，但监控告警阈值偏高**：100MB 磁盘空间告警阈值（L1125）对于 JSON 文件目录来说过于宽松。按每个 attempt 文件约 500 字节计算，100MB 意味着约 20 万个文件，远超正常运行范围。建议降至 10MB 或按文件数量告警。
3. **缺少 hooks 调用的结构化日志**：当前 hooks 调用的日志仅有 `logger.info` 和 `logger.warning`，缺少结构化字段（如 `hook_type`、`response_code`、`latency_ms`）。对于运维排查，结构化日志比自由文本更有价值。

### 仍然存在的架构薄弱点

**薄弱点 1：文档内部代码示例的一致性（中等风险）**

三处认证 header 构造实现风格不统一（`_hooks_headers()` / `_try_trigger_next()` 内联 / `_headers()`），R12 声称的 warning 日志在代码示例中不存在。这类文档-代码不一致在实施阶段可能导致混淆。

**建议**：实施前统一为 `_hooks_headers()` 单一入口，并在其中增加 token 空值 warning。

**薄弱点 2：L1→L3 级联更新机制未定义（中等风险）**

三层真理源的层级关系清晰，但 L1 变更时 L3 冗余字段的同步机制仍是空白。当前设计隐含假设"L1 变更时会重新初始化 L3"，但未显式定义。

**建议**：在 `scope_guard_check()` 中增加 L1.task_key 与 L3.task_key 的一致性校验，不一致时返回 `BLOCKED_SCOPE_MISMATCH` 并触发 L3 重建。

**薄弱点 3：并行模式实现深度不足（低风险）**

并行模式的 `parallel-create` 和 `parallel-merge` 缺少代码级设计，与串行模式的完整度差距明显。考虑到当前执行模式为串行（`single_active_card=true`），这是可接受的——并行模式可在后续迭代中补充。

**建议**：在 P1 阶段仅实现串行模式，并行模式作为 P4 或后续迭代的扩展点。

**薄弱点 4：降级链未区分错误类型（低风险）**

hooks 降级链的 L1 重试层对所有错误类型一视同仁，401 认证失败也会重试 3 次。虽然最终会降级到 cron watchdog，但浪费了 14 秒。

**建议**：在 `trigger_next_round()` 中检查 HTTP 状态码，4xx 错误直接跳过重试。

## 最终结论

修正后方案的加权总分从 **7.8/10 提升至 8.3/10**，提升幅度 +0.5 分。

15 项修正中，2 项 CRITICAL（端口 + 认证）和 5 项 HIGH 的修正直接消除了 hooks-first 架构的落地阻塞项。新增的并发写入保护（flock）、Schema 升级策略、ALL_DONE 边界条件处理、R9-R12 风险项、31 条 payload 迁移 checklist 显著提升了方案的工程完备性。

剩余薄弱点（文档内部代码一致性、L1→L3 级联更新、并行模式深度、降级链错误分类）均为可操作的增量改进，不影响整体架构的正确性和可执行性。方案已达到可进入实施阶段的质量水平。
