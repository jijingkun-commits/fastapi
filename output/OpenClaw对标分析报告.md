### 一句话结论

OpenClaw 的核心优势不在于单个工具有多强，而在于**三层治理架构**（记忆治理 + 技能治理 + 工具治理）形成了一个自适应的"操作系统"，让 Agent 能够随着使用时间增长变得更聪明、随着插件增多变得更强大、随着场景复杂变得更安全。本项目在意图路由和安全护栏上有不错的基础，但在记忆、技能、工具三个核心治理层存在系统性缺失。

## 二、逐维度深度对比

### 2.1 记忆层

#### OpenClaw 做了什么

```
┌─────────────────────────────────────────────┐
│              OpenClaw 记忆架构               │
│                                             │
│  MEMORY.md (持久事实层)                      │
│    - 跨会话持久化的用户事实/偏好              │
│    - 手动 + 自动提取                         │
│                                             │
│  memory/YYYY-MM-DD.md (会话上下文层)         │
│    - 每日会话摘要                            │
│    - 自动归档                                │
│                                             │
│  Compaction (压缩机制)                       │
│    - 上下文窗口即将溢出时触发                 │
│    - 压缩前先 flush 记忆 → 防"晚期健忘症"    │
│    - 保留最近 N 条 + 摘要                    │
│                                             │
│  Hybrid Search (混合检索)                    │
│    - Vector (语义相似) + BM25 (关键词精确)    │
│    - MMR 去重 + 时间衰减                     │
│    - 多后端自动降级 (OpenAI→Gemini→本地)      │
│    - 结果带 path + line 引用                 │
└─────────────────────────────────────────────┘
```

关键设计决策：
- **Pre-compaction memory flush**：在压缩上下文之前，先把当前对话中提取的事实写入 MEMORY.md，避免压缩丢失重要信息。这是 OpenClaw "越用越聪明"的核心机制。
- **混合检索 + MMR**：纯向量检索容易返回语义相似但内容重复的结果，BM25 补充精确匹配，MMR 保证多样性，时间衰减保证新鲜度。
- **多后端降级**：embedding 服务不可用时自动切换，保证记忆检索不中断。

#### 本项目现状

```
┌─────────────────────────────────────────────┐
│              本项目记忆现状                   │
│                                             │
│  user_preference_memory_service.py           │
│    - 规则提取：触发词 + 白名单模式匹配        │
│    - 4 个维度：语言/长度/结构/语气            │
│    - DB 持久化 (user_memory_repo)            │
│    - 上下文注入 (build_user_preference_ctx)  │
│                                             │
│  LangGraph Checkpointer                     │
│    - 会话级消息持久化                         │
│    - 无压缩/摘要机制                         │
│    - 无跨会话记忆                            │
└─────────────────────────────────────────────┘
```

#### 差距分析

| 能力 | OpenClaw | 本项目 | 影响 |
|------|---------|--------|------|
| 持久事实记忆 | MEMORY.md 自动提取+持久化 | 仅 4 个偏好维度的规则提取 | 无法记住用户的业务背景、常用查询、个人习惯 |
| 会话摘要 | 每日自动归档 | 无 | 长对话后期上下文丢失，重复提问 |
| 上下文压缩 | Pre-compaction flush + 摘要 | 无（依赖 LangGraph trim_messages） | 长对话质量下降，"晚期健忘症" |
| 记忆检索 | Vector + BM25 + MMR + 时间衰减 | 无检索（仅 DB 查询最近偏好） | 无法从历史对话中召回相关信息 |
| 引用溯源 | path + line number | 无 | 无法追溯记忆来源 |

#### 改进路线

| 阶段 | 目标 | 工作量 |
|------|------|--------|
| M1: 事实提取增强 | LLM 辅助提取用户事实（替代纯规则），扩展 memory_key 白名单到业务维度（常用分行、关注指标等） | 1-2 周 |
| M2: 会话摘要 | 对话结束时生成摘要，存入 `t_chat_session_summary` 表 | 1 周 |
| M3: 上下文压缩 | 在 preprocess 节点实现 pre-compaction flush，压缩前保存关键事实 | 1-2 周 |
| M4: 混合检索 | 引入向量存储（pgvector），实现 Vector + BM25 混合检索 | 2-3 周 |

### 2.4 意图路由

#### OpenClaw 做了什么

- Supervisor 统一路由，无独立 intent_classify 节点
- 依赖 LLM 的 function calling 能力自动选择工具/Agent
- 通过 System Prompt 中的 Agent 描述引导路由

#### 本项目现状

```
┌─────────────────────────────────────────────┐
│              本项目意图路由                   │
│                                             │
│  intent_classifier.py                        │
│    - 轻量级 LLM 快速分类（节省 Token）        │
│    - 10 种意图类型                            │
│    - 返回 intent + confidence + route_to     │
│                                             │
│  agent_schema.py                             │
│    - Schema 声明式路由（借鉴 TypeAgent）      │
│    - Agent 能力注册表                         │
│    - Intent + Entity 双维度匹配              │
│    - 优先级排序                               │
│    - 动态启用/禁用                            │
│                                             │
│  multi_agent_graph.py                        │
│    - Supervisor 节点做最终路由决策             │
│    - 结合 intent_classifier 结果             │
└─────────────────────────────────────────────┘
```

#### 评价

本项目的意图路由设计**优于 OpenClaw 的简单 Supervisor 路由**：
- `intent_classifier.py` 用轻量模型预分类，节省主模型 Token
- `agent_schema.py` 的 Schema 声明式路由借鉴了 TypeAgent，支持 Intent + Entity 双维度匹配和优先级排序
- 动态启用/禁用 Agent 的能力是 OpenClaw 没有的

差距仅在于：
- 意图分类器的准确率依赖 Prompt 质量，缺少 fallback 机制（分类失败时直接返回 unknown）
- Schema 路由目前是静态注册，未与 DB 中的 `t_agent_skills` 打通

### 2.6 子 Agent 编排

#### OpenClaw 做了什么

- **Subagent 工具** (`subagents-tool.ts`)：spawn 隔离子 Agent，支持 steer/kill/list 操作，深度追踪

#### 本项目现状

- Supervisor → 专家 Agent 的单层路由
- 无子 Agent 生成能力
- 无后台任务执行
- 无深度追踪

这是一个较大的架构差距，但对当前银行业务场景（问数 + 待办）的影响有限。当需要支持"帮我同时查三个分行的数据并汇总"这类并行任务时，才会成为瓶颈。

## 六、关键设计决策建议

### 6.1 记忆层：选择 LLM 提取还是规则提取？

**建议：混合方案。** 保留现有规则提取（快、省 Token），对规则未命中但包含触发词的消息，异步调用轻量 LLM 提取。这样既不增加主链路延迟，又能扩展提取范围。

### 6.2 工具治理：V0.1 方案是否可以直接实施？

**建议：可以。** V0.1 方案的 Registry + 4 层 Policy + HookRunner 设计合理，特性开关保证了回滚安全性。建议先实施 C1-C3（纯新增文件，零风险），再实施 C4（对接 multi_agent_graph.py，有特性开关保护）。

### 6.3 技能层：是否需要对标 ClawHub？

**建议：短期不需要。** 当前项目的技能数量有限（data_expert、todo_expert、knowledge_expert），DB 管理足够。当技能数量超过 10 个或需要支持第三方插件时，再考虑技能市场。

### 6.4 子 Agent 编排：是否需要 spawn 能力？

**建议：P3 优先级。** 当前 Supervisor → 专家的单层路由能覆盖大部分银行业务场景。当出现"同时查多个分行并汇总"或"先查数据再生成报告"这类多步骤并行需求时，再引入子 Agent spawn。
