## 0. 摘要校准（融合你的结论）

你当前结论是**准确且可落地**的，建议固化为本项目的治理基线：

1. **OpenClaw 的“智能感”核心不是 skill 文案，而是规则与执行协议。**
2. **规则是多层的**（系统提示词、工具策略、审批/沙箱、串行循环与收敛判定）。
3. **skill 更像能力目录**，不负责执行闭环本身。
4. 对你当前架构（Supervisor + 专家路由）而言，最缺的是：
   - 调研任务执行协议（Checklist → 执行 → 汇总）
   - 诊断观测工具（inventory/health）
   - done criteria 驱动的收敛（而非 no-tool-call 即结束）

一句话：**先建“规则+协议+证据链”，再扩 skill 数量。**

## Q1. 最小可落地规则集模板

### 1.1 最小规则集（6 条就够）

建议先上一个 `research_protocol_v1`，只含以下 6 条：

1. **模式判定**：命中“调研/检查/排查/盘点”即进入 `investigate`。
2. **先做后说**：进入 `investigate` 后，至少完成一个检查项工具调用才能输出结论。
3. **检查项驱动**：必须按 checklist 推进；未完成项不能宣称“已完成”。
4. **收敛条件**：按 done criteria 收敛，不再使用“无 tool_call 即结束”。
5. **权限边界**：读操作直接执行；写操作必须审批。
6. **结构化报告**：最终输出必须包含 `status/findings/evidence_refs/next_steps/blockers`。

### 1.2 最小规则模板（可复制）

```yaml
rule_pack:
  id: research_protocol_v1
  trigger:
    intents: ["调研", "检查", "排查", "盘点", "评估"]
    execution_mode: investigate

  protocol:
    tool_first: true
    checklist_required: true
    max_rounds: 6
    max_no_new_evidence_rounds: 2

  done_criteria:
    type: all_items_covered
    allow_skip_with_reason: true
    force_converge_when_no_new_evidence: true

  permission_boundary:
    read_ops: direct_execute
    write_ops: require_confirmation

  final_output_contract:
    format: execution_report_v1
    evidence_refs_required: true

  fallback:
    on_tool_error: mark_item_failed_and_continue
```

### 1.3 对应你项目的最小映射

| 规则能力 | 建议落点 | 你现状 | 最小改动 |
|---|---|---|---|
| 模式判定 | `SUPERVISOR_PROMPT` | 已有意图路由 | 加 execution_mode + checklist 下发 |
| 收敛控制 | `multi_agent_graph._evaluate` | 仅 no_tool_call 结束 | 改为 done criteria 判定 |
| 证据跟踪 | `MultiAgentState` + events | 事件流已有 status/tool/result | 增加 execution_evidence 与 checklist_state |
| 权限控制 | 审批链路 | 已有 `interrupt()` 基础 | 扩展写操作审批识别 |

## Q2. 执行协议放在哪一层最稳

### 2.1 结论（先给答案）

你这个阶段最稳的答案是：**A + C 组合**。

- **A（Supervisor Prompt）**：负责“要不要进入 investigate + 下发 checklist/done criteria”。
- **C（Evaluate Node）**：负责“是否真的完成 + 是否允许结束”。
- **B（独立 Planner Node）**：短期不必上；若上，优先做“确定性 checklist 扩展器”，不是再加一个自由规划 LLM。

### 2.2 为什么不是先上独立 Planner Node

对你当前系统，独立 Planner Node 会带来：

- 新增一次 LLM 调用，延迟与复杂度同步上升。
- 规划质量不稳定时，会把“执行问题”变成“规划+执行双重不稳定”。
- 你目前真正缺的是**执行协议和完成判定**，不是缺“会规划”的节点。

### 2.3 分层职责（建议）

| 层级 | 职责 | 输出 | 是否必须 |
|---|---|---|---|
| Supervisor | 判定 execution_mode、下发 checklist/done_criteria | handoff frame | 必须 |
| Expert Agent | 实际调工具执行检查项 | tool_calls + 临时结论 | 必须 |
| Evaluate | 验证完成度/证据，决定 continue/end | goto + convergence_reason | 必须 |
| Planner Node | 复杂任务拆解（可选） | expanded checklist | 可选（后置） |

### 2.4 你的推荐流程

```text
User
  -> Supervisor（判定 investigate + 注入 checklist）
  -> Expert（按 checklist 调工具）
  -> Evaluate（按 done criteria 校验）
      -> 未完成：continue
      -> 完成/强制收敛：end
```

## Q3. 诊断工具输入输出 Schema 设计

目标不是“Schema 规范漂亮”，而是让模型**稳定先执行再汇报**。

### 3.1 核心设计原则

1. **模型可见参数最少化**：尽量零参数或单参数。
2. **运行时上下文自动注入**：`task_id/check_item_id/trace_id` 不让模型填。
3. **统一响应信封**：所有诊断工具都返回相同外层字段。
4. **显式下一步建议**：工具结果里给 `next_recommended_tools`。
5. **证据对象标准化**：每次调用都产出 `evidence_id` 与摘要。

### 3.2 两层 Schema（强烈建议）

#### A) 模型可见输入（简单）

- `kb_inventory_scan()`：零参数
- `ragflow_health_check()`：零参数
- `kb_sample_query(kb_name: str)`：单参数

#### B) 运行时信封（系统注入）

```json
{
  "task_id": "t_20260218_001",
  "check_item_id": "kb_inventory",
  "trace_id": "trace_xxx",
  "attempt": 1
}
```

> 这部分由框架注入，不暴露给模型，避免参数噪声。

### 3.3 统一输出 Schema（重点）

```json
{
  "ok": true,
  "tool_name": "kb_inventory_scan",
  "summary": "扫描到 5 个知识库，4 active，1 inactive",
  "metrics": {
    "total_kb": 5,
    "active_kb": 4,
    "inactive_kb": 1,
    "latency_ms": 118
  },
  "artifacts": [
    {"type": "table", "name": "kb_inventory", "rows": 5}
  ],
  "evidence": [
    {
      "evidence_id": "ev_kb_inventory_001",
      "kind": "api_response",
      "digest": "sha256:...",
      "preview": "kbA active 120 docs"
    }
  ],
  "next_recommended_tools": ["ragflow_health_check"],
  "error": null
}
```

### 3.4 两个关键诊断工具建议

#### `kb_inventory_scan`

- **用途**：盘点知识库规模、状态、类型、可入库性风险。
- **建议指标**：`total_kb/active_kb/inactive_kb/unsupported_file_count/duplicate_doc_ratio`。
- **关键收益**：作为后续 `kb_sample_query` 的输入来源。

#### `ragflow_health_check`

- **用途**：确认服务/API/索引任务可用性。
- **建议指标**：`service_status/api_ok/indexer_ok/queue_depth/latency_ms/error_code`。
- **关键收益**：可直接驱动 checklist 中“可执行/跳过”的判定。

### 3.5 让模型“先做后说”的提示词约束

```markdown
当 execution_mode=investigate 时：
1) 必须先完成至少一个 checklist 工具调用；
2) 未产生 evidence_id 前，不得输出“已完成调研”；
3) 每条结论都必须引用 evidence_id 或 tool_call_id。
```

## Q4. 如何避免“看起来做了其实没执行”

### 4.1 关键思路：三段式证据链

1. **执行账本（系统生成）**：记录每次真实工具调用。
2. **检查项状态机（协议层）**：记录每个 item 的 pending/running/done/skipped/failed。
3. **最终报告校验（输出层）**：无 evidence_ref 的结论不允许收敛为 done。

### 4.2 建议状态字段（可直接落地）

```python
# app/ai/state.py 建议新增
protocol_context: dict = {
  "execution_mode": "investigate|execute|direct_reply",
  "done_criteria": "all_items_covered",
  "max_rounds": 6,
  "max_no_new_evidence_rounds": 2
}

checklist_state: dict = {
  "kb_inventory": {
    "status": "pending|running|done|skipped|failed",
    "required_tools": ["kb_inventory_scan"],
    "tool_call_ids": [],
    "evidence_ids": [],
    "reason": null
  }
}

tool_execution_ledger: list = [
  {
    "tool_call_id": "call_xxx",
    "tool_name": "kb_inventory_scan",
    "args_hash": "sha256:...",
    "started_at": "2026-02-18T12:30:00Z",
    "ended_at": "2026-02-18T12:30:01Z",
    "status": "success|error",
    "output_digest": "sha256:...",
    "error_code": null
  }
]

final_report: dict = {
  "status": "done|partial|blocked",
  "findings": [],
  "evidence_refs": [],
  "next_steps": [],
  "blockers": []
}
```

### 4.3 Evaluate 节点收敛门禁（建议）

`_evaluate` 必须从“语义判断”升级为“协议判断”：

1. 若 `execution_mode != investigate`：保持原策略。
2. 若 `investigate`：
   - 所有 required checklist item 必须 `done` 或 `skipped(with reason)`。
   - `final_report.evidence_refs` 必须能映射到 `tool_execution_ledger`。
3. 若连续 `N` 轮无新 evidence：强制 `partial` 收敛，并输出未完成项。
4. 若助手文本声称“已检查”但账本无调用：注入纠偏消息继续执行。

### 4.4 推荐最终输出格式（机器可校验）

```json
{
  "status": "done",
  "findings": [
    "4/5 知识库可用，kb_finance_2025 索引异常"
  ],
  "evidence_refs": [
    {
      "check_item_id": "kb_inventory",
      "tool_call_ids": ["call_101"],
      "evidence_ids": ["ev_kb_inventory_001"]
    },
    {
      "check_item_id": "ragflow_health",
      "tool_call_ids": ["call_102"],
      "evidence_ids": ["ev_rag_health_001"]
    }
  ],
  "next_steps": [
    "重建 kb_finance_2025 索引",
    "重跑采样检索验证"
  ],
  "blockers": []
}
```

## 落地路线图（MVP 两周）

### Week 1：规则与收敛闭环

1. **Supervisor Prompt** 增加 execution_mode 与 checklist 下发约束。  
2. **State** 增加 `protocol_context/checklist_state/tool_execution_ledger`。  
3. **Evaluate** 改为 done criteria 驱动，加入 no-new-evidence 强制收敛。  

### Week 2：诊断工具与证据可视化

1. 新增 `kb_inventory_scan`、`ragflow_health_check`（统一输出信封）。  
2. 将 tool result 转为 `evidence_id` 写入 ledger。  
3. 在事件流输出 `execution_evidence`，前端展示检查项证据卡片。

```yaml
check_item_status:
  - pending
  - running
  - done
  - skipped
  - failed

transition:
  pending -> running -> done
  running -> failed
  pending/running -> skipped (reason required)
```

### C. 最小 Done Criteria 模板

```yaml
done_when:
  - all_required_items in [done, skipped_with_reason]
  - each_finding_has_evidence_ref == true

force_partial_when:
  - no_new_evidence_rounds >= 2
  - rounds >= max_rounds
```

## 最终结论

你这次判断方向是对的：**先协议后 skill**。  
对当前 FastAPI + LangGraph 架构，优先落地“Supervisor 下发协议 + Evaluate 硬门禁 + 诊断工具统一证据输出”，就能把“看起来会做”升级成“真的在做且可证明”。
