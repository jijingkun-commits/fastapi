# 多轮对话"答非所问"根因诊断与修复摘要

> 本文档供后续 AI 接手修复使用，包含完整的诊断上下文、代码定位和修复方案。

---

## 一、问题描述

系统存在多轮对话"答非所问"现象：上一轮讨论过的问题，下一轮 Supervisor 就不知道用户意图，将补充/追问类消息当作全新问题处理。

---

## 二、架构概览

```
chat_service.stream()
  → graph.astream(input_state)           // input_state 只含当前轮 HumanMessage
  → LangGraph checkpoint 自动加载历史     // 历史消息从 PostgreSQL checkpoint 恢复
  → multi_agent_graph:
      START → preprocess → supervisor → [data_expert | todo_expert] → evaluate → postprocess → END
```

消息流转关键路径：
1. `chat_service.py` 构造 `input_state = {"messages": [HumanMessage(prompt)], ...}`
2. LangGraph checkpoint 自动将历史消息与新消息合并
3. `_create_streaming_agent_wrapper()` 内部对合并后的消息执行裁剪
4. 裁剪后的消息传给 Supervisor LLM 做路由决策

---

## 三、根因定位

### 根因：Token 预算过小导致历史被完全裁剪

**关键代码位置**：`app/ai/workflow/multi_agent_graph.py` 的 `_create_streaming_agent_wrapper()` 函数内部（约第 380-420 行）：

```python
# 1. 压缩超长 ToolMessage
prepared_messages = _prepare_messages_for_supervisor_inference(original_messages)

# 2. 计算 token 预算
from app.ai import config as ai_config
token_budget = _calculate_supervisor_context_budget(
    getattr(ai_config, "MESSAGE_MAX_TOKENS", SUPERVISOR_CONTEXT_MIN_TOKENS)
)

# 3. 按预算裁剪消息
pruned_messages = trim_messages(
    prepared_messages,
    max_tokens=token_budget,
    token_counter=count_tokens_approximately,
    strategy="last",
    start_on="human",
    end_on=("human", "tool", "ai"),
    include_system=True,
    allow_partial=False,
)
```

**关键数字**：
- `MESSAGE_MAX_TOKENS` 环境变量默认值：`4096`（定义在 `app/core/config.py`）
- `SUPERVISOR_CONTEXT_TOKEN_BUDGET_RATIO`：`0.85`
- 实际预算：`4096 × 0.85 = 3481 tokens`
- 一轮含工具调用的对话（SQL 结果、知识库文档）轻松消耗 2000-3000 tokens
- 结果：到第 2-3 轮时，上一轮问答已被 `trim_messages` 完全丢弃

### 叠加因素

| # | 问题 | 代码位置 | 影响 |
|---|------|---------|------|
| 1 | Token 预算过小（3481 tokens） | `app/core/config.py` → `MESSAGE_MAX_TOKENS=4096` | 2-3 轮后历史被完全裁剪 |
| 2 | 裁剪后无摘要注入 | `multi_agent_graph.py` → `_create_streaming_agent_wrapper` | 被裁掉的历史没有任何摘要保留 |
| 3 | Supervisor Prompt 缺乏多轮记忆指引 | `app/ai/prompts/agent_prompts.py` → `SUPERVISOR_PROMPT` | 决策树是单轮设计，无"先回顾历史再决策"指令 |

## 五、修复方案

### P0 - 扩大 Token 预算（立即见效，改一行配置）

**文件**：`.env` 或 `app/core/config.py`

将 `MESSAGE_MAX_TOKENS` 从 `4096` 提升到 `16384` 或更高。当前主流模型（Qwen/DeepSeek/GPT-4o）都支持 128K+ 上下文窗口，4096 过于保守。

```python
# app/core/config.py
MESSAGE_MAX_TOKENS = int(os.getenv("MESSAGE_MAX_TOKENS", "16384"))  # 原值 4096
```

或在 `.env` 中设置：
```
MESSAGE_MAX_TOKENS=16384
```

实际预算变为 `16384 × 0.85 = 13926 tokens`，足以保留 5-8 轮对话历史。

### P1 - Supervisor Prompt 增加多轮规则

**文件**：`app/ai/prompts/agent_prompts.py`

在 `SUPERVISOR_PROMPT` 的"执行原则"章节末尾增加：

```
5. **多轮上下文继承**：做出路由决策前，必须先回顾对话历史中最近 2-3 轮的问答：
   - 如果用户当前消息是短回复（如"好的""图表""按分行""柱状图"），必须结合上一轮 AI 回复理解完整意图
   - 委派给专家时，task_description 必须携带上一轮的关键上下文（已确认的指标、时间范围、维度、查询结果等）
   - 禁止将补充/追问/确认类消息当作全新问题处理
   - 如果上一轮是某个专家处理的，且用户在追问/补充，优先委派给同一个专家
```

### P2 - 引入对话摘要机制（中期优化）

**文件**：`app/ai/workflow/multi_agent_graph.py`

在 `_create_streaming_agent_wrapper()` 的 `trim_messages` 之前，对即将被丢弃的消息生成摘要：

思路：
1. 计算裁剪前后的消息差集（被丢弃的消息）
2. 对被丢弃的消息提取关键信息（用户问了什么、AI 回答了什么、涉及哪个专家）
3. 将摘要作为 SystemMessage 注入到裁剪后的消息列表开头

伪代码：
```python
# 裁剪前的消息
all_messages = prepared_messages

# 裁剪后的消息
pruned_messages = trim_messages(...)

# 计算被丢弃的消息数
dropped_count = len(all_messages) - len(pruned_messages)

if dropped_count > 0:
    # 提取被丢弃消息的摘要（可用轻量 LLM 或规则提取）
    dropped_messages = all_messages[:dropped_count]
    summary = _summarize_dropped_context(dropped_messages)  # 需新建此函数
    
    # 注入摘要
    summary_msg = SystemMessage(content=f"[历史对话摘要] {summary}")
    pruned_messages = [summary_msg] + pruned_messages
```

## 七、验证方法

修复后可通过以下场景验证：

1. **基础多轮**：第一轮问"查询上月贷款余额"，第二轮问"按分行统计"→ 应继承"上月贷款余额"上下文
2. **短回复追问**：第一轮问数据，第二轮说"画个图表"→ 应基于上一轮数据生成图表
3. **跨专家多轮**：第一轮创建待办，第二轮补充时间地点 → 应识别为待办补充而非新问题
4. **5轮以上对话**：连续对话 5 轮以上，检查第 5 轮是否仍能理解第 3-4 轮的上下文
